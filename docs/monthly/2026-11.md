## [#59476](https://github.com/rails/rails/pull/59476) Fix Active Support inline RBS signatures {#pr-59476}

**マージ日**: 2026/10/31 | **作成者**: [@amatsuda](https://github.com/amatsuda)

1. 概要 (1-2文で)  
Active Support に最近追加された「インライン RBS 型定義」と、実際の Ruby 実装とのズレをまとめて修正した PRです。主に「メソッドが本当は受け付けない値を受け付けることになっていた型」や、「戻り値の型が実装より粗かった箇所」が、実装に沿うように精密化されています。

---

2. 変更内容の詳細  

### 全体像

- 対象は Active Support のインライン RBS (`# :sig` コメント形式) で、実装と異なる部分を `gem_rbs_collection` にある手書きシグネチャと突き合わせて修正。
- 修正は大きく分けて:
  - 「実装では拒否される値を受け付けることになっていたシグネチャの修正」
  - 「振る舞いは正しいが、型がラフすぎたシグネチャの精密化」
- 実装コード自体はほぼ変えず、型側の修正が中心です。

---

### 実装が拒否する値を許容していたシグネチャの修正

#### 1) `ActiveSupport::ErrorReporter#report` / `#unexpected`

**Before (誤った型イメージ)**  
```rbs
def report(..., severity: Symbol?): void  # nil も OK という扱い
```

**After (正しい型のイメージ)**  
```rbs
def report(..., severity: Symbol): void   # nil は NG
```

- 実装では `severity` が `SEVERITIES` に含まれるかをチェックしており、`nil` を渡すと `ArgumentError`。
- よって `Symbol?`（`nil` 許容）ではなく、`Symbol` 固定に修正。

**挙動例**

```ruby
reporter.report(error, severity: nil)  # 実装上 ArgumentError になる
```

→ 型もこれを反映して `nil` 不可。

---

#### 2) `String#pluralize`

**Before**  
```rbs
def pluralize(count: Integer?, locale: Symbol?): String
```

**After**  
```rbs
def pluralize(count: Integer?, locale: Symbol): String
```

- 実装では `locale` に `nil` を渡すと `I18n::InvalidLocale` が発生。
- 従って「`nil` も受け取れる」という型は誤り。

**挙動例**

```ruby
"post".pluralize(2, nil) # => I18n::InvalidLocale が raise される
```

→ `locale` は `Symbol` のみ受け取るシグネチャに修正。

---

#### 3) `Array#in_groups` / `Array#in_groups_of` のグループサイズ

**Before**  
```rbs
def in_groups_of(number: Integer | Float, ...): Array[Array[...]]
```

**After**  
```rbs
def in_groups_of(number: Integer, ...): Array[Array[...]]
```

- 実装は `Integer` を期待しているが、`Float` を渡しても Ruby 側で `to_i` 的な解釈で動いてしまうケースがある。
- 型として「Float も正式サポート」とは言えないため、`Integer` のみに制限。
- `in_groups` も同様に修正。

**挙動例（実装側の実際の動き）**

```ruby
[1, 2, 3].in_groups_of(2.5)
# => [[1, 2], [3, nil], [nil]]
```

このように「たまたま動く」挙動はあるが、型として保証したい仕様ではないので `Integer` のみに。

---

#### 4) `ActiveSupport::Rescuable.rescue_from`

**Before (ざっくり 1 パターン)**  
```rbs
def rescue_from(*klasses, with: ^(Exception) -> untyped ?): void
```

**After (block 版 / with: 版の 2 パターンに分割)**  
- `with:` キーワードを使うオーバーロード
- ブロックを渡すオーバーロード

加えて:

- 「`with:` もブロックもどちらも指定しない」呼び出しは実装上 `ArgumentError` になるため、型的にも「必ずどちらかが必要」であることを表現。
- ブロックハンドラは実際には `instance_exec` でレシーバに対して実行されるため、型もそれに即した形に。

**挙動イメージ**

```ruby
# OK: with: ハンドラ
rescue_from SomeError, with: :handle_some_error

# OK: ブロックハンドラ
rescue_from SomeError do |exception|
  # ...
end

# NG: どちらも指定していない
rescue_from SomeError       # => ArgumentError (実装)
```

---

#### 5) `assert_changes`

**Before**  
```rbs
def assert_changes(expression, message: untyped?, &block): void
# expression: Proc | Kernel となっており、ほぼ何でも通ってしまう
```

**After**  
```rbs
def assert_changes(
  expression: String | Symbol | ^() -> untyped,
  message: String? = nil,
  &block: ^() -> untyped
): void
```

- 実装では `_expression_to_callable` が `String | Symbol | Proc` のみを受け付けている。
- それに合わせて:
  - `expression` の型: `String | Symbol | ^() -> untyped` に限定
  - `message` は実際には `String?` で扱われているので、`untyped` -> `String?` に精密化

**使用例**

```ruby
assert_changes -> { user.reload.name } do
  user.update!(name: "new")
end

assert_changes :updated_at, "timestamp should change" do
  user.touch
end
```

---

### 型が粗く、実装よりも情報量が少なかった箇所の精密化

#### 6) `Array#in_groups` / `Array#in_groups_of` の戻り値・fill オプション

- `fill_with` によって以下の 3 パターンがあるため、オーバーロードで表現:
  1. `fill_with` 省略 / `nil` … パディング要素は `nil`
  2. `fill_with: false` … パディングなし（最後の配列のサイズが小さくなり得る）
  3. `fill_with` に任意の値 … その値でパディング

- グループの中に `nil` が入るのは「パディングに `nil` を使う場合のみ」であることを型に反映。

- `in_groups_of` にブロックを渡した場合の戻り値も修正:
  - 実装上は「ブロックに各グループを渡して、**元の配列自身**を返す」ため、
  - 戻り値型を「グループの配列」ではなく「レシーバの `Array`」に合わせている。

**挙動例**

```ruby
[1,2,3].in_groups_of(2)
# => [[1, 2], [3, nil]]

[1,2,3].in_groups_of(2, false)
# => [[1, 2], [3]]

[1,2,3].in_groups_of(2, 0)
# => [[1, 2], [3, 0]]

[1,2,3].in_groups_of(2) { |group| p group }
# ブロックに [1,2], [3,nil] が渡され、戻り値は [1,2,3] (元配列)
```

---

#### 7) `String#in_time_zone`

- ゾーン指定あり / なし で戻り値が異なることをオーバーロードで表現。
  - ゾーン指定あり: `ActiveSupport::TimeWithZone?`
  - ゾーン指定なし: `Time?`
- 空文字列 (`""`) の場合は両方とも `nil` を返し得るので、`?` 付き。

**挙動例**

```ruby
"2024-01-01".in_time_zone      # => ActiveSupport::TimeWithZone
"2024-01-01".in_time_zone("UTC")  # => ActiveSupport::TimeWithZone
"".in_time_zone                # => nil
```

---

#### 8) `String#squish!` / `String#remove!`

- 戻り値は「標準の `String`」ではなく **レシーバ自身 (`self`)** であることを反映。
  - `SafeBuffer` のようなサブクラスに対しても、`SafeBuffer` のまま戻ってくる。

**挙動例**

```ruby
buf = ActiveSupport::SafeBuffer.new("  foo  ")
res = buf.squish!
res.class # => ActiveSupport::SafeBuffer
res.equal?(buf) # => true
```

→ 型でも `self` を返すようにして、サブクラス情報が失われないようにした。

---

#### 9) 真偽値フラグ引数を `bool` → `boolish` に

対象メソッド:  
- `String#titleize`
- `String#humanize`
- `String#parameterize`
- `String#foreign_key`
- `String#indent`
- `String#indent!`

- これらのオプション引数は実装上「真偽そのもの」ではなく「truthiness（真として評価されるか）」でチェックしている。
  - 例: `if options[:uppercase]` のような単純真偽値チェック
- そのため、厳密な `bool` ではなく、RBS 用語での「`boolish`（true と評価されうる型）」として定義。

**イメージ**

```ruby
"foo".titleize(keep_id_suffix: "yes")  # "yes" も truthy として扱われる
```

→ 実装と整合が取れるように、型も「Ruby 的な truthiness」を許容する。

---

3. 影響範囲・注意点  

- **主な影響は「型チェック／型補完ツール」側**  
  - RBS を用いた静的解析、型補完、エディタ支援などで、より実装に忠実な警告・補完が行われるようになります。
  - 実装挙動そのものはほとんど変えていないため、既存アプリのランタイム挙動への影響は基本的にありません。

- **型上は NG になるケース**
  - `ErrorReporter#report(severity: nil)` のように、実装上もエラーになる呼び出しが、型でもコンパイルエラーとして指摘されるようになります。
  - `Array#in_groups_of(2.5)` のような「たまたま Ruby が受け入れていた」ケースは、型的には不正な呼び出しとして扱われます（実装は変わっていないため、実行は従来どおり可能）。

- **負の影響になりにくい修正**
  - `String#in_time_zone` や `squish!` がより正確な戻り値型になることで、エディタ補完や後続処理の型推論精度が向上。
  - `assert_changes` や `rescue_from` のインタフェースが正しくモデリングされたことで、テストコード・コールバック定義時のミスを静的に検出しやすくなります。

- **RBS inline の制約による未対応ポイント**
  - `HashWithIndifferentAccess[T, U]` や `ArrayInquirer[T]` は、本来ジェネリクスだが、インライン RBS はジェネリッククラスを定義できないため、戻り値型は「生のクラス」まで。
  - `Object#in?` / `#presence_in` は `untyped` のまま。
    - `gem_rbs_collection` では `_IncludeP` というインタフェースで表現しているが、インラインでは定義できないため。

## [#59308](https://github.com/rails/rails/pull/59308) Instrument connection pool checkout waits {#pr-59308}

**マージ日**: 2026/10/31 | **作成者**: [@andrewfader](https://github.com/andrewfader)

1. 概要 (1-2文で)  
Active Record のコネクションプールで、空きコネクションがなくて `checkout` がブロックしている待ち時間を、`checkout_wait.active_record` というイベントとして計測・通知できるようにした変更です。これにより、プール逼迫時の「よく分からない遅さ」が可観測になり、`ConnectionTimeoutError` が出る前から問題把握・チューニングがしやすくなります。

---

2. 変更内容の詳細  

### 何を計測するようになったか

- 対象: Active Record のコネクションプール (`ActiveRecord::ConnectionAdapters::ConnectionPool`) における `acquire_connection` 内の「待ち時間」
- 条件:  
  1. アイドルなコネクション取得が失敗  
  2. バックグラウンドコネクションの取得もできない  
  3. 新規コネクションの作成もできない  
  → つまりプールが一杯で、他のスレッドがコネクションを返すのを待つしかない状態  
- その「ブロックして待っている区間」を `checkout_wait.active_record` という Active Support Instrumentation イベントとして発火します。

### イベント名とペイロード

- イベント名:  
  - `checkout_wait.active_record`
- 主なペイロード:
  - `:connection_pool`  
    - 対象となるコネクションプールオブジェクト（もしくは識別可能な情報）
  - `:checkout_timeout`  
    - 設定されている `checkout_timeout` の値（秒）
  - タイムアウトした場合:
    - `:exception`  
      - `ConnectionTimeoutError` などが入る（ActiveSupport::Notifications 標準の `:exception` 形式に準拠）

イベントの「duration（処理時間）」は「実際にブロックして待った時間」になります。  
つまり、checkout に成功した場合も、タイムアウトした場合も、その前にどれくらい待たされたかが計測可能です。

### 実行タイミングとロックとの関係

- イベント発火はプールのロックの「外側」で行われます。  
  - これにより、Instrumentation 自体がプールのロック競合を悪化させないように配慮されています。
- 例外として、「ピン留めされていたコネクションが破棄され、プール側にフォールバックして取り直す」ような経路では、ロック内で発火される場合がありますが、これはレアケースです。

### コード変更の概要

変更ファイル:

- `activerecord/lib/active_record/connection_adapters/abstract/connection_pool.rb`
  - `acquire_connection` 内に `ActiveSupport::Notifications.instrument("checkout_wait.active_record", payload) { ... }` のような計測ブロックが追加された形（+3/-1 行程度の小変更）。
- `activerecord/test/cases/connection_pool_test.rb`
  - `checkout_wait.active_record` イベントが正しく発火し、ペイロードや例外情報が期待通りであることを確認するテストが追加（+33 行）。
- `guides/source/active_support_instrumentation.md`
  - Active Support Instrumentation ガイドに `checkout_wait.active_record` の説明を追加（+12 行）。
- `activerecord/CHANGELOG.md`
  - 新しい計測イベント追加のエントリを追加（+8 行）。

### サンプルでの利用イメージ

アプリ側でこのイベントを購読すると、プール逼迫状況が可視化できます。例:

```ruby
ActiveSupport::Notifications.subscribe("checkout_wait.active_record") do |name, start, finish, id, payload|
  wait_ms = (finish - start) * 1000.0
  pool    = payload[:connection_pool]
  timeout = payload[:checkout_timeout]

  Rails.logger.warn(
    "[DB checkout wait] waited=%.1fms timeout=%.1fs pool=%s" % [
      wait_ms,
      timeout,
      pool.object_id # あるいは pool.spec.config などでより識別しやすく
    ]
  )
end
```

もしくは StatsD / Prometheus などにメトリクスとして送ることもできます:

```ruby
ActiveSupport::Notifications.subscribe("checkout_wait.active_record") do |_name, start, finish, _id, payload|
  wait = finish - start   # 秒
  MyStatsd.histogram("db.checkout_wait", wait, tags: ["timeout:#{payload[:checkout_timeout]}"])
end
```

3. 影響範囲・注意点  

- パフォーマンス・動作への影響
  - 通常の `checkout`（すぐにアイドルコネクションが取れる場合）は、このイベントは発火しません。
  - イベントはロック外で発火するため、プールの性能劣化リスクは低いです。
  - ただし、プールが慢性的に逼迫している環境では、このイベントが頻発するため、購読側（ログ出力・メトリクス送信）のオーバーヘッドに注意する必要があります。
- エラー（`ConnectionTimeoutError`）との関係
  - これまでは、`ConnectionTimeoutError` が起きるまで「何が遅いのか分からない」状態になりがちでしたが、
  - 今後はタイムアウト発生前から、待ち時間分のイベントが飛ぶため、「プールに空きがなくて詰まっている」ことを早期に検知できます。
- 計測の粒度
  - 計測対象はあくまで「プールが一杯で他スレッドの返却を待っている時間」のみです。
  - コネクション取得前後のアプリ処理時間やクエリ実行時間は別途、既存の instrumentation（`sql.active_record` など）で見る必要があります。
- バージョン依存
  - この PR は Rails 本体への変更なので、マージされたバージョン以降（Active Record の該当バージョン）でのみ利用可能です。
  - 自前で `ConnectionPool#checkout` に prepend して計測していた場合、この公式イベントに切り替えることで、パッチの維持コストを減らせます。

## [#59404](https://github.com/rails/rails/pull/59404) Compile Arel SQL up to 1.23x faster under YJIT by avoiding each_with_index in ToSql {#pr-59404}

**マージ日**: 2026/10/31 | **作成者**: [@czj](https://github.com/czj)

1. 概要 (1-2文で)  
Arel の SQL 生成処理（ToSql ビジター）から `each_with_index` / `inject` を排除し、YJIT（および ZJIT）で最適化しやすい `each` ベースのループに書き換えることで、SQL コンパイルを最大約 1.23 倍高速化するパフォーマンス改善 PRです。生成される SQL 自体はビット単位で同一であり、挙動変更はありません。

---

2. 変更内容の詳細  

### 背景・問題点

- プロファイルの結果、リレーションを SQL にコンパイルする際の自己時間の約 10% を `Enumerable#each_with_index` が占めていることが判明。
- 対象箇所は `Arel::Visitors::ToSql#inject_join` などで、AND/OR の連結、SELECT の投影リスト、ORDER BY など、SQL 文字列を組み立てるほぼ全ての「区切り文字を挟みながら列挙する」処理。
- `each_with_index` は C 実装であり、内部で `Array#each` を呼んで Ruby 側に yield する構造になっているため、YJIT が Ruby レベルでループ全体を最適化できない。
- 一方 Ruby 3.4+ では `Array#each` が Ruby 実装となり、YJIT がループ本体をそのまま JIT コンパイルできるため、`each_with_index` より `each` + Ruby 変数で index/フラグを持つ方が高速になりうる。

### 具体的なコード変更ポイント

変更ファイルは 1つのみ:

- `activerecord/lib/arel/visitors/to_sql.rb` (+6 / -12)

主な変更は次の3点です。

#### (1) `inject_join` から `each_with_index` を除去

元のイメージ（擬似コード）:

```ruby
def inject_join(sql, values, join_string)
  values.each_with_index do |value, i|
    sql << join_string unless i == 0
    # value に対する visit 等
  end
end
```

これを「最初の要素かどうか」を判定する `first` フラグに書き換え:

```ruby
def inject_join(sql, values, join_string)
  first = true
  values.each do |value|
    unless first
      sql << join_string
    end
    first = false

    # value に対する visit 等（元と同じ）
  end
end
```

ポイント:
- アルゴリズム・出力 SQL は同じまま、`each_with_index` を使わない構造に変更。
- これによりループ全体が Ruby コードだけで構成され、YJIT がまとめて最適化しやすくなる。

#### (2) `visit_Arel_Nodes_SelectStatement` での `inject` を `each` に変更

`Arel::Nodes::SelectStatement` を SQL に変換するビジター `visit_Arel_Nodes_SelectStatement` 内で:

- cores の列挙に `inject` を使っていた部分を、`each` ベースの普通のループに変更。
  - `inject` も C 実装で yield を繰り返すため、YJIT 観点では `each_with_index` と同種のボトルネックになりうる。
- ロジックとしては「複数 core を結合して SELECT 文全体の SQL を構築する」処理はそのままに、Ruby ループを素直に書き下した形に。

具体的なコードは PR 本文には載っていませんが、パターンとしては次のような変化です:

```ruby
# 変更前のイメージ
cores.inject(String.new) do |sql, core|
  # core を visit して sql に << して返す
end

# 変更後のイメージ
sql = +""
cores.each do |core|
  # core を visit して sql に << する
end
sql
```

#### (3) SELECT の ORDER BY を `collect_nodes_for` 経由に統一

これまで:

- UPDATE / DELETE の ORDER BY はすでに `collect_nodes_for` 経由で処理していた。
- SELECT の ORDER BY だけ、`collect_nodes_for` 相当の処理をその場でインライン実装していた。

今回:

- SELECT の ORDER BY も `collect_nodes_for` を利用するように変更し、ロジックを共通化。
- `collect_nodes_for` / `inject_join` をオーバーライドしているアダプタ側は、今後 SELECT の ORDER BY に対してもそのオーバーライドが適用されるようになる。

この変更も、生成される SQL は従来とバイトレベルで同一になるよう確認済みです。

---

3. 影響範囲・注意点  

### 性能面の影響

PR のベンチマーク結果（arm64, 5回交互計測の中央値）:

- Ruby 4.0.9 + YJIT:  
  - compile: 168.8k → 207.6k i/s (+23.0%)  
  - to_sql: 57.9k → 63.0k i/s (+8.8%)
- Ruby 3.3.13 + YJIT:
  - compile: +7.2%
  - to_sql: +3.1%
- Ruby 4.1.0-preview1 + ZJIT:
  - compile: +13.5%
  - to_sql: +5.0%
- 素のインタプリタ (YJIT/ZJIT なし) でもわずかにプラスか横ばい（3–4% 程度の改善〜誤差レベル）。

補足:

- メモリアロケーション数は「変更なし」。
- メリットが大きいのは Ruby 3.4+ の「`Array#each` が Ruby 実装」な環境で、YJIT (および ZJIT) を有効にした場合。
- Ruby 3.3 では `Array#each` がまだ C 実装なので、効果は小さめ（それでも若干の改善）。

### 機能的な影響（互換性）

- Rails/ActiveRecord 本体の振る舞いとしては、生成される SQL はテスト用に生成した 5,000 個のランダムなリレーションに対して「バイト列レベルで完全一致」と確認済み。
  - inlined values / bind values あり・なし双方で比較。
  - 「構造的に不正」なケース 216 件についてもエラー内容は一致。
- したがって、アプリケーションレベルの SQL 内容・挙動に変更はない前提。

ただし、次の点は注意が必要です:

#### サードパーティアダプタへの影響

- private メソッドである `collect_nodes_for` または `inject_join` をオーバーライドしているアダプタ（独自 DB アダプタや fork など）がある場合:
  - これまでは SELECT の ORDER BY にはそのオーバーライドが効いていなかったが、
  - 今回から SELECT の ORDER BY も `collect_nodes_for` / `inject_join` を通るようになる。
- つまり、「ORDER BY の SQL の書き方をアダプタ側でカスタマイズ」している場合、その挙動が SELECT にも波及する可能性がある。
  - 本来は private メソッドのオーバーライド自体が非推奨だが、もしやっている場合は挙動確認を推奨。

#### テスト・ドキュメント

- テスト追加・更新はこの PR では実施されていない（既存テストと SQL 同値性チェックでカバー）。
- CHANGELOG も更新されていない（挙動変更ではなく微小なパフォーマンス改善のため）。

## [#59479](https://github.com/rails/rails/pull/59479) Keep the optimized URL helpers with default URL options that don't shape the path {#pr-59479}

**マージ日**: 2026/10/31 | **作成者**: [@linyiru](https://github.com/linyiru)

1. 概要 (1-2文で)  
`routes.default_url_options` や `default_url_options` に `host` などの「パスに影響しないオプション」だけが設定されている場合でも、パフォーマンスの良い「最適化された URL ヘルパー」を使い続けられるようにする変更です。これにより、特にシリアライザや ActivityPub などリクエスト外で URL を大量生成するケースで、オブジェクト数・処理時間の削減が見込まれます。

---

2. 変更内容の詳細  

### これまでの挙動

- `routes.default_url_options`（ルートセット全体のデフォルト）や  
  コントローラ／メイラーの `default_url_options`（レシーバ単位のデフォルト）に **何か1つでも** オプションがあると、
  - `post_path(1)` や `post_url(1)` といった「最適化された URL ヘルパー」が無効になり、
  - 常に汎用ルート解決経路（`RouteSet#url_for` がフルに動く「general path」）が使われていました。
- これは、`host` しか設定していなくても同様で、  
  たとえばシリアライザ／メイラーでよくやる次のような設定だけでも最適化ヘルパが無効化されていました:

  ```ruby
  Rails.application.routes.default_url_options[:host] = "example.com"
  # または
  def default_url_options
    { host: "example.com" }
  end
  ```

- 一方で `RouteSet#url_for` 自体は、`RESERVED_OPTIONS`（予約済みオプション）として、  
  `:host, :protocol, :port, :script_name, :trailing_slash, ...` などは **パス生成には使わず**、  
  最終的な URL の組み立て (`ActionDispatch::Http::URL`) にだけ渡すようになっています。  
- 以前の PR (#59350) で、**明示的に引数で渡した** 予約済みオプションについては  
  最適化ヘルパー内で既にうまく扱うようになっていましたが、  
  **default_url_options 経由のオプション** は依然として「最適化ヘルパーを無効にする要因」のままでした。

### 今回の変更のポイント

1. **「パスに影響しない default_url_options だけなら最適化を維持」**

   - default_url_options に含まれるキーが
     - `RESERVED_OPTIONS` に含まれる、かつ
     - `:params` ではない
   - のみで構成されている場合、最適化された URL ヘルパーをそのまま使うように変更されました。
   - 具体例（いずれも「最適化ヘルパーを維持」されるようになる）:

     ```ruby
     # ルートセット全体
     routes.default_url_options = {
       host: "example.com",
       protocol: "https",
       trailing_slash: false,
     }

     # コントローラ側
     def default_url_options
       { host: "example.com", port: 3000 }
     end
     ```

   - 逆に、以下のような「パスやクエリに影響する」オプションが1つでも混ざると、
     従来どおり汎用ルート解決経路にフォールバックします:

     ```ruby
     # パスを変えるものの例
     { locale: :en }         # /en/posts/1 など
     { format: :json }       # /posts/1.json

     # クエリを増やすものの例
     { params: { page: 2 } }
     { page: 2 }

     # 文字列キー
     { "locale" => "en" }
     ```

2. **ルートセット側の default_url_options のマージ順を、`RouteSet#url_for` に合わせる**

   - `RouteSet#url_for` は、最後に `routes.default_url_options` をマージする挙動になっています。
   - 最適化されたヘルパーで default_url_options を扱う際にも、  
     この挙動と **同じマージ順** になるように変更されています。
   - これにより、同じ入力（パラメータ・default_url_options）に対して  
     「最適化ヘルパー」と「general path（url_for 経由）」が **同じ URL あるいは同じエラー** を返すことが保証されます。

3. **「そもそも最適化できないルート」は、default_url_options があるときも従来どおり general path を使う**

   - 一部のルートは構造上、最適化ヘルパーで安全に扱えません。例:
     - 「予約済みオプションと同名のセグメントがあるルート」  
       例: `get "/:host/posts/:id", to: "posts#show"`
     - 「必須セグメントの前にオプショナルセグメントがあるルート」  
       例: `scope "(:locale)" do; resources :posts; end`
   - この PR では、**そういった最適化不能なルート** に対しては、
     default_url_options が設定されている場合に **無理に最適化しない** ようになっています。
   - これにより、引数の位置解釈（positional arguments）などで  
     general path と挙動がずれないようにしています。

4. **パフォーマンス計測結果（Ruby 3.4）**

   予約済みオプションだけを default_url_options に設定している場合の改善例:

   | 呼び出し | オブジェクト数 (before → after) | 時間 (before → after) |
   |----------|----------------------------------:|-----------------------:|
   | `post_url(1)` + `routes.default_url_options[:host]` | 27 → 11 | 7.41 → 2.88 µs |
   | `post_path(1)` + `routes.default_url_options[:host]` | 25 → 9  | 6.40 → 2.10 µs |
   | `post_url(1)` + `def default_url_options = { host:, protocol: }` | 27 → 12 | 7.89 → 3.20 µs |

   いずれも 2〜3 倍近い高速化と、オブジェクト数の半減に近い効果が出ています。

5. **実アプリ（Mastodon v4.7.4）での効果**

   Mastodon ではシリアライザや ActivityPub 用に次のような default_url_options を利用:

   ```ruby
   {
     host: host,
     protocol: "https://",
     trailing_slash: false,
   }
   ```

   これにより、タイムライン 1 リクエストあたり 302 回もの route helper 呼び出しが  
   すべて general path になっていましたが、この PR 適用後は最適化ヘルパーが使われるようになり、
   1 リクエストあたりのオブジェクト数が以下のように削減されています（3 回の交互実行で同一値）:

   | Endpoint | main | このブランチ | 削減率 |
   |----------|-----:|------------:|------:|
   | Home timeline (20 statuses) | 120,721 | 113,401 | −6.1% |
   | Public timeline             | 74,648  | 70,028  | −6.2% |
   | Account statuses            | 93,309  | 87,609  | −6.1% |
   | ActivityPub outbox page     | 62,900  | 57,731  | −8.2% |
   | Status                      | 11,261  | 11,030  | −2.0% |

   なお、これは #59474（requirements 付きルートを最適化可能にした変更）の効果も含みます。  
   Mastodon の ActivityPub ルートは requirements を持ち、従来は default_url_options があると最適化を妨げていました。

6. **テスト**

- 22 種類のヘルパー呼び出し × 10 パターンの default_url_options について、
  - 最適化ヘルパーと general path が同じ URL もしくは同じエラーを返すことを確認。
- default_url_options を routes 側とレシーバ側（コントローラやオブジェクト）それぞれに設定したパターンを網羅。
- オプショナルセグメント、グロブ、format、エスケープ済みセグメント、requirements のあるルートとその失敗ケース、
  クエリパラメータ・URLオプションなどを含む。
- さらに以下を確認するテストも追加:
  - 条件を満たす default_url_options があるときに、きちんと最適化ヘルパーが使われること。
  - パスに影響する default_url_options があるときには、依然として general path が使われること。
  - route set の defaults がちゃんとマージされていること。
  - 最適化不能なルートが default_url_options のせいで誤って最適化されないこと。

---

3. 影響範囲・注意点  

- **パフォーマンス面**
  - `host` や `protocol` など、パスに影響しない default_url_options を多用しているアプリ（API サーバー、マイクロブログ系、SNS など）で特に恩恵が大きいです。
  - URL ヘルパーを大量に呼ぶ箇所（シリアライザ、バックグラウンドジョブ、ActivityPub など）でオブジェクト数・CPU 時間が目に見えて減る可能性があります。

- **互換性・挙動**
  - 最適化ヘルパーと general path で URL/エラーの結果が一致するよう厳密にテストされており、  
    正常系・異常系ともに挙動変更は原則ありません（内部実装の差し替えに近い）。
  - ただし、もしアプリ側が
    - 「わざと general path にフォールバックさせていた」
    - かつ「default_url_options に予約済みオプションだけを載せていた」
    ような極端なケースでは、今回からフォールバックしなくなりパフォーマンスが向上しますが、
    その挙動変化を前提にしていたコードがあると影響を受ける可能性はあります（通常は想定されないパターンです）。

- **default_url_options の設計方針への示唆**
  - 「パスを変える要素（`locale`, `format` など）」「クエリを変える要素（`params`, `page` など）」と、
    「ホストやプロトコルなどの URL メタ情報」を default_url_options で明確に分けて管理すると、
    今回の最適化の恩恵を最大限に受けられます。
  - `default_url_options` に「クエリパラメータ相当」を足していくと、  
    今回の最適化条件から外れてしまい general path に戻る点に注意してください。

## [#59471](https://github.com/rails/rails/pull/59471) Reduce allocations of polymorphic URL helpers with arrays and actions {#pr-59471}

**マージ日**: 2026/10/31 | **作成者**: [@linyiru](https://github.com/linyiru)

1. 概要 (1-2文で)  
polymorphic_path / polymorphic_url 系ヘルパーを「配列引数」や「アクション付き」で呼び出したときのオブジェクト生成数を減らし、パフォーマンスを改善する変更です。動作（生成されるURLやヘルパー名）は一切変えず、内部実装だけを最適化しています。

---

2. 変更内容の詳細  

### 対象となるヘルパー

- `polymorphic_path`, `polymorphic_url`
- `edit_polymorphic_path`, `new_polymorphic_path`, などアクション付きのポリモーフィックヘルパー
- 特に配列を使った呼び出し:
  - `polymorphic_path([user, comment])`
  - `polymorphic_path([user, Comment])`
  - `polymorphic_path([:edit, post])`
  - `polymorphic_path([:edit, user, comment])`
  - `form_with(model: [post, comment])`
  - `link_to "Edit", [:edit, post]`
などでオブジェクトアロケーションを削減しています。

---

### 主な最適化ポイント

#### 1) 配列のコピー回数削減

これまで:

- `polymorphic_method` が `compact` した結果として **新しい配列** を作る
- さらに `handle_list` などでその配列を **再度コピー**して処理

変更後:

- `polymorphic_method` が `compact` で作った配列を、そのまま後続処理でも再利用し、不要なコピーを行わない。

これにより、`polymorphic_path([user, comment])` のようなケースで毎回発生していた余分な配列生成が減ります。

---

#### 2) シンボルから文字列への変換方法の変更

これまで:

- `Symbol#to_s` を使っており、**毎回新しい文字列**オブジェクトを生成していた。

変更後:

- `Symbol#name` を使用。これは **凍結された(frozen)文字列** を返すため、余計なアロケーションが発生しにくい。

`[:edit, user, comment]` のようにアクションやスコープをシンボルで渡すパターンで、文字列化コストが下がります。

---

#### 3) ルートヘルパー名の組み立て方法の最適化

これまで（イメージ）:

- ルート名のパーツを配列として組み立て
  ```ruby
  parts = ["edit", "user", "comment"]
  helper_name = parts.join("_") + "_path"
  ```
- `join` で一度文字列を作り、それに `_path` などをさらに連結していた。

変更後（イメージ）:

- 1つの文字列として直接組み立てる:
  ```ruby
  helper_name = "edit_user_comment_path"
  ```
あるいは同等の「一回のビルドで済む」形に近づけ、`Array#join` + 文字列結合という複数段階のアロケーションを減らしています。

---

#### 4) アクション付きヘルパーの処理経路を簡略化

対象例:

- `edit_polymorphic_path(post)`
- `new_polymorphic_path([user, comment])`
- その他 `edit_...`, `new_...` などアクションプレフィックス付きポリモーフィックヘルパー

これまで:

- `edit_polymorphic_path(post)` は内部的に
  - `polymorphic_path` に `action: :edit` を含んだ `options` ハッシュを渡す
  - `polymorphic_path` 側でその `:action` を取り出して別処理
  - その過程で `Hash` のコピー・マージ・削除が行われる
- 結果として、**アクション情報をハッシュ経由でぐるっと回す**ために不要なオブジェクトが増えていた。

変更後:

- 他にオプションがない場合:
  - アクション情報（`:edit`, `:new` など）を、直接ビルダーに渡すように変更。
  - 余計な `Hash` を作らずに済む。
- ただし以下の場合は従来通り `polymorphic_path` / `polymorphic_url` を通す:
  - 他のオプションがある
  - オプションハッシュが渡されている
  - polymorphic mapping を使っている

これにより、`edit_polymorphic_path(post)` というごく一般的なケースでのコストも削減されています。

---

### ビフォー / アフターのアロケーション数

アプリ側で `resources :posts` と `resources :users { resources :comments }` がある環境、ビューコンテキストからの呼び出し時:

| 呼び出し | main (変更前) | this branch (変更後) |
|---|---:|---:|
| `polymorphic_path([user, comment])` | 17 | 14 |
| `polymorphic_path([user, Comment])` | 16 | 13 |
| `polymorphic_path([:edit, post])` | 17 | 13 |
| `polymorphic_path([:edit, user, comment])` | 18 | 14 |
| `edit_polymorphic_path(post)` | 11 | 8 |
| `polymorphic_path(post)` / `user_comment_path(user, comment)` | 変化なし | 変化なし |

特に「ネストされたリソース + 配列」「アクション付き」のパターンで 3〜5 オブジェクト程度の削減が見られます。

---

3. 影響範囲・注意点  

- **出力結果は完全に互換**  
  - 生成されるURL、named route helper の名前ともに、変更前と同一です。
  - テスト (`polymorphic_routes_test.rb`) もその前提で通っています。

- **主な影響範囲**
  - Action Pack の `ActionDispatch::Routing::PolymorphicRoutes`
  - それを利用する Action View の URL/フォームヘルパー (`link_to`, `form_with`, `form_for` 等) が内部的に高速化されます。
  - 既存のアプリケーションコードやルーティング DSL の書き方は一切変更不要です。

- **パフォーマンス的なインパクト**
  - 単発呼び出しでは数オブジェクトの差ですが、ビュー内で多用される（特にネストされたリソースを大量に表示する）ケースでは GC 負荷の減少が期待できます。
  - `resources` を多用し、`form_with(model: [parent, child])` を頻出させているようなアプリほど恩恵が大きいです。

- **互換性上の懸念**
  - public API の挙動は変えていないため、通常の利用では互換性問題は起きにくいです。
  - もし `polymorphic_path` の内部実装に依存した monkey patch を書いている場合は、内部の配列/ハッシュの扱いが一部変わっている点に注意が必要です。

  - `actionpack/lib/action_dispatch/routing/polymorphic_routes.rb`
    - polymorphic ルーティングのコア実装で、主にここに最適化が入っている。
  - `actionview/test/activerecord/polymorphic_routes_test.rb`
    - 既存テストの強化またはカバレッジ確認用の追加が行われている（新しい振る舞いはない）。

  - `polymorphic_routes_test.rb` を含む Action View / Action Pack の両テストスイートが、warning を error 扱いにした状態でパスしていると明記されています。

## [#59464](https://github.com/rails/rails/pull/59464) Compute action_methods without stringifying every public instance method {#pr-59464}

**マージ日**: 2026/10/31 | **作成者**: [@igorwwwwwwwwwwwwwwwwwwww](https://github.com/igorwwwwwwwwwwwwwwwwwwww)

1. 概要 (1-2文で)  
コントローラの `action_methods` を計算する際に、全ての public インスタンスメソッドを一度 String 化してから Set に入れていた処理を見直し、Symbol のままルートヘルパー名を差し引くことで、大規模アプリ(例: GitLab)のブート時間とオブジェクトアロケーションを大幅に削減するパフォーマンス改善です。挙動は従来と同一になるように保ちつつ、内部実装とキャッシュ戦略を最適化しています。

---

2. 変更内容の詳細

### 背景 / 問題点

- `AbstractController::Base#action_methods` は、各コントローラごとの「アクションとして扱うメソッド名の Set」を計算します。
- 現状は:
  1. コントローラの「全ての public インスタンスメソッド」を列挙
  2. それらをすべて String に変換
  3. さらに `UrlFor` レイヤで「ルートヘルパーメソッド名の集合」を String として取り出し、それを差し引き
  4. 残ったものを Set として `action_methods` にする  
- 多くのコントローラで `url_helpers` を include しているため、public メソッドの大半が「ルートヘルパー」であり、それらを毎回 String 化しては Set 演算、という処理が非常に重くなっていました。
  - GitLab 例
    - コントローラ 684 個
    - 各コントローラの public インスタンスメソッド約 8800 個
      - うち約 8100 個がルートヘルパー (ルート数 3300 に由来)
    - `action_methods` 計算にだけ 5.4 秒 (全体ブート 33 秒のうち) 消費
    - 結果的な `action_methods` Set 自体はごく少数の「本当のアクションメソッド」しか含まないのに、そこに至るまでの計算コストが高かった。

### 変更のアイデア

- 「ルートヘルパー名を差し引く」ところまでは、Symbol のまま処理する。
- 最終的に「コントローラの action 名」として公開するタイミングでだけ String に変換して Set を作る。
- 併せて、「ルートヘルパー名のリスト (helper_names)」も、Symbol 版をメモ化して再利用する。

### 実装上の変更点

#### 1. `AbstractController::Base#action_methods` の分割

従来:

```ruby
def action_methods
  # (イメージ) public_instance_methods から String の Set を作る実装
  @action_methods ||= begin
    methods = public_instance_methods(true).map(&:to_s)
    Set.new(methods).freeze
  end
end
```

新しい構造 (概要):

```ruby
# Symbol のリストを返す内部用フック (nodoc)
def internal_action_methods # 仮名：実際には :nodoc: な名前
  # 戻り値は Symbol の配列/集合
end

def action_methods
  # internal_action_methods の結果を String に変換して
  # Frozen な Set として公開
  @action_methods ||= internal_action_methods
    .map!(&:to_s)
    .to_set
    .freeze
end
```

- 実際のメソッド名は PR では `:nodoc:` 付きフックとして定義されており、外部 API ではなく内部用です。
- ポイントは、「コントローラが持つ public メソッド一覧」から「実際のアクション候補の Symbol 集合」を返すフェーズと、それを String の Set に仕上げるフェーズを分離したことです。

#### 2. `UrlFor` 側のオーバーライド対象の変更

- これまでは `UrlFor` が `action_methods` を直接オーバーライドし、そこからルートヘルパーを差し引いていました。
- 今回、`UrlFor` は **Symbol リストを返す内部フック (上記 `internal_action_methods` 相当)** をオーバーライドするように変更。
  - すなわち:
    1. ベース実装で「コントローラの public インスタンスメソッド (Symbol 群)」を取得
    2. `UrlFor` で「Symbol のままルートヘルパー名の集合を差し引く」
    3. 残った Symbol 群だけが「アクション候補」として返る
  - その後、ベース側で String 化して Set 化するため、「公開される `action_methods` の API と結果」は変わりません。

#### 3. ルートヘルパー名 (helper_names) の Symbol 版メモ化

対象: `action_dispatch/routing/route_set.rb`

- これまで:
  - `helper_names` が呼ばれるたびに、新しい String の配列を生成して返していた。
  - つまり `action_methods` 計算ごとに、ヘルパー名 String 群を都度生成 → Set 演算 → GC 負荷大。
- 変更後:
  - ルートコレクション (RouteSet) に「Symbol のヘルパー名一覧」をメモ化して保持。
  - ルートが追加されたりコレクションがクリアされたときだけ、このメモをクリア。
  - 既存の `helper_names` メソッドのインターフェイスは変更しない (必要ならメモ化した Symbol 群を元に String を返すなどの内部実装に留まる)。

疑似コードイメージ:

```ruby
class ActionDispatch::Routing::RouteSet
  def helper_names
    # 従来 API はそのまま (String の配列を返す)
  end

  def helper_names_symbols
    @helper_names_symbols ||= begin
      # 全ルートからヘルパー名 Symbol を列挙してメモ化
    end
  end

  def clear!
    @helper_names_symbols = nil
    super
  end
end
```

#### 4. CHANGELOG

`actionpack/CHANGELOG.md` に、このパフォーマンス改善と互換性についての記述が追加されています。

### パフォーマンス効果 (PR 計測値)

- 合成アプリ (600 controllers / 3000 resources):
  - 旧実装:
    - 1.22 秒
    - 3.6M オブジェクトアロケーション
  - 新実装:
    - 0.41 秒
    - 12.6K オブジェクトアロケーション
- GitLab 本番ブート:
  - 全体ブート時間: 32.7 s → 28.7 s (約 4 秒短縮)
  - `action_methods` 計算コストが大きく削減

なお、GitLab 673 コントローラについて、旧実装と新実装で `action_methods` の Set を 1 つずつ比較し、「1つたりとも差分がない」ことを検証済みです。

---

3. 影響範囲・注意点

- 公開 API / 挙動:
  - `AbstractController::Base#action_methods` の返り値 (内容・型) は従来と同一を維持する方針です。
  - `UrlFor` を include しているコントローラの `action_methods` も結果は変わらない想定です。
  - `helper_names` もインターフェイスは変更なし。
- 影響がありうるケース:
  - Rails 内部の非公開フック (`:nodoc:` で追加された Symbol リスト返却フック) を、独自に monkey patch したり rely するようなコードがあると影響を受ける可能性があります。
  - `UrlFor` や `AbstractController::Base` に対して、`action_methods` 自体を再定義・上書きするようなメタプログラミングをしている場合は、内部構造の変更と競合しうるため、アップデート時に挙動を確認してください。
- 性能的な期待:
  - ルート数 × コントローラ数が多い大規模モノリスほど恩恵が大きいです。
  - 開発環境のブート時間や Spring のプリロード時間、CI の起動時間短縮などにも寄与します。
- 互換性:
  - CHANGELOG にもある通り、ユーザランドから見える範囲での互換性は保たれており、「パフォーマンス改善のみ」を意図した変更です。

4. 参考情報 (あれば)

  - `AbstractController::Base#action_methods`
  - `AbstractController::UrlFor`
  - `ActionDispatch::Routing::RouteSet`
- 類似の最適化パターンとして、「Symbol のまま集合演算し、最終出力フェーズでだけ String 化する」「ルート定義が変わらない限りヘルパー名をメモ化する」という設計は、大規模 Rails アプリで頻出するパフォーマンスチューニングの基本パターンと言えます。

## [#59468](https://github.com/rails/rails/pull/59468) Autoload Arel {#pr-59468}

**マージ日**: 2026/10/31 | **作成者**: [@linyiru](https://github.com/linyiru)

1. 概要 (1-2文で)  
Active Record が `require "arel"` していたのをやめて、`Arel` をオートロードに変更し、「実際に必要になったタイミングでのみ Arel を読み込む」ようにした PR です。これにより開発環境でのブート時間短縮と読み込まれるファイル・オブジェクト数の削減を狙っています。

---

2. 変更内容の詳細  

### 何をしているか

- これまで:
  - `active_record` を `require` した時点で `Arel` 一式（ノード・ビジター・コレクタなど、約80ファイル）を即座に読み込んでいた。
  - その結果、`bin/rails` 系コマンドがアプリケーションをロードするたびに Arel も毎回ロードされていた。

- この PR 以後:
  - Active Record 側から Arel を「即時 require」するのではなく、「`Arel` という定数が参照されたタイミングで自動的にロードされる」ようにした（オートロード化）。
  - 実際には `ActiveRecord::Base` がロードされる際に `Arel::Table.engine` のロードフックを通じて Arel が読み込まれるので、通常の Rails アプリでの利用パターンは変わらない。
  - つまり「Arel は引き続き Active Record 経由で普通に使えるが、Active Record を require した直後にはまだ読み込まれておらず、必要になったときに読み込まれる」構造になる。

### 挙動の互換性

- 説明中の例:
  ```ruby
  require "active_record"

  # これまでと同様に動く
  Arel::Table.new(name: "users")
  ```
  `active_record` だけを require した状態でも、`Arel::Table.new` が従来どおり動作することが保証されています。  
  背景として、`ActiveRecord::Base` ロード時の `Arel::Table.engine` 設定処理がフックになっており、そのタイミングで Arel がオートロードされます。

### テスト追加内容

`railties/test/application/loading_test.rb` にテストが追加されています。内容は概ね次の検証です:

1. 開発モードでアプリケーションをブートした直後は、`Arel` がまだオートロード対象として残っていること。
2. `ActiveRecord::Base` をロードすると、そのタイミングで Arel が実際にロードされ、
   - `Arel` 定数が解決可能になること
   - `Arel::Table.engine` が正しくセットされること

このテストは現行 main ブランチでは失敗し、この PR の変更によってパスするようになります。  
また、Arel 自身を含む Active Record のテストスイート（SQLite 使用、10,135 テスト）が通っていることが明記されています。

### パフォーマンス計測結果

- この PR 単体による影響（開発モード／`rails new` 直後のアプリ）:
  - Development boot, median: 620 ms → 604 ms（約 -16 ms）
  - 読み込まれるファイル数: 1461 → 1383（-78 ファイル程度）
  - オブジェクト数: 321,683 → 314,585（約 -7k）

シリーズ全体（他の PR: #59465〜#59469 すべて適用）では、トータルで 619 ms → 513 ms と大きめの効果があることが説明されていますが、この PR はその中で Arel 部分を担当する変更です。

---

3. 影響範囲・注意点  

### 影響範囲

- 主に影響するのは**開発環境でのブートシーケンス**です。
  - `bin/rails` 系コマンド（`server`, `console`, `runner`, `test` など）がアプリケーションをロードする際に、不要なプロセスでは Arel を読み込まなくなります。
- 本番環境（`config.eager_load = true`）では、**イager ロード時に結局 Arel 一式がロードされる**ため、**本番のブート挙動・性能は実質的に変わりません**。

### 既存コードへの影響

通常の Rails/Active Record 利用パターンではほぼ影響はありませんが、以下のような特殊なケースでは意識しておくとよいです:

1. **Active Record を require しているが、`ActiveRecord::Base` をロードしない構成**で、かつ Arel を直接使うコード:
   - 例: `require "active_record"` だけ行い、`ActiveRecord::Base` を一切触らずに `Arel::Table` などを直接使うカスタムコード。
   - この場合でも、この PR の説明によれば `Arel::Table.new(name: "users")` は従来通り動くよう考慮されていますが、「どのタイミングで Arel がロードされるか」を前提にした非常にトリッキーなコードを書いている場合は挙動が変わる可能性があります。
2. **`Arel` がオートロードかどうかに依存したメタプログラミング**をしている場合:
   - たとえば `ActiveSupport::Dependencies.autoload_paths` や `autoload?("Arel")` の結果に依存するようなコードなど。
   - Rails 内部実装寄りのケースなので、通常のアプリ開発ではまず問題になりません。

### デバッグ時の注意

- 開発環境で「起動直後に Arel 関連のコードがまだロードされていない」ことがあり得ます。  
  何か定数解決問題が起きた場合は、`ActiveRecord::Base` のロードタイミングと Arel のオートロードタイミングを意識すると切り分けがしやすくなります。

---

4. 参考情報 (あれば)  

- この PR は、開発ブート時間短縮シリーズの一部:
  - #59465: テストランナーをテスト時のみ読み込む
  - #59466: Action Mailbox の Mail 拡張を InboundEmail 利用時にのみ読み込む
  - #59467: Marcel を ActiveStorage::Blob 利用時にのみ読み込む
  - #59468: 本 PR（Arel をオートロード）
  - #59469: Action View のヘルパーを使用時にのみ読み込む
- これらはすべて「`rails/all` で一括 require していたコンポーネントを、必要になったときにロードするようにする」という方針で統一されており、開発体験（ブートの速さ・メモリ）を改善しつつ、本番の eager load には影響を与えない設計になっています。

## [#59465](https://github.com/rails/rails/pull/59465) Load the test runner only when testing {#pr-59465}

**マージ日**: 2026/10/31 | **作成者**: [@linyiru](https://github.com/linyiru)

1. 概要 (1-2文で)  
このPRは、Railsアプリのブート時に常に読み込まれていたテストランナー関連（特に Prism と Rake::FileList）を、「実際にテストを実行する時だけ」読み込むように変更するものです。これにより、開発環境でのアプリ起動や各種 `bin/rails` コマンドの起動時間が数十ミリ秒改善されます。

---

2. 変更内容の詳細  

### 何が問題だったか

従来は、`rails/all` を `require` するプロセス（開発サーバ、コンソール、`bin/rails` 各種コマンドなど）が **常にテストランナーを読み込んでいた** ため、以下が毎回ロードされていました:

- `rails/test_unit/runner`
- そこからさらに:
  - `rails/test_unit/test_parser`（Prism を使用）
  - `rake/file_list`

しかし、テストランナーは本来「テストを実行するときにだけ必要」なものであり、開発サーバやコンソールなどには不要です。この不要な読み込みが、開発時のブートを遅くしていました。

### 具体的な変更点

主な変更ファイルは 2 つです。

#### 1) `Rails::TestUnitRailtie` の読み込みタイミング調整

**変更ファイル**: `railties/lib/rails/test_unit/railtie.rb`

今までは `Rails::TestUnitRailtie` がロードされるタイミングで:

- `rails/test_unit/line_filtering`
- → それ経由で `rails/test_unit/runner`
- → さらに Prism / `rake/file_list`

…まで一気に読み込まれていました。

このPRでは、`line_filtering` の `require` を **`ActiveSupport::TestCase` が拡張される瞬間まで遅延** させています。

イメージとしては:

```ruby
# 以前: Railtie が読み込まれた時点で line_filtering を require していた
require "rails/test_unit/line_filtering"  # ※これが runner → Prism を引きずる

ActiveSupport.on_load(:test_case) do
  # line_filtering で定義される機能をここで使う
end

# 変更後: on_load ブロックの中で require する
ActiveSupport.on_load(:test_case) do
  require "rails/test_unit/line_filtering"  # ← 実際にテストケースがロードされる時だけ
  # ActiveSupport::TestCase に line_filtering 機能を混ぜ込む
end
```

これにより:

- テストが実際にロードされる（＝`ActiveSupport::TestCase` がロードされる）までは  
  `line_filtering` および `runner` / Prism / `rake/file_list` は読み込まれない
- `bin/rails test` や Rake のテストタスク、Minitest プラグインなどは、**自分で runner を require 済み** なので挙動は変わらない

という状態になります。

#### 2) 新しいテストの追加

**変更ファイル**: `railties/test/application/runner_test.rb`

`bin/rails runner` 実行時に「テストランナーが読み込まれていないこと」を確認するテストが追加されています。

ポイント:

- 開発・本番両方の環境に対して、
- `bin/rails runner` を起動し、
- そのプロセス内で `Rails::TestUnit::Runner` などがロードされていないことを検証

これにより、「アプリブート時にテストランナーを読み込まない」という今回の変更が、将来の改修で誤って元に戻されないようにテストで担保しています。

---

3. 影響範囲・注意点  

### 影響範囲

- 対象:
  - `rails/all` を読み込む全てのプロセス（開発サーバ、コンソール、`bin/rails runner` 等）
  - 特に「テストを実行していない」プロセスでの挙動が変わります（=テストランナーを読まなくなる）。
- 非対象:
  - テスト実行系 (`bin/rails test`, Rake の test タスク, Minitest プラグインなど)
    - これらは元々 runner を明示的に require しているので、挙動は変わりません。
  - 本番環境の eager load 時:
    - Action View 側で Prism を eager load するため、最終的に Prism は読み込まれます。
    - ただし「9ファイル & 3.2kオブジェクト」分程度の削減効果はある模様。

### パフォーマンスへの影響

新規アプリ (`rails new` デフォルト) を使った計測結果（Ruby 3.4.12 / Debian 13）:

- 開発環境でのブート時間（median）
  - main: 620 ms → このPR: 598 ms（約 22 ms 削減）
- ロードされるファイル数
  - 1461 → 1443（▲18）
- 割り当てオブジェクト数
  - 321,684 → 305,655（▲約 16k）

`bin/rails` コマンドでアプリを起動する場合も概ね同程度の削減があり、  
`bin/rails runner nil`（development）では 868 ms → 770 ms 程度の改善が報告されています（このPR単体以外の改善も含む全体測定）。

### 注意点 / 互換性

- 通常の使い方 (`bin/rails test`, `rails test`, Rake タスク経由のテスト実行) では挙動は変わりません。
- 「アプリケーションブート時に、テストランナーが必ずロードされている」ことに依存するようなコード（かなり特殊ケース）があると、今回の変更で壊れる可能性があります。
  - 例: `config/initializers` 内で `Rails::TestUnit::Runner` クラスを参照している、など
  - そういったケースでは、必要に応じて自前で `require "rails/test_unit/runner"` する必要があります。

---

4. 参考情報 (あれば)

- PRで挙げられている関連最適化 PR 群（いずれも「必要になったときだけロードする」方向の変更）:
  - #59465 本PR: Load the test runner only when testing（−22 ms）
  - #59466: Load Action Mailbox's Mail extensions with InboundEmail（−40 ms）
  - #59467: Load Marcel with ActiveStorage::Blob（−13 ms）

  - #59469: Load Action View's helpers when they're used（−13 ms）
- 上記5つを全部適用した場合の新規アプリ開発ブート:
  - 619 ms → 513 ms
  - ロードファイル −190
  - オブジェクト −54k

Rails の「起動時に全部読み込む」設計から、「必要になったタイミングでロードする」方向への細かなチューニングの一環として捉えられるPRです。

## [#59452](https://github.com/rails/rails/pull/59452) [8-1-stable] Require `useragent` when loading `ActionController::AllowBrowser` {#pr-59452}

**マージ日**: 2026/10/31 | **作成者**: [@k0kubun](https://github.com/k0kubun)

1. 概要 (1-2文で)  
Rails 8.1系において、`ActionController::AllowBrowser` が内部で使う `useragent` gem を「最初のリクエスト時」ではなく「コントローラ定義時（クラス評価時）」に読み込むようにしたバックポートです。挙動やAPIは変えずに、JITコンパイラへの悪影響を減らし、起動後の最初のリクエスト時のオーバーヘッドを避けるためのパフォーマンス改善です。

---

2. 変更内容の詳細  

### 何が変わったか

元の変更 (#57974) を 8-1-stable にそのまま cherry-pick したもので、実質 2 行差分の小さな修正です。

これまでの 8.1 では:

- `allow_browser` を使ったコントローラで
- リクエストが**初めて**来たタイミングの `before_action` の中で
- `require "useragent"` が呼ばれていた

という構造になっていました。

このPRでは:

- `allow_browser` の**クラスマクロを呼んだタイミング**で
- `require "useragent"` を実行するように変更しています。

擬似コードでいうと、イメージは以下のような変化です（実際のコードは2行変更のみですが、概念的な違いを示します）:

**変更前（イメージ）**

```ruby
class ApplicationController < ActionController::Base
  allow_browser versions: :modern

  before_action :check_browser

  private

  def check_browser
    require "useragent"  # ← 最初のリクエスト中にロードされる
    # UserAgent.parse(request.user_agent) ...
  end
end
```

**変更後（イメージ）**

```ruby
class ApplicationController < ActionController::Base
  # クラス定義が評価されるとき（= 起動時の eager_load 時）に require
  allow_browser versions: :modern  # ← ここで require "useragent"
end
```

実際の差分としては `actionpack/lib/action_controller/metal/allow_browser.rb` 内で:

- これまで `before_action` 内にあった `require "useragent"` を削除
- `allow_browser` クラスマクロの実行時に `require "useragent"` を行うように変更

という2行の置き換えに近い内容です。

### なぜそうするのか（動機）

- Rails 8.1 では、`allow_browser` を利用する最初のリクエスト中に `useragent` を `require` していたため、
  - すでに JIT コンパイラが「もう完成形」と見なしていたコードが、
  - ランタイム途中で新しい定数やメソッドの定義によりパッチポイントが無効化され、
  - ZJIT での再コンパイルが発生してしまう、という問題が確認されています（ruby/ruby#19617 の `shipit` ベンチマーク）。
- `config.eager_load = true` な本番環境では、「アプリケーション起動時」にクラス定義が評価されるので、
  - `allow_browser` クラスマクロ実行時に `require "useragent"` しておけば、
  - 起動時に gem が読み込まれ、JIT が安定した状態でリクエスト処理に入れるようになります。
- `useragent` はすでに `actionpack` のハード依存関係であり、
  - 遅かれ早かれ必ず読み込まれるものなので、
  - 「ちょっとだけ早め（クラス評価時）に require する」ことによる互換性問題は基本的に発生しません。

---

3. 影響範囲・注意点  

### 振る舞い面での影響

- 公開APIおよび表向きの挙動は**変わりません**。
  - `allow_browser` のオプションや判定ロジック、レスポンス内容などは従来通りです。
- 変わるのは「`useragent` がいつロードされるか」だけです。
  - 変更前: 該当コントローラへの**最初のリクエスト中**にロード
  - 変更後: コントローラで `allow_browser` を**宣言した時点**（= eager_load 環境では起動時）でロード

### パフォーマンス / JIT への影響

- 利点:
  - 本番環境（`config.eager_load = true`）では、アプリ起動後の最初のリクエスト時に `useragent` を読み込むオーバーヘッドがなくなります。
  - JIT (ZJIT) の観点では、最初のリクエスト途中で大きな `require` が走らないため、定数・メソッドの再解決や再コンパイルを減らせます。
- 影響範囲:
  - `allow_browser` を使っているコントローラが存在するアプリケーション。
  - それ以外のコントローラでは `allow_browser` を呼ばない限り `useragent` は読み込まれない点は従来通りです。

### 注意点・互換性

- `useragent` は `actionpack` のハード依存なので、通常の Rails プロジェクトでは特別な対応は不要です。
- もし非常に特殊な構成で、
  - Rails がブートする前 / gem が揃う前に `allow_browser` を評価するような独自ローダやコード生成をしている場合、
  - そこで `require "useragent"` が発生するタイミングが変わる可能性があります。
  - ただし、現実的にはほぼ想定されないケースです。
- テスト:
  - `actionpack/test/controller/allow_browser_test.rb` はこのブランチでも通過することが確認されています。
  - 実際に `allow_browser versions: :modern` を持つコントローラを定義すると、
    - 変更前: 最初のリクエスト時に `$LOADED_FEATURES` に `useragent` が追加
    - 変更後: コントローラ定義時点で `$LOADED_FEATURES` に追加
    が確認されています。

## [#59470](https://github.com/rails/rails/pull/59470) Don't add a trailing slash after a required format in optimized URL helpers {#pr-59470}

**マージ日**: 2026/10/31 | **作成者**: [@linyiru](https://github.com/linyiru)

1. 概要 (1-2文で)  
Rails の URL ヘルパー最適化で導入された挙動により、「必須フォーマット付きのルート + `trailing_slash: true`」のときに、拡張子の後ろに余計なスラッシュ (`/projects/1.json/`) が付いてしまう不具合を修正する PRです。一般ルート生成ロジックと同様に、フォーマットが必須セグメントの場合は末尾スラッシュを付けないよう、最適化ヘルパー側の条件分岐が調整されています。

---

2. 変更内容の詳細  

### 問題の背景

以下のようなルーティングを考えます:

```ruby
# config/routes.rb
get "/projects/:id.:format", as: :project
```

このとき、`trailing_slash: true` を指定して URL ヘルパーを呼ぶと:

```ruby
project_path(1, :json, trailing_slash: true)
# 現在(問題ありの挙動):
# => "/projects/1.json/"
# 期待される挙動(従来の一般パス生成と同じ):
# => "/projects/1.json"
```

`#59350` で追加された「最適化された URL ヘルパー」は、`trailing_slash` のように「パス構造を変えない」オプションについては、一般的なパス生成ロジックをバイパスして高速経路を通るようになっています。  
しかし、その最適化ルートでは「フォーマットがルートの必須パーツとして指定されている場合」を正しく考慮しておらず、`format:` オプション経由で指示されたフォーマットしか見ていませんでした。その結果:

- 位置引数でフォーマットが渡されている (`project_path(1, :json, ...)`)
- かつ ルート定義上 `:format` が必須セグメント (`:id.:format`) になっている

というケースで、本来は末尾スラッシュを付けるべきでないのに `"/"` を付与してしまう差異が、最適化ヘルパーと一般ヘルパーの間で生じていました。

### 今回の修正内容

`actionpack/lib/action_dispatch/routing/route_set.rb` の最適化 URL ヘルパー生成ロジックで、**フォーマットがルートの必須セグメントとして存在する場合**は `trailing_slash` を無視し、末尾スラッシュを追加しないように条件を変更しています。

擬似コード的には、以下のようなイメージです（実際のコードはもう少し低レベルですが、意味としてはこうなります）:

```ruby
# 変更前 (イメージ)
path = build_optimized_path(...)
path << "/" if options[:trailing_slash]

# 変更後 (イメージ)
path = build_optimized_path(...)

if options[:trailing_slash]
  # ルートに :format が必須セグメントとして含まれていない場合のみ付与
  unless route_has_required_format_segment?
    path << "/"
  end
end
```

つまり、「フォーマットが必須な一部のパターン (`:id.:format` など)」では、`trailing_slash: true` を指定しても `"/projects/1.json"` のままで、拡張子 `.json` の後に `/` が付かないようにしています。一般パス生成ロジックと挙動を揃える調整です。

### テスト追加

`actionpack/test/dispatch/routing_test.rb` にテストが追加されています。内容としては、以下のようなケースを網羅し、「最適化パス生成」と「一般パス生成」が同じ結果を返すことを確認しています。

- `project_path(1, :json, trailing_slash: true)`
- `project_path(1, :json, trailing_slash: true, anchor: 'frag')`
- `project_path(1, :json, trailing_slash: true, page: 2)`

テストでは「最適化ヘルパー経由」と「一般パス生成経由」の結果を比較しており、現状の main ブランチではこの比較が失敗するところを、この PR によって一致するように修正しています。

---

3. 影響範囲・注意点  

- 対象:
  - `:format` をルートの必須パーツに含めているルート（例: `get "/projects/:id.:format"`）
  - かつ、`*_path` / `*_url` ヘルパー呼び出しで `trailing_slash: true` を使っているケース
- 影響内容:
  - これまで (まだ未リリースの main のみ) `"/projects/1.json/"` のように「拡張子の後に `/` が付いていた」最適化ルートの挙動が、`"/projects/1.json"` に戻ります。
  - 一般的な URL 仕様としても、拡張子の直後に意味のないスラッシュが入るのは不自然であり、既存の安定版 Rails の挙動とも整合します。
- 後方互換性:
  - バグ修正であり、リリース済みバージョンにはまだ入っていない挙動を正すものなので、実運用中アプリへの互換性影響は基本的にありません。
  - もし main ベースで `"/projects/1.json/"` に依存するようなコードや外部サービス連携を組んでいた場合は、URL が `"/projects/1.json"` に変わる点に注意が必要ですが、そのような使い方は通常想定されません。

---

4. 参考情報 (あれば)  

- 関連 PR: [#59350](https://github.com/rails/rails/pull/59350) – URL ヘルパーの最適化で、`trailing_slash` などパス形状に影響しないオプションを最適化パスで扱うようにした変更。
- 影響コンポーネント:
  - `ActionDispatch::Routing::RouteSet`（ルーティングと URL ヘルパー生成）
  - Action Pack のルーティング／URL 生成周りのテストスイートは、warnings-as-errors でもパスしているとのこと。

## [#59474](https://github.com/rails/rails/pull/59474) Optimize URL helpers for routes with requirements {#pr-59474}

**マージ日**: 2026/10/31 | **作成者**: [@linyiru](https://github.com/linyiru)

1. 概要 (1-2文で)  
`constraints` などの「セグメントに対する正規表現制約」を持つルートでも、URLヘルパーの高速な最適化パス (`OptimizedUrlHelper`) を使えるようにしたパフォーマンス改善のPRです。制約違反時のエラー挙動や、オプション付き URL 生成の挙動は既存の一般パスと揃えたまま、オブジェクト生成数と実行時間を大きく削減しています。

---

2. 変更内容の詳細  

### 何が問題だったか

Rails のルーティングでは、以下のように `constraints` でセグメントを正規表現制約するのがよくあります:

```ruby
resources :posts, constraints: { id: /\d+/ }
get "/@:username/:id",
    to: "statuses#show",
    as: :short_account_status,
    constraints: { username: %r{[^@/.]+}, id: /\d+/ }
```

ところが、従来の `UrlHelper.optimize_helper?` は

```ruby
route.path.requirements.empty? # => true でないと最適化しない
```

という条件だったため、「制約付きルート」は常に一般的な URL 生成パス（遅い方）を通っていました。  
Mastodon の例では、パブリックタイムラインの 1 リクエスト内で 302 回のルートヘルパー呼び出しのうち 122 回がこの「制約付きルート」だった、という事例が示されています。

### この PR が行うこと

#### 1. 制約付きルートでも OptimizedUrlHelper を使う

`constraints` を持つルートに対しても、条件付きで `OptimizedUrlHelper` を使えるようにしました。  
ただし、その際に

- **必須セグメント**（`:id`, `:username` など）については  
  そのルートの `requirements` に定義された正規表現と突き合わせてチェックする
- **チェックに失敗した場合（未指定 / 不一致）** は  
  これまで通り一般パスにフォールバックし、同じエラーを投げる

という挙動を追加しています。

ここで使われる正規表現は、従来の一般パスと同じく「アンカー付き（\A … \z）」のもの（`requirements_for_missing_keys_check`）なので、挙動が従来と変わらないように注意されています。

疑似コード的にはイメージとして:

```ruby
def optimized_helper(...)
  if all_required_segments_match_requirements?(args)
    # 早いパス（OptimizedUrlHelper）
    build_url_fast(...)
  else
    # 従来の一般パスにフォールバック
    build_url_general(...)
  end
end
```

#### 2. オプションセグメントの扱い

- 一般パス側は、「フォーマット以外のオプションセグメント」は **現在のリクエストから値を埋める** 仕様があります。
- 一方、`OptimizedUrlHelper` は「リクエスト由来でオプションセグメントを埋める」ことはしません。

そのため、この PR では次のポリシーが取られています:

- **フォーマット (`.:format`) 以外のオプションセグメントを持つルート** は  
  引き続き **最適化しない（一般パスのまま）**
- 例:  

  ```ruby
  scope "(:locale)", locale: /en|es/ do
    resources :posts
  end
  ```
  
  ここでは `(:locale)` がオプションセグメント & 制約付きなので、**このルートは最適化対象外**。  
  テスト `TestOptionalScopesWithOrWithoutParams` でそのケースをカバーしています。

逆に言うと、

- 制約付きだけど
- 「フォーマット以外のオプションセグメントを持たないルート」

に限って `OptimizedUrlHelper` が適用されます。

#### 3. パフォーマンス改善の具体的な数字

Ruby 3.4 での 1 コールあたりのオブジェクト数と時間:

| 呼び出し例 | オブジェクト数 (before → after) | 時間 (before → after) |
|-----------|-----------------------------------|------------------------|
| `post_path(1)` | 25 → 10 | 5.97 → 2.18 µs |
| `post_url(1, host: "example.com")` | 28 → 13 | 7.15 → 3.40 µs |
| `short_account_status_url("alice", 1, host: "example.com")` | 28 → 13 | 8.36 → 4.02 µs |

1 回あたり数 µs・十数オブジェクトの差ですが、タイムライン表示など URL ヘルパーの多用箇所ではトータルで効く改善になります。

#### 4. テスト追加内容

新しいテストでは、「最適化パス」と「一般パス」が

- 同じ URL を生成するか
- 同じエラーメッセージを投げるか

を多様な引数パターンで比較しています。カバーしている引数:

- 制約に **マッチする値**
- **マッチしない値**
- `nil`
- 空文字
- 末尾に改行を含む値
- `to_param` を実装したオブジェクト

さらに、それぞれについて:

- オプション無し
- `format` オプション
- `anchor`（フラグメント）オプション
- クエリパラメータ付き
- `host` オプション付き

を組み合わせてテストし、挙動が完全に一致することを検証しています。  
また、制約付きかつオプションセグメントを持つルート（`(:locale)` など）で、「リクエストからオプションが埋まる」従来挙動も維持されていることを確認しています。

著者は

- 「制約チェックを外す」とテストが落ちる
- 「オプションセグメントを持つルートも最適化する」とテストが落ちる

ことも確認済みと明記しています。

---

3. 影響範囲・注意点  

- 対象:
  - `resources ... constraints: {...}` のような **制約付きルートの URL ヘルパー** 全般
  - とくに、ID や username に対する正規表現制約を多用するアプリ（Mastodon など）では効果が大きい
- 互換性:
  - 正規表現の適用方法は従来と同じ（アンカー付き）で、  
    「引数が制約に合わないときに発生するエラー」は、メッセージ含めて以前と同じになるよう調整されています。
  - `(:locale)` など **フォーマット以外のオプションセグメントを持つルートは最適化しない** ので、  
    その種のルートの挙動は完全に従来通りです。
- アプリ側の対応:
  - 通常は何も変更不要で、そのままパフォーマンス向上の恩恵を受けられます。
  - もし以前から URL 生成時の例外メッセージに依存したコードがあっても、  
    テストで「一般パスと同じメッセージ」であることが保証されています。
  - 自作のルーティング拡張（エッジなメタプロ / monkey patch）をしている場合は、  
    `UrlHelper.optimize_helper?` 周りの挙動変化の影響がないかは一応確認した方が安全です。

---

4. 参考情報 (あれば)  

- 変更ファイル:
  - `actionpack/lib/action_dispatch/routing/route_set.rb`  
    - `UrlHelper` / `OptimizedUrlHelper` と、どのルートを最適化対象にするかのロジックが変更
  - `actionpack/test/dispatch/routing_test.rb`  
    - 制約付きルート + 最適化ヘルパーの比較テストが多数追加
- ベンチマークコード（PR 記載）:

  ```ruby
  Routes = ActionDispatch::Routing::RouteSet.new
  Routes.draw do
    resources :posts, only: :show, constraints: { id: /\d+/ }
    get "/@:username/:id", to: "statuses#show",
                           as: :short_account_status,
                           constraints: { username: %r{[^@/.]+}, id: /\d+/ }
  end
  H = Routes.url_helpers
  # objects: GC.stat(:total_allocated_objects) over 1,000 calls
  # time: best of 5 runs of 100,000 calls
  ```

この PR により、「制約付きだが素直な（オプションがない）ルート」の URL ヘルパーは自動的に高速化され、  
特に大量に URL ヘルパーを叩くアクションで GC 負荷とレスポンス時間の削減が期待できます。

## [#59472](https://github.com/rails/rails/pull/59472) Read the user agent's version and browser once in allow_browser {#pr-59472}

**マージ日**: 2026/10/31 | **作成者**: [@linyiru](https://github.com/linyiru)

1. 概要 (1-2文で)  
`allow_browser` が内部で利用する `BrowserBlocker` において、UserAgent から「ブラウザ名」と「バージョン」を何度も再計算していた処理を一度だけにまとめることで、各リクエストあたりのオブジェクト生成数と処理時間を削減するパフォーマンス改善です。Rails が新規生成したアプリのデフォルト設定（`allow_browser versions: :modern`）で、UA パースのオーバーヘッドを軽減します。

---

2. 変更内容の詳細  

### 背景となる問題

- Rails の新規アプリケーションでは、生成される `ApplicationController` にデフォルトで以下のようなコードが入る想定です:

  ```ruby
  class ApplicationController < ActionController::Base
    allow_browser versions: :modern
  end
  ```

- `allow_browser` はリクエストごとに UserAgent をパースしてブラウザやバージョンを判定しますが、その内部で使われる `UserAgent` オブジェクトが、
  - `version` を読むたびにバージョン解析をやり直す  
  - `browser` を読むたびにブラウザ判定をやり直す  
 という実装になっており、`BrowserBlocker` 側でも
  - version を 2 回
  - browser を 3 回  
  読み出していました。

- その結果、1 回の `allow_browser` チェックで `Webkit#application` が 27 回呼ばれるなど、不要なスキャンが大量に走っていました。

### この PR の変更点（ロジック面）

`BrowserBlocker` 内で、UserAgent からブラウザ名とバージョンを「一度だけ」取得し、それをローカル変数にキャッシュしてから後続の判定に使うように変更しています。

概念的には、以下のようなイメージです（擬似コード）:

**変更前（イメージ）**

```ruby
def blocked?(user_agent)
  # それぞれ内部で UA の products をスキャンする
  if user_agent.browser == "Safari"
    # ...
  end

  if user_agent.version < required_version
    # ...
  end

  # 別の条件でも再び user_agent.browser / .version を使う
  if user_agent.browser == "Safari" && user_agent.version < another_version
    # ...
  end
end
```

**変更後（イメージ）**

```ruby
def blocked?(user_agent)
  browser = user_agent.browser  # 一度だけ計算
  version = user_agent.version  # 一度だけ計算

  if browser == "Safari"
    # ...
  end

  if version < required_version
    # ...
  end
```

## [#59478](https://github.com/rails/rails/pull/59478) ActiveSupport::Duration: precompute float versions of constants {#pr-59478}

**マージ日**: 2026/10/31 | **作成者**: [@byroot](https://github.com/byroot)

1. 概要 (1-2文で)  
ActiveSupport::Duration が内部で使っている時間定数（1分=60秒、1時間=3600秒、1日=86400秒など）について、「float 版」をあらかじめ計算しておくことで、`to_f` 呼び出しを減らし、Duration 周りの浮動小数演算を高速化するパフォーマンス改善の PR です。元 PR #59266 の修正として入り、同等の計算結果を保ったまま割り算や `fdiv` のコストを下げています。

---

2. 変更内容の詳細  

### 何をしたか

- `ActiveSupport::Duration` 内部で使っている時間関連の整数定数に対して、対応する `Float` 版の定数を追加し、それを使うように変更しています。
  - 例：  
    - これまで: `SECONDS_PER_DAY = 86_400` を使い、必要に応じて `SECONDS_PER_DAY.to_f` を呼んでいた  
    - 変更後: `SECONDS_PER_DAY_F = 86_400.0` のような float 定数を定義し、最初から float 同士の演算を行う

- その結果、`Duration#in_hours`, `Duration#in_days`, `Duration#parts` 内部などで行われる
  - `n / SOME_INT.to_f`
  - `n.fdiv(SOME_INT)`
  
  のようなパターンが、
  - `n / SOME_FLOAT`
  - `n.fdiv(SOME_FLOAT)`  

  に置き換わる（あるいは Ruby がより最適化しやすい形になる）ように調整されています。

### なぜそれで速くなるのか

PR 内のベンチマークは「整数定数を都度 `to_f` する場合」と「最初から float 定数を使う場合」を比較しています。

ベンチマークコードの本質は次の通りです:

```ruby
n = 100000
d = 86400      # Integer
f = 86400.0    # Float

n/d.to_f   # パターン1: Integer 割り算 + to_f
n/f        # パターン2: Float との割り算
n.to_f/f   # パターン3: 先に n を to_f
n.fdiv(d)  # パターン4: Integer.fdiv(Integer)
n.fdiv(f)  # パターン5: Integer.fdiv(Float)
```

計測結果から分かること:

- 4.1-dev / 4.0 系いずれの Ruby でも、`/to_f`（整数で割ってから `to_f`）より、最初から float を使う `/f`, `fdiv(f)` の方が **1.1〜1.3倍程度高速**
- Ruby 4.0.7 では `fdiv(Integer)` が特に遅く、`fdiv(Float)` が最速
- Ruby 4.1-dev では `fdiv(Integer)` もだいぶ速くなっているが、それでも「都度 `to_f`」より「最初から float」の方が一貫して速い

→ つまり、「定数側をあらかじめ float にしておき、演算時に `to_f` を呼ばないようにする」ことで、Duration 内部の計算コストを削減できる、というのがこの PR の狙いです。

---

3. 影響範囲・注意点  

### 影響範囲

- 影響を受けるのは、ActiveSupport::Duration が内部で秒換算などを行う箇所です。
  - 例:
    - `5.minutes.to_f`, `1.hour.to_f`, `1.day.to_f`
    - `2.days / 3` のような計算で内部的に行われる秒換算
    - `duration.in_hours`, `duration.in_days` などの内部実装
- API の挙動（戻り値の型や見た目）は変わらない想定です。
  - 元々 float を返していたところは引き続き float を返し、計算結果の「人間が見て分かるレベル」の値も変わらないように設計されています。

### 注意点（浮動小数の誤差について）

- この PR は「整数 → float への変換タイミング」を変えているだけで、整数演算を float 演算に置き換えるような大胆な変更ではありませんが、
  - 既存でも float を使っていた箇所について、「to_f の場所」が変わるため、strict equality (`==` でのビットレベル同一期待) をしているような *極端に厳しいテスト* がある場合は、誤差によりごく小さな差が出る可能性があります。
- 通常の Rails アプリで、`Duration#to_f` や `in_hours` などの結果をそのまま UI 表示やおおまかな計算に使っている範囲では問題にならないはずです。

### パフォーマンス的なインパクト

- 変更は activesupport の 1 ファイル・十数行レベルの軽微なもので、互換性を崩さず局所的に高速化しています。
- Duration の計算が非常に頻繁に走るようなアプリケーション（大量の時間計算・スケジューリング・ログ集計など）では、微小ですが GC や CPU 使用率の観点でプラスに働く可能性があります。

- 元 issue / PR  
  - 本 PR が修正している元 PR: https://github.com/rails/rails/pull/59266  
- Ruby の数値演算最適化の文脈  
  - Ruby 3.2 以降、`fdiv` や除算の最適化、YJIT による数値演算高速化が進んでおり、「整数 to float 変換の回数を減らしておく」ことはベンチマークでも度々言及されています。

## [#59294](https://github.com/rails/rails/pull/59294) Forward arguments from HashWithIndifferentAccess#merge to update {#pr-59294}

**マージ日**: 2026/10/31 | **作成者**: [@sampokuokkanen](https://github.com/sampokuokkanen)

1. 概要 (1-2文で)  
`ActiveSupport::HashWithIndifferentAccess#merge` が、可変長引数の受け渡し方法を従来の「配列にまとめてから splat」でなく、Ruby 3.4 以降で効率的に動作する「`...` による引数転送」に書き換えられました。これにより一部 Ruby バージョンで割り当て（allocation）削減とわずかな性能改善が見込まれます。

---

2. 変更内容の詳細  

### 何を変えたか

対象：`activesupport/lib/active_support/hash_with_indifferent_access.rb`

`HashWithIndifferentAccess#merge` メソッド内で `update` を呼び出す部分の引数の渡し方のみが変更されています。

もともとの典型的なイメージは次のような形です（擬似コード）:

```ruby
def merge(*args, &block)
  dup.update(*args, &block)
end
```

これを「引数転送演算子 `...`」を用いた形に変更しています:

```ruby
def merge(...)
  dup.update(...)
end
```

※ 実際のコードは多少文脈が異なるかもしれませんが、変更の本質はこの「`*args` + `*args` での再スプラット」から「`...` でそのまま転送」にする点です。

### なぜ変えたか

従来の実装では:

1. `merge` が `*args` で引数を一度配列にまとめる  
2. `update(*args)` で再度それをスプラットし  
3. `update` 側の `*rest` で再び配列として受け取る

という二重の配列生成が発生していました。

Ruby 3.4 以降では `def foo(...); bar(...); end` のような「`...` による引数転送」は、呼び出し元の引数配列を再生成せずに渡せるよう最適化されているため、余分な配列割り当てを避けられます。  
Ruby 3.3 では挙動・オーバーヘッドはほぼ変わりませんが、コードとしても意図が明確になります。

### ベンチマーク結果（PR 説明より）

`hwia.merge(hash)` に対する 50,000 回 × 15 バッチの計測:

- Ruby 3.3.5  
  - allocations: 4 → 4（変化なし）  
  - 947ns → 929ns（わずかに速い）
- Ruby 3.4.0-preview 以降相当（4.0.7, 4.1-dev 等）  
  - allocations: 4 → 3（1つ減少）  
  - 時間も数 % 程度の改善

YJIT では現状 `send_forwarding` のフォールバックが多発するため、`merge` 呼び出しごとのフォワーディングが最適化されておらず、約 3% 程度遅くなるケースが観測されています。一方、インタプリタと ZJIT では僅かながら高速化が見られます。

---

3. 影響範囲・注意点  

### 挙動の互換性

- 公開 API（`HashWithIndifferentAccess#merge` の振る舞い）は変更されていません。
  - 受け取れる引数の種類・個数
  - ブロックの扱い
  - 戻り値
  いずれもこれまでと同じです。
- そのため、通常のアプリケーションコードから見たときの互換性リスクは極めて低いです。

### パフォーマンス面

- Ruby 3.4 以降:
  - `HashWithIndifferentAccess#merge` に対するアロケーションが 1 つ減る想定。
  - 大量に `merge` を呼び出す処理（例：パラメータのマージを繰り返す API 層など）では、微小ながら GC プレッシャーの削減・処理時間の改善が期待できます。
- Ruby 3.3 系:
  - アロケーション数は変わらず、性能差もごく小さい（計測上は誤差レベルの改善）。
- YJIT 利用時:
  - 現状の YJIT は `...` のフォワーディングコールをコンパイルしていないため、`HashWithIndifferentAccess#merge` に対して統計上は `send_forwarding` のフォールバックカウントが増えます。
  - 説明では 3% 程度の遅さが観測されていますが、これは非常にマイクロなベンチマーク環境での数字であり、実アプリケーションでは他の要因に埋もれる可能性が高いです。
  - 将来の Ruby / YJIT 側の最適化で改善される見込みがあります。

### その他の注意点

- 変更ファイルは 1 ファイル・4 行（+2/-2）のみであり、テストスイート（Active Support）は通過済みです。
- バグフィックスや表向きの挙動変更ではないため、CHANGELOG の更新は行われていません。

4. 参考情報 (あれば)  

- PR 本体: https://github.com/rails/rails/pull/59294  
- 関連トピック:
  - Ruby の引数転送 (`def method(...); other(...); end`) に関する最適化は Ruby 3.4 以降で導入・強化中。
  - 同作者による類似の最適化 PR（特に `#59293`）も、`HashWithIndifferentAccess` 周辺や Active Support の内部での引数転送パターンの最適化を目的としていると考えられます。

## [#59320](https://github.com/rails/rails/pull/59320) Ignore blank forwarded hosts during request host extraction {#pr-59320}

**マージ日**: 2026/10/31 | **作成者**: [@svyatov](https://github.com/svyatov)

1. 概要 (1-2文で)  
Rails の `ActionDispatch::Request#host` が `X-Forwarded-Host: ,` のような「空のフォワードホスト」ヘッダで `NoMethodError` を起こしていた不具合を修正し、空の値は無視して `HTTP_HOST` などの従来ロジックにフォールバックするようにした PR です。これにより、HostAuthorization を含むリクエスト処理が壊れにくくなり、非標準的・壊れたプロキシヘッダにもより強くなります。

---

2. 変更内容の詳細  

### 問題の背景

現在の（PR 適用前の）`ActionDispatch::Request#raw_host_with_port` は概ね以下のような動きをしていました（PR 説明の「OriginalRequest」と同等）:

```ruby
def raw_host_with_port
  @raw_host_with_port ||= if forwarded = x_forwarded_host.presence
    forwarded.split(/,\s?/).last
  else
    get_header("HTTP_HOST") || "#{server_name}:#{get_header('SERVER_PORT')}"
  end
end
```

ここで問題となるケース:

- リクエストヘッダ: `X-Forwarded-Host: ,`
  - `x_forwarded_host` は空文字列扱いになる（header は存在するが中身が「`,`だけ」など）
  - `presence` の扱い・split の結果として「最終的に空文字 or 何も無い」状態になりうる
  - その結果 `raw_host_with_port` が `nil` を返し、最終的に `Request#host` の中で `NoMethodError` (`nil` に対してメソッド呼び出し) が発生  
  - 同様に HostAuthorization ミドルウェアも、許可されたホストを記録する際に例外を起こすことがある

HTTP 的には壊れた・非標準的なヘッダですが、Rails としては「異常系ヘッダでアプリケーションが 500 エラーになる」のを避けたい、というのがこの PR のモチベーションです。

### 今回の修正内容

PR では「パース後に空になってしまった `X-Forwarded-Host` を無視し、`HTTP_HOST` などにフォールバックする」というチェックを追加しています。

おおまかな挙動は以下のようになります（擬似コードレベルの説明）:

```ruby
def raw_host_with_port
  @raw_host_with_port ||= begin
    forwarded = x_forwarded_host.presence
    if forwarded
      parsed = forwarded.split(/,\s?/).last
      if parsed.present? # ← 新たに「パース後も空かどうか」を確認
        parsed
      else
        # パース結果が空なら Forwarded Host を無視し、HTTP_HOST などへフォールバック
        get_header("HTTP_HOST") || "#{server_name}:#{get_header('SERVER_PORT')}"
      end
    else
      # そもそも X-Forwarded-Host が無い or 完全に空の場合は従来どおり
      get_header("HTTP_HOST") || "#{server_name}:#{get_header('SERVER_PORT')}"
    end
  end
end
```

PR 説明中の具体例:

```text
X-Forwarded-Host: ,
Before: raw_host_with_port => nil; host raises NoMethodError
After:  raw_host_with_port => original Host; host and port parse normally
```

つまり、

- `X-Forwarded-Host` がカンマだけ、空白だけ、最後のエントリが空、などのケースでは
  - 「Forwarded Host としては無効」とみなし、
  - `HTTP_HOST`（または `SERVER_NAME:SERVER_PORT`）にフォールバック
- 有効な値が入っている通常ケース（`example.com`, `example.com:3000`, `first, second:3000` など）では、これまで通り `X-Forwarded-Host` が優先される

### テストの追加

以下のファイルにテストが追加されています。

- `actionpack/test/dispatch/request_test.rb`
  - カンマだけの `X-Forwarded-Host`
  - 空白だけのリスト
  - 最終エントリが空のリスト
  - ホスト名とポートのパース
  などをカバー

- `actionpack/test/dispatch/host_authorization_test.rb`
  - HostAuthorization ミドルウェアに対して:
    - 空／カンマだけの `X-Forwarded-Host` でも許可ホストなら問題なく通過する
    - 禁止ホストなら従来どおりブロックされる
  といったケースを確認

いずれも「元々の host 認可ロジックは変えないが、空の Forwarded Host のせいで例外だけ出る」という状況を防ぐための回帰テストです。

---

3. 影響範囲・注意点  

### 影響範囲

- 対象:
  - `ActionDispatch::Request#host` / `#raw_host_with_port`
  - `X-Forwarded-Host` を見るあらゆるミドルウェア・アプリケーションコード
    - 例: `ActionDispatch::HostAuthorization`
- 具体的な影響:
  - 空（あるいはカンマだけ・空白だけなど）の `X-Forwarded-Host` ヘッダが来たときに
    - 以前: `NoMethodError` で 500 エラーになる可能性
    - 以後: ヘッダを無視し、`HTTP_HOST` などのオリジナルホストにフォールバック
- Forwarded Host が「正しく設定されている」環境の挙動は変わりません。

### 既存アプリへの影響・互換性上の注意

- 多くの正しいリバースプロキシ設定では:
  - もともと `X-Forwarded-Host` は空ではないため、この変更による挙動差はありません。
- 一部の壊れた／怪しいプロキシが
  - `X-Forwarded-Host: ,` のようなヘッダを送っていた場合:
    - これまでは「Forwarded Host を優先しつつ、結果として例外・500 になっていた」可能性
    - 今後は「Forwarded Host を無視し、オリジナルの `HTTP_HOST` に基づく挙動」になります
- もしアプリ側で独自に `request.env["HTTP_X_FORWARDED_HOST"]` をパースしている場合は、この PR の変更は直接は関係ありません。ただし、
  - Rails の `request.host` とアプリ独自ロジックで Forwarded Host の解釈が食い違う可能性があるため、Forwarded 系ヘッダを扱うコードはこの挙動に合わせて整理しておくとよいです。

### セキュリティ的な観点

- この PR は「許可／禁止判定を変える」のではなく
  - 「Forwarded Host が壊れていても例外で落ちないようにする」ための堅牢性向上が主眼です。
- HostAuthorization のロジック自体（どのホストを許可とみなすか）は変更されておらず、
  - 修正後も、Forwarded Host に有効な値が入っていれば従来どおりそれが優先されます。
- 逆に言うと、「空または空白だけの `X-Forwarded-Host` でホスト偽装を狙う」といった攻撃ベクトルは
  - この修正により「エラーにはならないが、偽装にもならずオリジナルホストになる」という挙動になります。

4. 参考情報 (あれば)

## [#59374](https://github.com/rails/rails/pull/59374) Write Duration#iso8601 values as plain decimal numbers {#pr-59374}

**マージ日**: 2026/10/31 | **作成者**: [@wleeaf](https://github.com/wleeaf)

1. 概要 (1-2文で)  
ActiveSupport::Duration#iso8601 が、常に ISO 8601 準拠かつ ActiveSupport::Duration.parse で再パース可能なフォーマットになるように修正した PR です。浮動小数点数や Rational を含む duration でも、指数表記や分数表記ではなく「通常の 10 進小数」で出力されるようになります。

---

2. 変更内容の詳細  

### 問題点

従来の `ActiveSupport::Duration#iso8601` は内部パーツをそのまま `to_s` していたため、以下のような問題がありました。

- Float は `Float#to_s` により指数表記になることがある  
  - 0.0001 未満の値、非常に大きな値など
- Rational は `Rational#to_s` により「分数」として出力される

結果として、ISO 8601 として不正な文字列が生成され、`ActiveSupport::Duration.parse` で読めないケースがありました。

```ruby
0.00005.seconds.iso8601      # "PT5.0e-05S"   # ISO 8601 的には不正
1e16.seconds.iso8601         # "PT1.0e+16S"
Rational(3, 2).days.iso8601  # "P3/2D"

ActiveSupport::Duration.parse("PT5.0e-05S")
# => ActiveSupport::Duration::ISO8601Parser::ParsingError
```

このような値は実際に発生し得ます:

- 非常に短い経過時間測定: `(t1 - t0).seconds` がマイクロ秒オーダー
- `DateTime - DateTime` が `Rational` 日数で返るケース

### 対応内容

`ISO8601Serializer` 内に `format_number` ヘルパーを導入し、duration の各構成要素の数値出力を一元化しました。

ポイント:

- **Float の扱い**  
  - `BigDecimal(float.to_s).to_s("F")` で「指数表記を使わない 10 進小数」に変換
  - 桁は `Float#to_s` と同じ精度を維持しつつ、表記だけをプレーン小数にする

- **Rational の扱い**  
  - 一旦 Float に変換してから上記の Float 経路で出力
  - ISO 8601 の「P3/2D」のような分数表記を廃止し「P1.5D」のような小数表記に統一

- **Integer / BigDecimal / precision オプション経路**  
  - これらは従来どおりの扱いを維持し、今回の変更は Float / Rational に限定

#### 修正後の挙動例

```ruby
0.00005.seconds.iso8601      # => "PT0.00005S"           # 指数表記ではなく小数
1e16.seconds.iso8601         # => "PT10000000000000000.0S"
Rational(3, 2).days.iso8601  # => "P1.5D"
```

従来エラーになっていたものも、ISO 8601 的に妥当な形式になり、パースできるようになります。

### テストの追加・変更

`activesupport/test/core_ext/duration_test.rb` の `test_iso8601_output` にテストケースを追加・強化:

- 追加ケース
  - 秒単位の小さな Float (`0.00005.seconds`)
  - 時間単位の小さな Float
  - Rational 日数 (`Rational(3, 2).days`)
  - 時間 + Rational 秒 (混在ケース)
- 各 `iso8601` 出力が `ActiveSupport::Duration.parse` でパースでき、元の duration と **等価であること** を確認するようにテストを拡張

これらのテストは本 PR の変更なしでは失敗し、変更後は通ることが確認済みです。

また、テストスイート全体をある程度走らせた結果、`main` と同じ既知の失敗のみで、新規の失敗は増えていないことが報告されています (主にタイムゾーン関係のテスト)。

### CHANGELOG

`activesupport/CHANGELOG.md` に今回の仕様変更が追記されています。  
(バグ修正だが挙動が変わるため、利用者向けに通知されるべき変更として扱われている)

---

3. 影響範囲・注意点  

- **ISO 8601 文字列のフォーマットが変わる**  
  - 以前: `"PT5.0e-05S"`, `"P3/2D"` などが出ることがあった  
  - 以後: `"PT0.00005S"`, `"P1.5D"` などプレーンな 10 進小数に統一
- **`ActiveSupport::Duration.parse` との往復互換性が向上**  
  - `Duration#iso8601` → `Duration.parse` のラウンドトリップでエラーになっていたケースが解消される
- **過去の出力に依存したコードへの影響**  
  - 文字列フォーマット (指数表記 / 分数表記) に強く依存したパース・比較ロジックがある場合は影響を受ける可能性があります。
    - 例: `"P3/2D"` を前提として自前パーサを書いている、指数表記を期待している等
  - ただし、ISO 8601 準拠の一般的なパーサ (数値部が 10 進小数であることを想定しているもの) にはむしろ互換性が高まる変更です。
- **数値の丸め・精度に関する注意**  
  - Rational は Float を経由するため、理論上は Float 変換に伴う丸めの影響を受けます。
  - とはいえ、もともと `DateTime - DateTime` が Rational になる程度の文脈であり、かつ元々 ISO 8601 として不正な分数表記だったため、実務上は「妥当な仕様変更」と考えられます。
  - Float 部分は `Float#to_s` 相当の精度なので、以前と比較して「値そのものの精度」が落ちる変更ではなく、「表記の仕方」だけを変えています。

---

4. 参考情報 (あれば)  

- 関連 Issue / PR
  - #42344, #42348: 大きな整数に対する ISO 8601 出力の修正 (今回の変更はその残りのケース対応)
- 影響する主なユースケース
  - 計測時間など短時間の duration を ISO 8601 でログ・API 返却するアプリ
  - `DateTime` 差分を ISO 8601 で表現・保存し、後で `Duration.parse` で復元したいワークフロー
- 実装の要点
  - `ISO8601Serializer` に `format_number` を導入し、Float/Rational → BigDecimal → "F" 形式の文字列、というパスで一貫した 10 進小数表記を実現している点がコアの変更です。

## [#59375](https://github.com/rails/rails/pull/59375) Set Vary to Sec-Fetch-Site directly when it is empty {#pr-59375}

**マージ日**: 2026/10/31 | **作成者**: [@sampokuokkanen](https://github.com/sampokuokkanen)

1. 概要 (1-2文で)  
`ActionController::Base` の CSRF 対策用 `after_action` が `Vary` ヘッダに `Sec-Fetch-Site` を追加する処理について、`Vary` が空のケースでは文字列操作を行わず、直接 `"Sec-Fetch-Site"` をセットするようにしてオブジェクト生成と処理時間を削減するパフォーマンス改善のPRです。既に `Vary` が存在する場合の挙動は変えず、空の場合のみ最適化しています。

---

2. 変更内容の詳細  

### 背景

- Rails の CSRF 対策 (`ActionController::RequestForgeryProtection`) では、ブラウザから送られる `Sec-Fetch-Site` ヘッダに基づく保護を行うため、`after_action` で全レスポンスに `Vary: Sec-Fetch-Site` を付与しています。
- これまでの実装は、「現在の `Vary` を取得 → `split(',')` → `strip` → `uniq` → `"Sec-Fetch-Site"` を足して `join(', ')`」という形で、たとえ `Vary` がまったく設定されていない(空文字/`nil`)場合でも同じ処理を通していました。
- 多くのレスポンスではそもそも `Vary` が設定されていないため、「`Sec-Fetch-Site` だけを付けたいだけなのに、毎回複数の文字列や配列を生成している」という無駄なアロケーションが発生していました。

### 何を変えたか

- `append_sec_fetch_site_to_vary_header`（名称はPR説明より推定）内で、**レスポンスに `Vary` がまだ存在しない／空である場合は、直接 `response.headers["Vary"] = "Sec-Fetch-Site"` と代入**するように変更。
- `Vary` が既に存在する場合は、従来通り
  - カンマ区切りで分割
  - 空要素除去・空白除去
  - `Sec-Fetch-Site` を重複しないように追加
  - 再びカンマ区切り文字列として結合
  という既存ロジックを使い続けます。

コードイメージ（あくまで説明用の擬似コード）:

```ruby
def append_sec_fetch_site_to_vary_header
  vary = response.headers["Vary"]

  if vary.blank?
    # ここが今回の最適化
    response.headers["Vary"] = "Sec-Fetch-Site"
  else
    # 従来通りの安全なマージ処理
    values = vary.split(",").map { _1.strip }.reject(&:empty?)
    values << "Sec-Fetch-Site" unless values.include?("Sec-Fetch-Site")
    response.headers["Vary"] = values.join(", ")
  end
end
```

`ActionController::Rendering` が `"Accept"` ヘッダに対して行っている最適化と同様のパターンを、`Sec-Fetch-Site` に対して適用した形です。

### 計測結果

- 単一ファイル構成の production アプリ (Ruby 4.0.7, 全レスポンスで `Vary` が未設定) での 1 リクエストあたりのオブジェクトアロケーション削減:
  - `GET /posts.json`: 1073.1 → 1067.1
  - HTML show: 677.2 → 671.4
  - HTML index (20件): 2360.0 → 2353.3

- `append_sec_fetch_site_to_vary_header` 単体ベンチ (Ruby 4.1.0dev, 200,000回×15バッチ×before/after 交互で測定):
  - `Vary` がない場合:
    - interpreter: 928ns (7 objects) → 587ns (1 object)
    - YJIT: 581ns → 256ns
    - ZJIT: 635ns → 314ns
  - `Vary: Accept` がある場合は、ほぼ同等で僅差。新旧どちらが速いかはケースにより分かれるが誤差レベル。

---

3. 影響範囲・注意点  

- **機能面の変更は実質ゼロ**  
  - `Vary` が空: 以前も結果は `"Sec-Fetch-Site"` だけだったため、最終的なレスポンスヘッダは同じ。
  - `Vary` が存在する: 既存コードパスを通るため動作は変わらない。
  - そのため、アプリ側から見た挙動変更・互換性問題は基本的にありません。

- **パフォーマンスへの影響**  
  - `ActionController::Base` を継承する全コントローラに対し、CSRF 保護が有効なアクションでは毎回呼ばれるため、トラフィックの多いアプリ／API ほど恩恵があります。
  - 特に `Vary` を明示的に使っていないアプリでは、ほぼすべてのレスポンスでこの最適化が効きます。

- **テスト状況**  
  - Action Pack のテストスイート（システムテストを除く）がパスしているとのこと。
  - PR時点ではこの変更専用の追加テストは書かれておらず、「外部挙動は変えていない」という前提で既存テストに頼っている状態です。

- **将来の拡張時の注意**  
  - 今後、`Vary` を操作する別のミドルウェア／フィルタを追加する場合も、このロジックは「`Vary` が空ならセット、そうでなければマージ」という形なので、挙動として自然です。
  - ただし、もしアプリ側で `Vary` を `nil` や空文字に明示的に書き換えるようなコードがある場合、その後にこのフィルタが走ると `Sec-Fetch-Site` だけが再セットされる、という点は頭に入れておくとよいです（これは以前から同様の結果になっていたはずです）。

---

4. 参考情報 (あれば)  

- 類似実装: `ActionController::Rendering` が `Vary: Accept` をセットする際の最適化パターンを踏襲。
- ベンチマーク結果から、特に `Vary` が未設定である典型ケースにおいて、オブジェクトアロケーション数・処理時間ともに目に見えて改善していることが示されています。
- CSRF 保護と `Sec-Fetch-Site` ヘッダの関係については、Rails ガイドの「セキュリティ」「クロスサイトリクエストフォージェリ (CSRF)」の章や、ブラウザ Fetch Metadata (`Sec-Fetch-*` ヘッダ群) のドキュメントを参照すると背景理解が深まります。

## [#59373](https://github.com/rails/rails/pull/59373) Don't build an asynchronous queries session until it's needed {#pr-59373}

**マージ日**: 2026/10/31 | **作成者**: [@sampokuokkanen](https://github.com/sampokuokkanen)

1. 概要 (1-2文で)  
Active Record の非同期クエリ用セッション（AsynchronousQueriesTracker）が、リクエストやジョブごとに必ずフル構築されていたのを「実際に非同期クエリが使われたときにだけ本体を構築する」ように遅延初期化した PR です。これにより、非同期クエリを使わない大多数のケースでオブジェクト生成コストと実行時間が削減されます。

---

2. 変更内容の詳細  

### 背景

- Active Record の executor hook（リクエスト／ジョブ実行前後で呼ばれる部分）が、毎回 `AsynchronousQueriesTracker` のセッションを開始していました。
- セッション開始時に `Concurrent::AtomicBoolean` や `Concurrent::ReadWriteLock` など、合計 21 個のオブジェクト（うち 6 個の mutex, 3 個の condition variable）が生成されます。
- しかし、これを実際に利用するのは `load_async` などの「非同期クエリ API」を使った場合のみで、ほとんどのリクエスト・ジョブでは作ってすぐ破棄されていました。

### 変更の要点

- `start_session` で「実体のセッション」ではなく「プレースホルダー」を push するように変更。
- 実際のセッション（非同期クエリを追跡するためのオブジェクト群）は、`current_session` が最初に呼ばれたタイミングで初めて構築（遅延初期化）されます。
- 一度もセッション本体が構築されなかった場合（つまり非同期クエリが 1 回も呼ばれなかった場合）は、`finalize_session` では単にスタックからプレースホルダーを pop するだけで終了します。
- セッションはスタック構造を維持しており、ネストした executor 実行や再入可能な実行（re-entrant runs）も従来通り動きます。
- `start_session` は依然としてスタック（あるいはそのハンドル）を返すため、`TestFixtures` が「セッションが始まっていること」を示すフラグとして利用する挙動もそのままです。

コード自体の差分は `asynchronous_queries_tracker.rb` における 4 行追加 / 3 行削除のみと非常に小さく、実装としては「セッションオブジェクトの生成をラップし、最初のアクセス時まで遅らせる」程度の変更と考えられます。

---

3. 影響範囲・注意点  

### パフォーマンスへの影響

作者提供のベンチマークから:

- 1ファイルの production アプリ (Ruby 4.0.7) での 1 リクエストあたりのオブジェクトアロケーション数:
  - `ActionController::API` JSON show: 357 → 337
  - HTML index (20 records): 2360 → 2339
  - PATCH update + redirect: 823 → 803  
  → 非同期クエリを使わない典型的なリクエストでも 20 個前後のアロケーション削減が確認されています。

- `AsynchronousQueriesTracker.run` + `complete` を 1 executor サイクルとして計測 (Ruby 4.1.0dev):
  - interpreter: 3704 ns → 347 ns
  - YJIT: 2118 ns → 182 ns
  - ZJIT: 2064 ns → 171 ns  
  → 非同期クエリセッションまわりのオーバーヘッドが 10x 以上削減されており、executor hook 周辺のコストがかなり下がっています。

### 機能面の影響

- 非同期クエリ API (`load_async` 等) の挙動自体は変わらない想定です。  
  - 非同期クエリを使った場合は、初回アクセス時にセッションが作られ、以後は従来通りキャンセル／待機が行われます。
- 非同期クエリを 1 度も使わなかった executor 実行では、セッション実体が作られないため、`finalize_session` は空のプレースホルダーを pop するだけになりますが、
  - 「キャンセルすべきクエリも待つべきクエリもない」状態なので、意味的にも問題はありません。

### 既存コードへの注意点

通常の Rails アプリ開発者目線では、以下の通り互換性リスクはほぼありません。

- `AsynchronousQueriesTracker` の内部実装に依存しているようなメタプログラミング／モンキーパッチをしていない限り、アプリケーションコード側の修正は不要です。
- 非同期クエリセッションが「executor 開始時にすぐ構築されている」ことを前提にしているテストやライブラリがある場合は、挙動が変わる可能性がありますが、そのような依存はかなりレアケースと思われます。
- Active Record の SQLite / PostgreSQL スイートは通過しているため、主要 DB + 非同期クエリの基本的な挙動は担保されています。

---

4. 参考情報 (あれば)  

- 対象ファイル: `activerecord/lib/active_record/asynchronous_queries_tracker.rb`
- 変更規模: 1ファイルのみ、+4 / -3 と小さな差分だが、executor hook 経由で全リクエスト・ジョブに影響するため、ランタイムコスト改善効果は相対的に大きい変更。  
- この PR は CHANGELOG 更新なし（挙動は互換を保ったパフォーマンス改善扱い）。

## [#59376](https://github.com/rails/rails/pull/59376) Don't parse an empty query string {#pr-59376}

**マージ日**: 2026/10/31 | **作成者**: [@sampokuokkanen](https://github.com/sampokuokkanen)

1. 概要 (1-2文で)  
`Request#GET` がクエリ文字列を持たないリクエストでも毎回クエリ解析処理を走らせていたのをやめ、クエリ文字列が `nil` または空文字のときは即座に空の params ハッシュを返すようにして、無駄なオブジェクト生成と処理時間を削減した PR です。機能的な挙動はほぼ変えず、パフォーマンスとメモリ効率を改善する目的の変更です。

---

2. 変更内容の詳細  

### 何が問題だったか

- Rails の `ActionDispatch::Request#GET` は、HTTP リクエストのクエリパラメータを `ParamBuilder.from_query_string(query_string)` を通じて毎回構築しています。
- しかし、クエリ文字列が
  - そもそも存在しない (`nil`)
  - 空文字 (`""`)
  の場合でも、
  - `QueryParser.each_pair` 用の Enumerator を生成し
  - 空文字列の `split`
  などを行った後、結局「空の Hash」を返すだけ、という無駄な処理が走っていました。

### 今回の変更点

- `actionpack/lib/action_dispatch/http/param_builder.rb` に、クエリ文字列が空のケースに対するショートサーキットを追加しています（+2行のみの変更）。
- 処理イメージとしては次のような形です（実際のコードとは若干擬似コードですが、意図としてはこんな感じです）:

```ruby
module ActionDispatch
  class Http::ParamBuilder
    def self.from_query_string(query_string)
      # ここが今回のポイント
      return HashWithIndifferentAccess.new if query_string.nil? || query_string.empty?

      # 従来通りのパース処理
      params = HashWithIndifferentAccess.new
      QueryParser.each_pair(query_string) do |key, value|
        # ... パラメータの構築 ...
      end
      params
    end
  end
end
```

- つまり、「空のクエリ文字列であれば、パーサ周りには一切触れずに、その場で新しい `HashWithIndifferentAccess` を返す」ようにしています。
- 返しているオブジェクトはこれまでと同じく
  - 新しいインスタンス
  - `HashWithIndifferentAccess`
  - ミュータブル（後から `params[:foo] = "bar"` などが可能）
 であり、既存コードの利用パターンと互換性があります。

### ベンチマーク結果

- 単一ファイル構成の production 環境アプリ（Ruby 4.0.7）での 1リクエストあたりアロケーション:

  | request                     | before | after  |
  |----------------------------|--------|--------|
  | `ActionController::API` JSON show | 357    | 354    |
  | `GET /posts.json`          | 1073.1 | 1070.1 |

  数値差は小さいですが、「クエリなしの大量アクセス」がある場合、積み上がりで効いてくるタイプの最適化です。

- `ParamBuilder.from_query_string` 単体のベンチ（Ruby 4.1.0dev）:

  - クエリが空文字 `""` の場合は、Interpreter/YJIT/ZJIT いずれも「常に after が速い」(10/10 ラウンド)。

## [#59380](https://github.com/rails/rails/pull/59380) Read libvips' orientation field in the Vips image analyzer {#pr-59380}

**マージ日**: 2026/10/31 | **作成者**: [@g-pavlik](https://github.com/g-pavlik)

1. 概要 (1-2文で)  
Active Storage の Vips 画像アナライザが画像の回転情報を誤認識する不具合（特に TIFF など EXIF 以外で orientation が保存される場合）を修正し、libvips の `orientation` フィールドを一貫して参照するようにした PR です。これにより、アナライザと変換（variant）パイプラインの挙動が揃い、回転メタデータの解釈が正しくなります。

### 問題点

従来の Vips 画像アナライザ (`ActiveStorage::Analyzer::ImageAnalyzer::Vips`) は、画像の回転情報を以下のように取得していました:

- `exif-ifd0-Orientation` という「人間可読ラベル」ベースの EXIF フィールドを参照  
- libvips が EXIF メタデータとして回転情報を持っている場合はこれで動くが、TIFF など「ネイティブなタグ」に orientation が保存されているケースでは、このフィールドに値が入らない／ずれた値になる

このため、

- あるいは逆に、想定と異なる判定結果になる

- 以前: `exif-ifd0-Orientation`  
- 以後: libvips が提供する汎用の `orientation` フィールド  

を使うようにしています。  
Active Storage の「variant パイプライン」（画像変換処理側）ではすでに `orientation` フィールドを利用していたため、今回の修正で

- アナライザ（メタ情報分析）
- 変換（variant 生成）

の両方が同じ `orientation` を見に行くように統一された形です。

#### 変更ファイルのポイント

1. `activestorage/lib/active_storage/analyzer/image_analyzer/vips.rb`  
   - `metadata` の取得時に orientation を読むキーを `exif-ifd0-Orientation` から `orientation` に変更。  
   - 実装イメージとしては、例えば以下のようなイメージの差分と考えられます（実際のコードは若干異なる可能性あり）:

   ```ruby
   # 旧実装（イメージ）
   def rotation
     metadata["exif-ifd0-Orientation"]
   end

   # 新実装（イメージ）
   def rotation
     metadata["orientation"]
   end
   ```

   これにより、EXIF に限らず libvips が認識している orientation 情報を一貫して利用します。

2. `activestorage/test/analyzer/image_analyzer/vips_test.rb`  
   - 新しい挙動（libvips の `orientation` を読む）のためのテストケースを追加。

3. `activestorage/CHANGELOG.md`  
   - Active Storage の変更点として「Vips image analyzer が libvips の `orientation` フィールドを読むようになった」旨を追記。  
   - バグ修正としてリリースノートに載る形の変更です。

---

3. 影響範囲・注意点  

- 主な影響対象:
  - Active Storage で `image_processing: vips` を利用し、`ActiveStorage::Analyzer::ImageAnalyzer::Vips` を使っているアプリケーション
  - 特に、TIFF や EXIF 以外のメタデータ領域に orientation を持つ画像を扱うケース

- 挙動の変化:
  - 以前は `exif-ifd0-Orientation` のみを見ていたため「回転なし」と判定されていた画像が、今回の変更後は「回転あり」と正しく検出されるようになります。
  - これに伴い、Active Storage の解析結果として得られるメタ情報（例: `image.metadata[:rotation]` 相当の値）や、その結果を前提とした UI / 処理ロジックが、過去と異なる結果を返す可能性があります。

  - バグ修正としての変更であり、画像ファイルそのものを書き換えるような処理はありません。
  - 「正しい orientation 情報を得られるようになる」方向の変更なので、仕様としては自然であり、多くのアプリにとっては改善になる想定です。

## [#59383](https://github.com/rails/rails/pull/59383) ActiveStorage: Fix JSON::ParserError from ffprobe duplicate keys {#pr-59383}

**マージ日**: 2026/10/31 | **作成者**: [@jdelStrother](https://github.com/jdelStrother)

1. 概要 (1-2文で)  
ActiveStorage が ffprobe の JSON 出力に重複キーが含まれる場合に `JSON::ParserError` を起こしていた問題を、JSON パース時に重複キーを許可することで修正した PRです。あわせて、JSON gem の最低バージョン引き上げと、ffprobe に依存するテストまわりの調整が行われています。

---

2. 変更内容の詳細  

### 2-1. ffprobe 出力の重複キーによる JSON::ParserError の回避

問題の発端は、`ffprobe -show_format -show_streams -print_format json` などの出力に、以下のように同じキー（ここでは `date`）が複数回出てくるケースがあることです:

```json
"tags": {
  "date": "2026-10-26T12:11:28-03:00",
  "encoder": "Adobe Premiere Pro 2026.0 (Windows)",
  "encoded_by": "Adobe Premiere Pro 2026.0 (Windo",
  "date": "2026-10-26",
  "creation_time": "12:12:02",
  "time_reference": "0"
}
```

JSON 自体の仕様上は重複キーは未定義扱いですが、  
- JSON gem 2.x までは黙って最後のキーで上書きされる挙動  
- JSON gem 3.0+ ではデフォルトで重複キーがエラー (`JSON::ParserError`) になる挙動  

という差異があり、Rails で使用している JSON gem を 3.0+ にすると、ActiveStorage 内で ffprobe の JSON を解析している箇所（`ActiveStorage::Analyzer::AudioAnalyzer` など）で例外が出るようになります。

この PR では、ActiveStorage 側の ffprobe 結果のパースで `allow_duplicate_key: true` を明示的に渡すようにして、重複キーを許容するように変更しています。

変更イメージ（実際のコードに準じた擬似コード）:

```ruby
# 変更前（概念的に）
metadata = JSON.parse(stdout)

# 変更後
metadata = JSON.parse(stdout, allow_duplicate_key: true)
```

これにより、

- JSON gem 3.0+ でも ffprobe の出力がパースエラーにならない
- 重複キーはこれまで通り「後勝ち」で上書きされる（JSON gem の挙動に依存）

という挙動になります。

対象は少なくとも以下（diff から）:
- `activestorage/lib/active_storage/analyzer/audio_analyzer.rb`
- `activestorage/lib/active_storage/analyzer/video_analyzer.rb`  
※VideoAnalyzer も同様の形で ffprobe 出力を JSON.parse しており、そちらも合わせて `allow_duplicate_key: true` が指定されています。

---

### 2-2. JSON gem の最低バージョンの引き上げ

`allow_duplicate_key:` オプションは JSON 2.3 以降でサポートされているため、Gemfile の JSON 依存を更新しています。

- Gemfile: `json` のバージョン制約を `2.0+` から `2.3+` に引き上げ  
- Gemfile.lock: それに対応する lock ファイルの更新（+1/-1）

これにより、Rails 自体として「JSON 2.3 未満では動作保証しない」形になります。

ffprobe 周りのテストがいくつか調整されています。

#### 2-3-1. ffprobe 非存在時のテスト挙動統一

## [#59401](https://github.com/rails/rails/pull/59401) Reuse frozen PostgreSQL bind placeholders: 64 objects instead of 164 and up to 1.24x faster for an IN of 50 ids {#pr-59401}

**マージ日**: 2026/10/31 | **作成者**: [@czj](https://github.com/czj)

1. 概要 (1-2文で)  
PostgreSQL の Arel visitor がバインドパラメータ用の文字列（`"$1"`, `"$2"` …）を毎回新規生成していたのをやめ、最大 256 個分をあらかじめ凍結したテーブルから再利用するようにした PR です。これによりオブジェクト生成数が大きく減り、特に `IN` 句で多数の ID を渡すクエリのコンパイル性能が最大 1.24 倍ほど向上します。

2. 変更内容の詳細  

### 何をしているか

- PostgreSQL visitor が SQL を生成する際、バインドパラメータを `$1`, `$2`, ... のような placeholder 文字列で表現します。
- これまで:
  - 各クエリの各バインドごとに `"#{n}"` や `"$#{n}"` に相当する文字列を都度生成していました。
  - 特に `$10` 以降は「`"$"` の文字列」と「`"10"` の文字列」のように複数オブジェクトが関わるため、`IN` 句に大量の ID を渡すとオブジェクト数が膨らむ構造でした。
  - 例: `where(id: 50 ids)` で 164 個ものオブジェクトがコンパイル時に生成される。

- この PR の変更:
  - `BIND_BLOCK`（PostgreSQL visitor がプレースホルダ文字列を組み立てる部分）を変更し、**最初の 256 個分のプレースホルダ `$1`〜`$256` を「凍結された短い文字列のテーブル」から返す**ようにした。
    - 256個の frozen String を配列などに事前構築 (約 10KB)。
    - visitor 側は、番号が 1〜256 の場合はテーブルから取り出すだけ、257 以上は従来通りその場で文字列を生成。
  - このテーブルは freeze 済みかつ単純な配列なので **Ractor 共有可能**。
  - `TWO_DIGITS` in `ActiveSupport::TimeZone` で使っている「2 桁の文字列キャッシュ」と同じパターンの最適化。
  - `arel/visitors` がどの visitor を使う場合でもロードされるため、**PostgreSQL を使わないアプリでも起動時にこのテーブルは一度作られる**。

実際のコード変更範囲は小さく、`postgresql.rb` 内の `BIND_BLOCK` 実装が以下のようなイメージに変わっています（擬似コード）:

```ruby
# 変更前 (イメージ)
BIND_BLOCK = ->(collector, col) do
  i = collector.add_bind(col)
  collector << "$#{i}"  # "$1", "$2" をその場で生成
end

# 変更後 (イメージ)
POSTGRES_BIND_PLACEHOLDERS = Array.new(256) { |i| "$#{i + 1}".freeze }.freeze

BIND_BLOCK = ->(collector, col) do
  i = collector.add_bind(col)

  if i <= 256
    collector << POSTGRES_BIND_PLACEHOLDERS[i - 1]
  else
    collector << "$#{i}"  # 257 以降は従来通り生成
  end
end
```

### テスト

- 新規テストで **300個のバインド** をコンパイルし、テーブル範囲（1〜256）とそれを超える範囲（257 以降）両方をカバー。
- 重要なのは「生成された SQL が正しいか」であり、プレースホルダ再利用による**オブジェクト数の変化はアサートしていない**（main でも同じ SQL が生成されることを保証）。
- そのため挙動（外部から見える SQL）は完全に後方互換です。

### パフォーマンス・メモリの変化

PR 説明中のベンチ結果（`to_sql_and_binds` で DB に行かない純粋なコンパイル性能）:

- 3つの bind:

  | ケース | 1回あたりのオブジェクト数 | no JIT | YJIT |
  |-------|----------------------------|--------|------|
  | main  | 12                         | 143.8k i/s | 411.0k i/s |
  | PR後 | 8                          | 147.0k i/s (1.02x) | 473.7k i/s (1.15x) |

- `IN` 句で 50 ids:

  | ケース | オブジェクト数 | no JIT | YJIT |
  |-------|----------------|--------|------|
  | main  | 164            | 38.1k i/s | 71.7k i/s |
  | PR後 | 64             | 41.6k i/s (1.09x) | 88.8k i/s (1.24x) |

- `IN` 句で 500 ids:

  | ケース | オブジェクト数 | no JIT | YJIT |
  |-------|----------------|--------|------|
  | main  | 1,514          | 4,742 i/s | 8,702 i/s |
  | PR後 | 1,004          | 5,110 i/s (1.08x) | 9,806 i/s (1.13x) |

傾向として:

- bind の数が少ないクエリでもオブジェクト生成は微減し、YJIT では 10〜15% 近い向上。
- bind が多い `IN` 句（配列 where）では、**オブジェクト数が約 40〜60% 減**、実行回数も 1.1〜1.25x 程度向上。

さらに著者は「256 ではなく 1024 要素のテーブルにした場合」も試していて:

- テーブルサイズ: 約 40KB（256 の場合は約 10KB）
- `IN 500 ids` の場合:
  - オブジェクト数: 514（256テーブル時は 1,004）
  - 性能: no JIT 1.13x, YJIT 1.26x とさらに改善
- ただし 3 binds・50 binds といった現実的に多いケースは 256 テーブルと変わらない。

このため、「256 と 1024 のどちらが良いか？」をレビューに問いかけています。

---

3. 影響範囲・注意点  

**影響範囲:**

- 対象:
  - ActiveRecord + PostgreSQL を使う全アプリケーションの **SQL 生成 (Arel visitor)** に影響。
  - 特に `where(id: array)` のように **大量の bind を使うクエリを頻発するアプリ**（多くの ID をまとめて検索するパターン）で効果が出やすい。
- 直接的な仕様変更はなし:
  - 生成される SQL のプレースホルダ形式 (`$1`, `$2`, ...) は従来通りで、**見た目も順序も同じ**。
  - bind 数が 256 を超えるケースでも、257 以降は従来通りの生成方法にフォールバックするだけで、SQL の互換性は保たれる。
- メモリ:
  - Rails 起動時に約 10KB の frozen String テーブルを 1つ確保（PostgreSQL を使っていなくても）。
  - テーブル自体は Ractor 共有可・再利用されるためランタイムの増加はごく小さく、頻繁にクエリを発行するアプリではトレードオフとして十分割に合うと考えられる。

**注意点・互換性:**

- 挙動上の互換性:
  - 主に内部実装の改善であり、アプリ側から見える仕様の変更はありません。
  - 文字列オブジェクトの ID が変わったことに依存しているようなコード（普通は書かない）でない限り、破壊的な影響はないはずです。
- YJIT / JIT との関係:
  - ベンチは Ruby 4.0.9 + macOS arm64 環境で計測されており、YJIT 有効時に特に改善幅が大きい。
  - 実際の本番環境（Ruby バージョンや GC 設定、JIT 有無）によって改善幅は異なる可能性がありますが、**悪化するケースは考えにくい**種類の最適化です。
- 他 DB アダプタ:
  - 今回は PostgreSQL visitor 専用の最適化。SQLite/MySQL 用 visitor には影響しません。
  - ただしテーブル構築コードは `arel/visitors` ロード時に走るため、PostgreSQL を使わないアプリでも僅かな起動時メモリ増加（〜10KB）は発生します。

## [#59418](https://github.com/rails/rails/pull/59418) Accept Symbol values for the routing format: option {#pr-59418}

**マージ日**: 2026/10/31 | **作成者**: [@cestercian](https://github.com/cestercian)

1. 概要 (1-2文で)  
このPRは、ルーティングの `format:` オプションに `Symbol`（例: `format: :json`）を渡した場合でも、`String`（`"json"`）と同様に正しく扱われるようにするバグ修正です。Rails 3.2 では動いていた挙動が Rails 4.0 で静かに壊れていた回帰を解消しています。

---

2. 変更内容の詳細  

### 何が問題だったか

以下のようなルーティング定義をしても:

```ruby
get "/users", to: "users#index", format: :json
```

意図としては:

- このルートのデフォルト `format` が `"json"` になる
- `/users` にアクセスすると `params[:format]` が `"json"` になる
- `/users.xml` はこのルートにマッチしない

ことを期待しますが、現状（PR前）は次のような挙動でした:

- フォーマットの「制約」も「デフォルト」も設定されない
- `/users.xml` もマッチしてしまう
- `recognize_path("/users")[:format]` は `nil`

一方、`format: "json"`（文字列）と書いた場合は、期待通りに:

```ruby
get "/users", to: "users#index", format: "json"
# => デフォルト format が "json"
# => /users.xml は 404（このルートにはマッチしない）
```

となっていました。

この差は、内部で `format` を正規化する `ActionDispatch::Routing::Mapper::Mapping#normalize_format` が、`true` / `Regexp` / `String` のみを扱い、`Symbol` を素通りさせていたために起きていました。

Rails 3.2 では `format: :json` も正しく扱われていましたが、Rails 4.0 の変更（`String === format` チェック導入）で回帰が入り、以後ずっと直っていなかった、という位置づけです。

### 具体的な修正内容

`ActionDispatch::Routing::Mapper::Mapping#normalize_format` で、`Symbol` を `String` と同等に扱うように変更しています。

ポイント:

- `format` が `Symbol` の場合、`to_s` して `"json"` のような文字列に変換
- その文字列に対して、従来通り:
  - requirement 用の正規表現を `Regexp.compile("json")` で生成
  - デフォルト値として `"json"` を設定
- これにより、`params[:format]` は他のデフォルト同様 `String` のまま（`:json` にはならない）

コードイメージとしては:

```ruby
def normalize_format(format)
  case format
  when true
    # ...（従来通り）
  when Regexp
    # ...（従来通り）
  when String, Symbol
    value = format.to_s
    [Regexp.compile(value), value]
  else
    # 何もしない
  end
end
```

（実際のコードは多少異なる可能性がありますが、概念としてはこういう変更です。）

この修正は `get` だけでなく、`scope` や `resources` も共通の `normalize_format` を通るため、一括で改善されます。

#### サンプル: `get` ルート

```ruby
# PR後（Symbol でも OK）
get "/users", to: "users#index", format: :json

# 以下と等価な挙動になる
get "/users", to: "users#index", format: "json"
```

- `/users`  
  - マッチする
  - `params[:format] #=> "json"`
- `/users.xml`  
  - マッチしない（別ルートがあればそちら、なければ 404）

#### サンプル: `scope` と `resources`

```ruby
scope format: :json do
  resources :users
end

# もしくは
resources :users, format: :json
```

- `GET /users`  
  - `params[:format] #=> "json"`
- `GET /users.xml`  
  - このスコープ / resources のルートにはマッチしない

### テストとCHANGELOG

- 既存の format-option 関連テストを拡張する形で回帰テストが追加されています
  - `format: :json` を指定した場合に、`format: "json"` と同じ requirement / default になること
  - `recognize_path("/users")[:format] == "json"` になること
  - `/users.xml` がマッチしないこと
  - `scope` や `resources` 経由の場合も同様であること
- `actionpack/CHANGELOG.md` にこの挙動修正が記載され、外部向けに明示されています

---

3. 影響範囲・注意点  

- 影響範囲:
  - ルーティングで `format: :json` のように `Symbol` を使っている（または今後使う）場合にのみ影響します
  - これまで `format: :json` が「効いていなかった」アプリでは、PR適用後に**挙動が変わります**
    - 今まで `/users.xml` が通っていたルートが、通らなくなる可能性があります
- 既存アプリでの注意点:
  - 回避のために既に `format: "json"` と書いている場合は、挙動は変わりません（現状維持）
  - 逆に、「`format: :json` が効いていない前提で、わざと `/users.xml` も通していた」ようなコードがある場合は、修正後にルーティングが変わるので確認が必要です
- 型について:
  - `params[:format]` は常に `String` です（`:json` ではなく `"json"`）。これまで `format: "json"` で得られていた挙動を壊さないように配慮されています。

---

4. 参考情報 (あれば)  

- 対応 Issue: #59412（`format: :json` が効かないことに関する報告）
- 回帰元コミット: Rails 4.0 頃に入った `format` 判定の `String === format` 変更  
- 類似オプションとの一貫性:
  - `constraints: { format: :json }`
  - `controller: :users`
  - `action: :index`
  - `via: :get`  
 これらが元々 `Symbol` を受け付けていたのに対し、`format:` だけが受け付けない状態だったのを解消し、API の一貫性を取り戻す変更です。

## [#59477](https://github.com/rails/rails/pull/59477) Check if `::UserAgent` is defined before requiring {#pr-59477}

**マージ日**: 2026/10/31 | **作成者**: [@byroot](https://github.com/byroot)

1. 概要 (1-2文で)  
このPRは、`ActionController::Metal::AllowBrowser` が `::UserAgent` クラスを `require` する前に、その定義有無をチェックするように変更し、不要な `require` 呼び出しを避けてパフォーマンスを改善するものです。`require` が `$LOADED_FEATURES` を都度走査するコストを、既に定義済みのケースでは回避できるようにしています。

---

2. 変更内容の詳細  

変更ファイル:
- `actionpack/lib/action_controller/metal/allow_browser.rb` (+1 / -1)

実質的には1行のロジック修正で、イメージとしては次のような変更です（※実際のコードを概ね再構成した例）:

```ruby
# 変更前（例）
require "user_agent"

module ActionController
  module AllowBrowser
    # ...
  end
end

# 変更後（例）
unless defined?(::UserAgent)
  require "user_agent"
end

module ActionController
  module AllowBrowser
    # ...
  end
end
```

ポイント:
- `require "user_agent"` を**無条件で呼ぶ**のではなく、トップレベルの `::UserAgent` がすでに定義されているか (`defined?(::UserAgent)`) を確認した上で `require` するようにした。
- これにより、
  - 既に別の場所で `UserAgent` がロードされている場合 → `require` を呼ばない
  - 未ロードの場合 → これまで通り `require "user_agent"` を実行
- 参照されているフォローアップ元PR: https://github.com/rails/rails/pull/57974  
  → 元PRで `UserAgent` 利用まわりのロジックが導入・変更されており、その最適化・仕上げとして本PRが入っている位置づけです。

技術的背景:
- Ruby の `require` は内部的に `$LOADED_FEATURES`（すでにロードしたファイルの一覧）を線形探索して「同じファイルを二重にロードしていないか」を確認します。
- 大規模アプリケーションや多くのファイルがロードされる環境では、この探索コストが積み重なります。
- `defined?(::UserAgent)` のチェックは単純な定数解決で済むため、既に定義済みなら `require` するよりも高速に判定が可能です。

---

3. 影響範囲・注意点  

影響範囲:
- `actionpack` の `ActionController::Metal` にある `AllowBrowser` 機能（おそらくブラウザ判定や User-Agent ベースの許可制御に関するモジュール）が `UserAgent` クラスに依存する部分のみ。
- `::UserAgent` が
  - すでにアプリ側や別のライブラリ側で定義済み → 今後は Rails 側では `require "user_agent"` を呼ばなくなる。
  - 未定義 → 従来どおり `require "user_agent"` が行われるため挙動は変わらない。

挙動面の注意:
- 名前空間を変更しているわけではなく **トップレベル `::UserAgent`** の有無で判断するため、以下のようなケースでも従来どおり `require` されます:
  ```ruby
  module MyApp
    class UserAgent
      # ...
    end
  end
  ```
  → この場合、`defined?(::UserAgent)` は `nil` なので `require "user_agent"` が実行されます。
- 逆に、アプリ内で独自の `::UserAgent` クラスを定義している場合:
  ```ruby
  class UserAgent
    # アプリ独自の実装
  end
  ```
  → Rails 側では `require "user_agent"` を行わず、その独自実装が利用され得ます。  
    - すでにそういう構成で動かしているアプリでは、今回の変更により「意図通りに独自 `::UserAgent` が使われる」ことがより確定的になる反面、「本来は gem の `UserAgent` を使う前提だったが、たまたま同名クラスを定義していた」という場合には潜在的に挙動が変わる可能性があります。
    - ただし、これは Ruby の定数解決ルールに沿った自然な結果であり、PRの目的である「無駄な `require` の回避」とトレードオフになる部分です。

パフォーマンス面:
- アプリケーションの起動時やリクエスト処理中に何度も `AllowBrowser` がロード・参照されるような環境では、特に `$LOADED_FEATURES` が肥大化している場合に軽微ながらパフォーマンス改善が見込めます。
- 変更はきわめて小さく、API 互換性への影響は限定的です。

---

4. 参考情報 (あれば)  

- フォローアップ元PR: https://github.com/rails/rails/pull/57974  
  → `AllowBrowser` / `UserAgent` 周りの初期導入・修正の文脈を把握するのに有用です。
- Ruby `require` の挙動と `$LOADED_FEATURES`:
  - Ruby公式ドキュメント: https://docs.ruby-lang.org/ja/latest/method/Kernel/m/require.html  
  - `$LOADED_FEATURES` が線形リストであることから、ファイル数が増えるほど `require` チェックが遅くなりうる、という一般的な話題を背景にした最適化です。

## [#59454](https://github.com/rails/rails/pull/59454) [8-1-stable] Run async calculations and `async_find_by_sql`/`async_count_by_sql` synchronously inside a joinable transaction {#pr-59454}

**マージ日**: 2026/10/31 | **作成者**: [@bensheldon](https://github.com/bensheldon)

1. 概要 (1-2文で)  
このPRは、ActiveRecord 8.1系 (`8-1-stable`) に対して、「joinable なトランザクション内では非同期クエリを同期的に実行する」よう挙動を修正するバックポートです。`async_find_by_sql` / `async_count_by_sql` や、非同期計算 (`async_*`) 系メソッドがトランザクション内で例外を起こさず安全に動くようにします。

---

2. 変更内容の詳細

### 背景

- Rails 8 では `load_async` や `async_***` 系 API により、クエリをスレッドプールで非同期実行する仕組みがあります。
- 一方で、**joinable なトランザクション**（ネスト可能・再利用可能なトランザクション）の内部で非同期クエリを飛ばすと、接続共有・ロック・トランザクション境界の整合性の問題が起こりやすく、原則として許可されていません。
- このPRでは、そのようなトランザクション内では「非同期クエリ呼び出しだとしても、内部的には同期クエリとして即時に実行する」というフォールバック動作を導入・補強しています。

---

### 変更1: `async_find_by_sql` / `async_count_by_sql` の挙動 (querying.rb)

対象ファイル: `activerecord/lib/active_record/querying.rb` (+9/-2)

- `async_find_by_sql`, `async_count_by_sql` が、**joinable トランザクション内部かどうか**を判定し、内部で使う低レベルクエリ実行メソッドが変わります。
- 元PR (#59223) では `_sql_for_find` が導入されていましたが、8.1系には存在しないため、`async_count_by_sql` は引き続き `sanitize_sql(sql)` を利用する形でバックポートされています。

イメージとしては次のような処理です（概念的な疑似コード）:

```ruby
def async_find_by_sql(sql, ...)
  if connection.current_transaction.joinable?
    # トランザクション中 → 非同期は諦めて同期実行
    records = find_by_sql(sql)
    # すでにロード済みの Relation::LazyEnumerator を返す など
  else
    # トランザクション外 → 通常どおり非同期実行
    async_adapter.schedule_find_by_sql(sql, ...)
  end
end

def async_count_by_sql(sql, ...)
  sanitized = sanitize_sql(sql)
  if connection.current_transaction.joinable?
    # 同期で count 実行
    count_by_sql(sanitized)
  else
    # 非同期実行
    async_adapter.schedule_count_by_sql(sanitized, ...)
  end
end
```

ポイント:

- joinable トランザクション中で非同期を無理に走らせず、**安全な同期クエリにフォールバック**します。
- 8.1系では `_sql_for_find` がないため、`async_count_by_sql` は以前と同じく `sanitize_sql` ベースで SQL を整えています。

---

### 変更2: `ids` / `async_ids` と計算系 (`calculations.rb`)

対象ファイル: `activerecord/lib/active_record/relation/calculations.rb` (+20/-4)

- 8.1系では `ids` が `pluck` に委譲せず、自前で `select_all` を発行している実装になっています。
- このため、**トランザクション内で `async_ids` を呼ぶと、内部で `select_all` が直接非同期実行されようとして例外が起きる**という問題がありました。
- このPRでは、`ids` の内部で使う `select_all` 相当処理を `_async_select_all` に切り出し、そのなかで「joinable トランザクション中かどうか」を判定して同期 / 非同期を切り替えるようにしています。

概念的には以下のような分岐です:

```ruby
def _async_select_all(arel)
  if connection.current_transaction.joinable?
    # トランザクション中 → 同期実行
    connection.select_all(arel)
  else
    # トランザクション外 → 非同期実行
    async_adapter.select_all(arel)
  end
end

def ids
  # 従来: connection.select_all(arel) を直接呼んでいた
  rows = _async_select_all(arel_for_ids)
  rows.map { |row| row[primary_key] }
end

def async_ids
  # 8.1系の実装方針に沿って、上記 _async_select_all を経由することで、
  # トランザクション中なら同期、外なら非同期として動作するようになる
end
```

ポイント:

- `async_ids` が joinable トランザクション内で例外にならないよう、**`ids` 自体も「非同期の可否を判断するレイヤー」を通す**ようになった、という修正です。
- 結果として、`async_ids` も他の `async_*` メソッドと同様に「トランザクション内では同期にフォールバック」する整合性が取れます。

---

### 変更3: テスト追加 (load_async_test.rb)

対象ファイル: `activerecord/test/cases/relation/load_async_test.rb` (+42/-0)

- joinable トランザクションの中で以下が**例外を出さず同期実行されること**を確認するテストが追加されています:
  - `async_find_by_sql`
  - `async_count_by_sql`
  - `async_ids`
  - 他の async 計算関連メソッド
- 典型的には次のようなケースがカバーされます（イメージ）:

```ruby
test "async_find_by_sql runs synchronously inside joinable transaction" do
  Post.transaction(joinable: true) do
    relation = Post.async_find_by_sql("SELECT * FROM posts")
    assert_equal Post.count, relation.to_a.size  # 例外が出ない / 実際に結果が取れる
  end
end
```

これにより、今回の挙動変更が実際に動作していることが検証されています。

---

3. 影響範囲・注意点

- 対象バージョンは Rails 8.1 系 (`8-1-stable`) のみです（`main` 側の変更 #59223 のバックポート）。
- **アプリケーションコードから見える主な変化**:
  - joinable なトランザクション内で `async_*` メソッド（`async_find_by_sql`, `async_count_by_sql`, `async_ids` など）を呼んだ場合、
    - 以前: 環境や組み合わせによっては例外や不整合が起こりうる
    - 今回以降: 例外を避けるため**同期的に即時実行にフォールバック**する
  - そのため「トランザクション内なのにバックグラウンドでクエリが走り続けている」といった危うい状態を避けられます。
- パフォーマンス上の注意:
  - joinable トランザクション内で `async_*` を多用しても、実際には同期クエリとして実行されるため、**期待した非同期並列実行による高速化は得られません**。
  - 非同期化によるスループット向上を狙う場合は、**トランザクション境界の外側で `async_*` を呼ぶ設計にする**必要があります。
- 互換性:
  - 公開APIのメソッドシグネチャは変わらず、挙動も「例外が減り、安全側に倒れる」方向の変更のため、**後方互換性は高い**と考えられます。
  - ただし「トランザクション内で非同期になること」を前提にした特殊な実装があれば、その前提は成り立たなくなる点には注意が必要です。

## [#58728](https://github.com/rails/rails/pull/58728) Read structure dump exclusions from the database being dumped {#pr-58728}

**マージ日**: 2026/10/31 | **作成者**: [@ngan](https://github.com/ngan)

1. 概要 (1–2文で)  
`db:structure:dump`（`structure_dump`）実行時に、`schema_ignored_tables` の判定と PostgreSQL の `search_path` 取得を「ダンプ対象DBではなく現在の接続DB」から読んでいたバグを修正し、常に「ダンプ対象の DB 設定 (`db_config`)」に対して接続して情報を取得するようにした PR です。これにより、マルチDB構成やカスタムタスクから `ActiveRecord::Tasks::DatabaseTasks.structure_dump` を直接呼び出すケースでも、期待通りに無視テーブル・search_path が反映されます。

---

2. 変更内容の詳細

### 問題の背景

従来の `structure_dump` の挙動:

- `schema_ignored_tables` のパターンマッチは **`ActiveRecord::Base` が現在接続している DB** のテーブル一覧に対して行っていた。
- その結果として:
  - 無視すべきテーブルの判定が「ダンプ対象 DB」ではなく「現在接続中の DB」を元にされる。
  - 判定後に `--ignore-table=<ダンプ対象DB名>.<テーブル名>` を組み立てていたため、  
    「存在しないテーブルを指定する (false positive)」と「本当は無視すべきテーブルが無視されない (false negative)」の両方が起こり得た。
- `bin/rails db:schema:dump` は `with_temporary_pool(db_config)` で一時的に接続を切り替えてからアダプタを呼ぶためこの問題は出ないが、  
  `ActiveRecord::Tasks::DatabaseTasks.structure_dump` を直接叩くケース（マルチDBアプリで自前の Rake タスクを書いていて DB をループしながらダンプする、など）ではバグが顕在化していた。

具体例（MySQL、`schema_ignored_tables = [/\A_.+_gho\z/]` の場合）:

- 現在の接続: `activerecord_unittest`
- ダンプ対象: `activerecord_unittest2`

期待:
- `activerecord_unittest2` に存在してパターンにマッチする `_lives_in_target_gho` を **無視** したい。

実際:
- 現在接続中の `activerecord_unittest` の `_lives_in_primary_gho` を見てしまい、  
  `--ignore-table=activerecord_unittest2._lives_in_primary_gho` を出力する（ダンプ対象には存在しないため実害はない）。
- 一方、本来無視すべき `_lives_in_target_gho` は「現在の接続側にはない」ため検出されず、`structure.sql` に含まれてしまう。

PostgreSQL 固有の問題:
- `structure_dump` の最後に `SET search_path TO #{connection.schema_search_path}` をダンプに追記しているが、  
  ここでも「現在接続中の DB の search_path」を使っており、「ダンプ対象 DB の search_path」になっていなかった。

### 修正方針

- `structure_dump` が必要とする情報（テーブル一覧、`schema_ignored_tables` のマッチング、`schema_search_path` など）は、  
  **「ダンプ対象 DB の `db_config` から新しく開いた接続」** を通して読むように変更。
- 新しく開いた接続は **ダンプ終了時に必ず閉じる**（`disconnect!`）。  
  - `with_temporary_pool` / `with_temporary_connection` のようにグローバルな `ActiveRecord::Base` の接続プールを差し替えない。
  - これにより、呼び出し元の接続状態に副作用を与えない。
- MySQL / SQLite については、`schema_ignored_tables.any?` な場合だけ接続を開くようにしており、  
  デフォルト設定（無視テーブルなし）では従来通り **シェルコマンドをそのまま叩くだけで DB への接続を開かない**。
- PostgreSQL はもともと search_path 取得のために接続を読んでいたので、常に接続を開く点は変わらないが、  
  今回の修正で「接続先が常にダンプ対象 DB」になる。

### コード側のポイント（概念レベル）

ファイル単位で見ると:

- `activerecord/lib/active_record/tasks/abstract_tasks.rb`
  - ダンプ対象 `db_config` から新しい接続を開いて処理し、終わったら閉じるための共通的な仕組みが追加されている（タスク用の抽象ヘルパ）。
- `mysql_database_tasks.rb` / `sqlite_database_tasks.rb`
  - `schema_ignored_tables` が空でなければ `db_config.new_connection` で接続を開き、
    そのコネクションからテーブル一覧を読み、`schema_ignored_tables` でマッチングしたテーブルを `--ignore-table` / `-T` オプションに反映。
  - 処理終了後に `disconnect!` で接続を閉じる。
- `postgresql_database_tasks.rb`
  - これまで `ActiveRecord::Base.connection` から読んでいた search_path を、「ダンプ対象 DB の接続」から読むように変更。
  - `schema_ignored_tables` による ignore-table の解決も同様にダンプ対象 DB への接続で行う。

疑似コードイメージ（概念）:

```ruby
def structure_dump(db_config, filename)
  connection = db_config.new_connection

  ignored_tables = resolve_ignored_tables(connection, schema_ignored_tables)
  search_path    = connection.schema_search_path # PostgreSQL

  # ignored_tables / search_path を元に pg_dump / mysqldump / sqlite コマンドを組み立てて実行

ensure
  connection&.disconnect!
end
```

※ 実際の実装は各アダプタごとに分かれていますが、考え方としては上記のような「ダンプ対象 db_config から接続を開いて、それを使う」という変更です。

### テストの更新

- MySQL (`mysql2_rake_test.rb`) / SQLite (`sqlite_rake_test.rb`) / Trilogy それぞれで、
  - 無視テーブルが「ダンプ対象 DB のものだけに適用されているか」
  - 「現在接続中の別 DB にある同名テーブル」には影響しないか
  を検証する回帰テストが追加。
- PostgreSQL (`postgresql_rake_test.rb`)
  - 変更量が多く、`structure_dump` 用のテストをヘルパでラップし、
    - ダンプ対象 DB の接続をモック／フェイクで用意
    - 意図的に到達不能なホストを指定するケースでもテストできるようにしつつ、
    - 「必ず接続が閉じられている」ことも検証するように整理。
  - search_path が `"SET search_path TO dumped_schema;"` を含むことを期待し、  
    以前のように `"ambient_schema"` が出てしまう場合にはテストが落ちるようになっている。

---

3. 影響範囲・注意点

- **影響を受ける主なケース**
  - `ActiveRecord::Tasks::DatabaseTasks.structure_dump` を **直接** 呼び出しているアプリケーション／Rake タスク。
  - マルチ DB 構成で、「ある DB に接続したまま別の DB を structure dump している」ようなカスタム処理。
- 期待される変化
  - `schema_ignored_tables` による除外が「実際にダンプしている DB」を基準に行われるようになる。
  - PostgreSQL では `structure.sql` 内の `SET search_path TO ...;` が「ダンプ対象 DB の search_path」になる。
- 互換性上の注意
  - これまで「バグ前提の挙動」に依存していた場合（たとえば“今つながっている DB のテーブルを ignore したい”という非常に特殊な状況）は挙動が変わりますが、  
    通常の設計では「ダンプ対象 DB を基準にする」方が正しいため、多くの場合はバグ修正としてのプラス影響のみです。
- 接続／到達性に関する注意
  - MySQL / SQLite:
    - `schema_ignored_tables` が空（デフォルト）なら従来通り DB への新規接続は不要です。
    - `schema_ignored_tables` を設定している場合は、**ダンプ対象 DB への接続が実際に張れる必要があります**（テーブル一覧を取得するため）。
  - PostgreSQL:
    - もともと search_path の取得のために接続していたので「新しく到達性の要件が増える」ことはありませんが、
      今回から「必ずダンプ対象 DB に対して接続を開く」ことになったため、  
      テストや CI で「ダンプ対象 DB だけ意図的に到達不能にしている」ような状況があれば考慮が必要です。
- リソースと副作用
  - `with_temporary_pool` / `with_temporary_connection` を使わずに **スタンドアロンのコネクション** を開いて即クローズする方式なので、
    - 呼び出し元の `ActiveRecord::Base` のコネクションプールには影響しません。
    - 特に SQLite では、「`with_temporary_connection` が DB ファイルを再作成してしまう」といった副作用を避けています。

---

4. 参考情報 (あれば)

- PR タイトル: **Read structure dump exclusions from the database being dumped**
- 対応範囲:
  - SQL 形式の schema dump (`schema_format = :sql`) をサポートする 3 つのアダプタ（MySQL / PostgreSQL / SQLite）＋ Trilogy における `structure_dump`。
- 関連設定:
  - `ActiveRecord::Base.schema_ignored_tables`  
    （`ActiveRecord::SchemaDumper.ignore_tables` と同義に扱われることが多い）  
    正規表現／文字列／配列などで、ダンプ時に無視したいテーブルを指定するための設定。
- 類似パターン:
  - Action Cable の PostgreSQL アダプタがサブスクリプション用に `pool.new_connection` + `disconnect!` を使っているのと同じパターンで、  
    「グローバルな接続状態を汚さない一時的な接続」の作り方として Rails 内で既存実績のある手法に揃えています。

## [#59458](https://github.com/rails/rails/pull/59458) Freeze tag strings before marking them HTML safe {#pr-59458}

**マージ日**: 2026/10/31 | **作成者**: [@linyiru](https://github.com/linyiru)

1. 概要 (1-2文で)  
`content_tag` や `tag.xxx` などのタグヘルパーが内部で生成する文字列を、HTML セーフ化する前に `freeze` することで、不要な文字列オブジェクトの割り当てを 1 つ削減し、リンクやフォーム要素が多いページでのメモリ・パフォーマンスを改善する変更です。挙動や API は変わらず、`SafeBuffer` 自体は引き続き変更可能なままです。

---

2. 変更内容の詳細  

### 背景となる問題

`content_tag_string` / `self_closing_tag_string` は、以下のようなおおよその処理をしています:

```ruby
tag_string = "<div class=\"card\">Hello</div>" # 文字列補間で生成
safe = tag_string.html_safe                    # SafeBuffer に包む
```

Ruby の実装上、文字列が 23 byte を超える（64bit 環境）と、  
「**凍っていない文字列(String)」と「SafeBuffer の内部文字列」**が中身を共有できず、

- 補間で作られた `tag_string`
- その内容を共有するための「隠し文字列」

という 2 つ目の文字列オブジェクトが余計に割り当てられていました。  
しかも元の `tag_string` はすぐ GC 対象になるため、実質「捨てるためだけの文字列」を毎回 1 個多く作っている状態でした。

### 今回の対策

この PR では、「**HTML セーフ化する前にタグ文字列自体を `freeze` する**」ように変更しています。

イメージとしては:

```ruby
tag_string = "<div class=\"card\">Hello</div>".freeze
safe = tag_string.html_safe  # SafeBuffer はこの凍結済み文字列をそのまま内部で共有
```

こうすることで:

- `tag_string` は不変(`frozen`)なので、SafeBuffer との内容共有が可能
- SafeBuffer のために新しい「隠し文字列」を作らずに済む
- `tag_string` 自体は他で参照しない（一時的なローカル変数）ので、凍結しても悪影響はない

という状態になり、**タグ 1 つあたり文字列オブジェクト 1 個ぶんのメモリ割り当てを削減**できます。

### SafeBuffer の挙動は維持

重要なのは、「**返される `SafeBuffer` オブジェクト自体はこれまで通り可変である**」という点です。

テストでは、以下を確認しています:

- `content_tag`
- `tag.div`
- `tag.input`
- `tag`（任意タグ）

いずれも、

```ruby
buf = content_tag(:div, "Hello", class: "card")
buf << " world"  # これが問題なく動くこと
```

のように、返り値の `SafeBuffer` に対する追記ができ、  
**その追記が後続のタグ生成に影響しない**ことが明示的にテストされています。

このテストは、もし `SafeBuffer` 自体を `freeze` してしまった場合に失敗するよう書かれており、  
あくまで「内部で一時的に作るタグ文字列だけを `freeze` している」ことを保証しています。

### パフォーマンス計測結果

Ruby 3.4.1 arm64 + `GC.stat(:total_allocated_objects)` によると:

| ケース | main | この PR |
| --- | ---: | ---: |
| `link_to("Post number 42", "/posts/42")` | 5 | 4 |
| `content_tag(:div, "Hello", class: "card")` | 5 | 4 |
| `tag.input(type: "hidden", name: "authenticity_token", value: "abc")` | 5 | 4 |
| `tag.br`（23byte以下で埋め込み可能） | 3 | 3 |
| パーシャル内で 100 レコード分に `link_to` | 2148 | 2048 |

主に 23byte を超えるタグ（属性付きの多くのタグ）で 1 オブジェクト削減されており、  
`link_to`, `button_to`, form helpers など **tag builder ベースのあらゆるヘルパーが恩恵を受ける**形です。

---

3. 影響範囲・注意点  

- 影響範囲:
  - Action View のタグ関連ヘルパー全般 (`content_tag`, `tag.*`, `link_to`, `button_to`, 各種 form helper など)
  - しかし、**外部に見える挙動や API は変更されていません**。
- 注意点:
  - 返される `SafeBuffer` はこれまで同様にミュータブルであり、`<<` などで追記できます。
  - `CHANGELOG` 更新は不要とされていますが、**動作仕様の変更ではなくパフォーマンス最適化扱い**です。
  - タグ文字列が 23byte 以下（オブジェクト内に埋め込める長さ）の場合、もともと追加アロケーションはほぼなかったため、改善効果はありません（`tag.br` のようなケース）。

アプリケーションコード側で、`content_tag` や `tag` が返す `SafeBuffer` をこれまで通り扱っている限り、  
この変更による互換性問題が発生する可能性はかなり低いと考えられます。

- Ruby の文字列内部表現に関するポイント:
  - 64bit 環境では、23byte までの短い文字列はオブジェクト内に「埋め込み」表現される
  - より長い文字列はヒープ上に別途確保され、そのポインタを持つ
  - 不変(`frozen`)文字列は他オブジェクトと中身を安全に共有しやすく、`SafeBuffer` がそれを再利用できるようになると、余計なコピーや「隠し文字列」の作成が省ける

## [#59456](https://github.com/rails/rails/pull/59456) Parse each address once when calculating the remote IP {#pr-59456}

**マージ日**: 2026/10/31 | **作成者**: [@linyiru](https://github.com/linyiru)

1. 概要 (1-2文で)  
Rails の `ActionDispatch::RemoteIp` ミドルウェアで、リモート IP 判定時に同じ IP 文字列を何度も `IPAddr` にパースしていた処理を見直し、1回のパース結果を再利用するようにしてオブジェクト生成数を削減した PR です。挙動（どの IP がクライアントとして選ばれるか）は変えずに、特にログ出力など頻繁に呼ばれるケースのパフォーマンスを改善します。

---

2. 変更内容の詳細  

### 背景となる既存実装の問題

`ActionDispatch::RemoteIp` の内部では、以下のような流れでクライアント IP を決定しています（簡略化）:

- `GetIp#sanitize_ips`  
  - `Client-Ip`, `X-Forwarded-For`, `REMOTE_ADDR` などから候補 IP の文字列配列を作る
  - 各文字列を `IPAddr.new` でパース
  - `to_range` を呼んで `Range<IPAddr>` を作る（このときさらに 2つの `IPAddr` オブジェクトが生成される）
  - ネットマスク付きのアドレスを弾く 等のフィルタリングを行う
- `GetIp#first_non_proxy`  
  - 上で作った文字列群に対して、再度 `IPAddr.new` でパースし直しつつ、`trusted_proxies` と比較して最初の「プロキシでない IP」を選ぶ

問題点:
- 同じ IP 文字列に対して `IPAddr.new` を最大 2 回呼んでいる
- ネットマスクを含まないアドレスにも一律 `to_range` を呼んでおり、不要なオブジェクト（`IPAddr` 2つ + `Range`）を毎回生成している
- この処理はデフォルトのログ出力（"Started GET ... for ..."）のたびに走るため、全リクエストに対して無駄なアロケーションが発生

### 今回の変更ポイント

#### 1) sanitize_ips でのパースと range 生成の最適化

- 以前は全ての IP 文字列に対して:
  ```ruby
  ip = IPAddr.new(raw_ip)
  ip_range = ip.to_range # 実際にはネットマスクチェック目的
  ```
  としていたが、`IPAddr` の仕様として:
  - `"1.2.3.4"` のようにスラッシュがない場合は「ホストアドレス（単一 IP）」として扱われる
  - `"1.2.3.4/24"` のようにスラッシュ付きの場合だけネットマスクが解釈される
- これを利用し、**スラッシュを含むアドレスにだけ range を生成する**ように変更:
  - 「スラッシュなし＝常に単一ホスト」であり、ネットマスク付きアドレスかを確認するために `to_range` する必要がない

これにより、一般的な `"203.0.113.7"` のようなアドレスでは `Range` と余分な `IPAddr` が生成されなくなります。

#### 2) sanitize_ips でパースした IP オブジェクトの再利用

- `sanitize_ips` 内で、各文字列を `IPAddr` にパースした結果を保持し、そのまま `first_non_proxy` に渡すように変更:
  - これまでは `first_non_proxy` 内でも同じ文字列を再度 `IPAddr.new(raw_ip)` していた
  - 変更後は、`sanitize_ips` 由来の IP については、既に生成済みの `IPAddr` オブジェクトをそのまま使う
- ただし API 互換性のため:
  - `first_non_proxy` は依然として「文字列 or IPAddr など」を受け取れる
  - `sanitize_ips` がアプリ側でオーバーライドされて別の形式を返す可能性もあるため、「渡されていない文字列」については従来どおり `IPAddr.new` でパースするフォールバックを維持

#### 3) ネットマスク付きアドレスに関するテストの追加

- これまで `Client-Ip` や `REMOTE_ADDR` に `"2001:db8::1/64"` のような**ネットマスク付き IP** が来たときの挙動はテストされていなかった
- 本 PR では、**変更前の main ブランチで挙動を固定してから**、その結果を期待値として 14 パターン分のテストを追加
  - `Client-Ip` と `REMOTE_ADDR` の組み合わせを変えたテーブルテストのような形
  - `X-Forwarded-For` は Rack 側のバージョン依存（Rack 3.2.7 ではスラッシュ付きアドレスを捨てる挙動）があるため、ここでは利用しないテストにしている
- このテストは:
  - main (変更前) と本 PR で同じ結果になる
  - `sanitize_ips` 内の「ネットマスク付きアドレスを弾くチェック」を外すとテストが落ちる  
 ＝ 挙動を変えずに内部実装を改善できていることの回帰テストになっている

### 4) パフォーマンス（オブジェクトアロケーション）の改善

Ruby 3.4.1 arm64 / デフォルトの trusted proxies / `GC.stat(:total_allocated_objects)` 計測:

| ケース | main | この PR |
| --- | ---:| ---:|
| LB 経由: REMOTE_ADDR=10.0.0.5, XFF=203.0.113.7 | 65 | 45 |
| 2段プロキシ: XFF=203.0.113.7, 10.1.2.3 | 101 | 65 |
| IPv6 LB: REMOTE_ADDR=fc00::5, XFF=2001:db8::7 | 142 | 96 |
| 直アクセス: REMOTE_ADDR=127.0.0.1 | 37 | 22 |

- Rack 経由のシンプルな `render plain:` リクエストで、401 → 386 object allocations に削減
- マシン負荷の関係で時間計測は載せていないが、GC 負荷低下につながる変更

---

3. 影響範囲・注意点  

- 対象範囲:
  - `ActionDispatch::RemoteIp` ミドルウェア内部 (`GetIp#sanitize_ips`, `GetIp#first_non_proxy`)
  - `remote_ip` を利用するログ出力やアプリケーションコード全般に、**間接的にパフォーマンス改善**として効く
- 互換性 / 挙動:
  - 公開インターフェース（`request.remote_ip` など）の**挙動変更はなし**とされている
  - ネットマスク付きアドレスに関しては、**変更前と同じ結果になることをテストで保証**している
  - `sanitize_ips` / `first_non_proxy` のメソッドシグネチャや返り値の形式は変えていない
  - `sanitize_ips` を独自にオーバーライドしているアプリや gem があっても、`first_non_proxy` 側でフォールバックパースするため、基本的には問題は起きない設計
- 他 PR (#57627) との関係:
  - 両者とも `first_non_proxy` 内の `IPAddr.new(raw_ip)` 行を触るためテキスト上はコンフリクトするが、意味的には両立する
  - #57627 で `ip.native` を使うようにしても、それは新しい `IPAddr` を返すだけであり、「sanitize_ips で保持している IP オブジェクト」を破壊しないので、この PR の「パース結果の再利用」方針とは問題なく共存可能

注意点としては、「自分で `ActionDispatch::RemoteIp` を monkey patch している」ような場合に、内部の挙動に依存していると微妙な影響が出る可能性はありますが、通常のアプリケーション利用ではそのようなケースは稀で、基本的に安全な内部最適化です。

---

4. 参考情報 (あれば)

- 対象ファイル:
  - `actionpack/lib/action_dispatch/middleware/remote_ip.rb`
  - `actionpack/test/dispatch/request_test.rb`
- 関連 PR:
  - #57627: `first_non_proxy` 内で `ip.native` を使う変更（この PR と意味的に競合しない）
- Rack の挙動:
  - Rack 3.2.7 では `X-Forwarded-For` 内のスラッシュ付き IP を捨てる挙動があり、Rails 側より前段でフィルタされる
  - そのため、ネットマスク付き IP のテストは `Client-Ip` と `REMOTE_ADDR` に限定している

## [#59453](https://github.com/rails/rails/pull/59453) Reuse the period of time zones without transitions {#pr-59453}

**マージ日**: 2026/10/31 | **作成者**: [@linyiru](https://github.com/linyiru)

1. 概要 (1–2文で)  
UTC など「一切の遷移（サマータイム等）がないタイムゾーン」について、`TimeZone` が `TZInfo::TimezonePeriod` を毎回新規生成せずに再利用するようにして、ActiveSupport/ActiveRecord におけるタイムゾーン関連のオブジェクト生成数と処理時間を削減する変更です。機能的な挙動は変えずに、UTC をデフォルトタイムゾーンとする一般的な Rails アプリのパフォーマンスを改善します。

---

2. 変更内容の詳細  

### 問題背景

- Rails の `ActiveSupport::TimeWithZone` は、ローカル時刻・オフセット・略称を初めて求めるタイミングで `TimeZone#period_for_utc` を呼び出し、`TZInfo::TimezonePeriod` を取得しています。
- UTC のような「遷移のないタイムゾーン」では、tzinfo レベルでは常に同じ単一の period を返すにもかかわらず、**呼び出しの度に `TZInfo::Timestamp` と `TimezonePeriod` を新しく生成**していました。
- この処理は `record.created_at.to_date`, `l(record.created_at)` など、リクエスト中に大量に呼ばれうるため、オブジェクトアロケーションとCPUコストの無駄が発生していました。

### この PR のコア変更

#### 1) 遷移を持たないタイムゾーンでは period をキャッシュして再利用

- `TimeZone#initialize` の時点で、tzinfo の period を一度だけ調べ、「開始も終了も遷移がない period ＝全時刻をカバーする固定 offset のゾーン（UTC/固定オフセットの Etc/GMT±X など）」であるかを判定。
- そのようなゾーンの場合、**その period をインスタンス変数として保持**し、以降の `period_for_utc` と `period_for_local` では、tzinfo に問い合わせず **同じ period オブジェクトを返す**ように変更。

イメージとしては:

```ruby
class ActiveSupport::TimeZone
  def initialize(*)
    # 既存のロジックで tzinfo ゾーンを取得
    period = @tz.period_for_utc(Time.utc(2026, 1, 1))

    if period.start_transition.nil? && period.end_transition.nil?
      # 遷移のないゾーンと判定
      @period_without_transitions = period.freeze # ゾーンと一緒に共有可能に
    end
  end

  def period_for_utc(time)
    if @period_without_transitions
      @period_without_transitions
    else
      @tz.period_for_utc(time)  # 従来通り tzinfo に委譲
    end
  end

  def period_for_local(time, dst = true)
    if @period_without_transitions
      @period_without_transitions
    else
      @tz.period_for_local(time, dst)
    end
  end
end
```

※実際のコードは多少異なりますが、概念的にはこのような形です。

- `TimeZone#initialize` はもともと `utc?` 判定のために period を調べていたので、「遷移なし判定＋キャッシュ」によって **追加の period 取得コストは発生しません**。
- 得られた period は TimeZone オブジェクトと同様に shareable にしており、Ractor で共有可能な性質も維持されています。

#### 2) 遷移を持つタイムゾーンの挙動はそのまま

- サマータイムを持つ `America/New_York` などでは、これまで通り tzinfo に問い合わせ、UTC⇔ローカル変換時に EST/EDT を切り替えます。
- 従って DST を伴うタイムゾーンの挙動は一切変わっていません。

#### 3) テストの追加

追加テストで、主に以下を検証しています。

- UTC / `Etc/UTC` / `Etc/GMT+5`：  
  - 1900, 2026, 2100 など離れた年の時刻に対して `period_for_utc` / `period_for_local` が **常に同一の period オブジェクトを返す**こと。
  - その period の offset, abbreviation が tzinfo のものと一致すること。
  - `TimeWithZone` を通したローカル時刻計算も期待通りであること。
- 遷移を持つゾーン（例: `America/New_York`）：  
  - 年や季節に応じて EST/EDT が正しく切り替わること（＝キャッシュは使われず既存のロジックが使われていること）。
- UTC の `TimeZone` が依然として **Ractor-shareable** であること。

#### 4) パフォーマンス/メモリへの効果

作者の計測（Ruby 3.4.1 arm64）によると:

- `TimeWithZone.new(utc_time, Time.zone).day`（UTC）  
  - アロケーション数: 3 → 1
- `Time.zone.local(...).hour`（UTC）  
  - アロケーション数: 6 → 3
- `America/New_York` ではアロケーション数は変化なし（4 / 7 → 4 / 7）

Rails アプリ全体として:

- 100 レコードをロードして各レコードで timestamp を1回読むリクエスト：  
  - 2597 → 2197 allocations
- 同じ 100 レコードをコレクションパーシャルでレンダリング：  
  - 4342 → 3942 allocations

処理時間の一例（かなりノイジーな環境での計測のため参考値）:

- 単一の UTC timestamp 読み込み:  
  - 約 1.1–2.1 µs → 0.34–0.38 µs
- 100件リクエスト（YJIT使用）:  
  - 中央値 542 µs → 483 µs

---

3. 影響範囲・注意点  

- **挙動の変更は原則なし**  
  - 仕様上は「遷移のないタイムゾーンの period オブジェクトを毎回新規生成していたものを、同一オブジェクトに変えただけ」なので、 `TimeWithZone` の返す値（ローカル時間・offset・abbr）は変わりません。
  - サマータイムを持つゾーンは完全にこれまで通りです。

- **恩恵が大きいケース**  
  - `config.time_zone = 'UTC'` や `Etc/UTC`, 固定 offset のタイムゾーン (`Etc/GMT+5` など) を使っているアプリケーション。
  - 特に大量の Active Record レコードの timestamp をテンプレート側でレンダリングしている場合に、オブジェクト生成数削減の恩恵を受けます。

- **互換性リスク**  
  - `TimezonePeriod` オブジェクトの「同一インスタンス性」に依存したコード（例えば `object_id` の比較など）を書いていると、UTC ゾーンでは今後「常に同じオブジェクトが返ってくる」ようになるため、挙動が変化する可能性はあります。ただし、そのようなコードは通常の利用では想定されていません。
  - Ractor 互換性はテストで担保されています。

- **CHANGELOG なし**  
  - 挙動の変更ではなく最適化のみのため、CHANGELOG には記載していません。

---

4. 参考情報 (あれば)

- 関連 PR / コミット:
  - #58785 およびコミット `bd2f4d1cb9`  
    - `TimeZone#today` における「UTC が一定なゾーンでの period lookup をスキップする」最適化。今回の変更はその流れをさらに進め、period オブジェクトそのものの再利用に踏み込んだもの。
- 計測方法:
  - `GC.stat(:total_allocated_objects)` によるアロケーションカウント。
  - Ruby 3.4.1 arm64 環境でのベンチマーク。タイミングは変動が大きいため、主に allocation 数の削減が根拠となっています。

## [#59451](https://github.com/rails/rails/pull/59451) Make Parameters#to_h and #to_unsafe_h up to 1.6x faster by copying each hash once {#pr-59451}

**マージ日**: 2026/10/31 | **作成者**: [@czj](https://github.com/czj)

1. 概要 (1-2文で)  
Rails の `ActionController::Parameters` における `to_h` / `to_unsafe_h` で、ネストしたハッシュを二重コピーしていた箇所を一度のコピーに抑えることで、最大約 1.6 倍の高速化を行った PR です。挙動（返却値の構造や `HashWithIndifferentAccess` の性質）は維持しつつ、内部実装をより効率的なメソッドに差し替えています。

---

2. 変更内容の詳細  

### 何をしているか

対象は Strong Parameters のこのあたりの処理（擬似コードイメージ）です:

```ruby
def to_h
  # もともと:
  # 1. HashWithIndifferentAccess を transform_values で変換しつつ
  # 2. with_indifferent_access で再度 Indifferent に変換していた
end
```

現状の問題点:  

- `Parameters#to_h` / `#to_unsafe_h` は、ネストした `Hash` を処理する際に:
  - `HashWithIndifferentAccess#transform_values` が **新しい `HashWithIndifferentAccess` を返す**
  - その戻り値に対してさらに `with_indifferent_access` を呼んで **もう一度 dup する**
- つまり、**各ネストハッシュが「2回コピーされている」** 状態になっている。  
- `to_h` は許可済みパラメータのマスアサイン (`Post.new(params.expect(post: ...))`) のたびに呼ばれるため、フォーム送信のたびにこのコストが積み上がる。

### 変更点

この PR では、`with_indifferent_access` の呼び出しを、より賢い変換メソッドである `nested_under_indifferent_access` に置き換えています。

`nested_under_indifferent_access` の挙動:

- 引数がすでに `HashWithIndifferentAccess` の場合:
  - そのまま（不要なコピーなしで）利用
- 引数が通常の `Hash` の場合:
  - `HashWithIndifferentAccess` に変換

これにより:

- **「常に dup する」→「必要なときだけ変換する」** に変わる
- それでも以下の 2 ケースでは変換が必要なため、動作は維持される:
  1. `to_h` にブロックを渡したとき（ブロックが plain `Hash` を返しうる）
  2. `Parameters#transform_values!` で plain `Hash` が保存されたとき

結果として:

- ネストしたハッシュは原則「1回だけ」コピーされるようになり、`to_h` / `to_unsafe_h` が高速化

### テストの追加・変更

2 つの重要なテストが追加されています:

1. `to_h` / `to_unsafe_h` の「完全コピー性」の保証テスト  
   - 返り値のハッシュ/配列が、元の `Parameters` オブジェクトと **ネストしたハッシュや配列を共有していない** ことを確認  
   - これにより、「高速化のために破壊的・共有的になっていないか」を担保

2. `transform_values!` 後のハッシュが「indifferent」で返ってくることのテスト  
   - `Parameters#transform_values!` で単なる `Hash` を内部にセットした場合でも
   - `to_h` / `to_unsafe_h` の結果ではそのハッシュが `HashWithIndifferentAccess` として振る舞うことを確認  
   - このテストは `nested_under_indifferent_access` による変換をやめると失敗するため、変換が必要であることの裏付けにもなっている

### 擬似コードイメージ

元:

```ruby
# HashWithIndifferentAccess を transform したあとで、
# with_indifferent_access でもう一度包み直していたイメージ
hash = some_hash_with_indifferent_access.transform_values { ... }
hash = hash.with_indifferent_access  # ← ここで不要な二重コピーが発生
```

変更後:

```ruby
# nested_under_indifferent_access により、
# 既に indifferent なものはそのまま利用し、
# plain Hash だけを変換する
hash = some_hash_with_indifferent_access.transform_values { ... }
hash = hash.nested_under_indifferent_access
```

---

3. 影響範囲・注意点  

### 影響範囲

- 対象: `ActionController::Parameters#to_h` / `#to_unsafe_h` の内部実装
- 主に次のようなコードパスで恩恵がある:
  - Strong Parameters を使ったフォーム入力のマスアサイン:
    ```ruby
    Post.new(params.expect(post: [:title, :body]))
    # 内部で to_h が走る
    ```
  - 深くネストしたパラメータを `to_h` / `to_unsafe_h` で普通のハッシュに変換する処理

パフォーマンス計測結果（抜粋・概略）:

- `to_h`（フラット 5 キー）: 最大 ~1.5–1.6x  
- `to_h`（ネストした order）: 最大 ~1.5–1.6x  
- `to_unsafe_h`（ネスト）: 最大 ~1.4–1.6x  
- `expect + to_h` 全体では 1.08–1.11x 程度の向上（`expect` 部分のコストも含むため）

### 互換性・注意点

- 48,000 パターンのランダムパラメータを使った検証で、以下が「main ブランチと完全に同じ」であることが確認済み:
  - `to_h`（許可された場合 / 許可されていない場合のエラー含む）
  - ブロック付き `to_h`
  - `to_unsafe_h`
  - `to_hash`
- 比較内容:
  - 返り値のクラス
  - frozen 状態
  - `default` / `default_proc`
  - `compare_by_identity`
  - ネスト構造
  - 返り値を変更しても元の `Parameters` が変わらないこと

つまり、**外部から見える挙動は変わらず、パフォーマンスだけが向上**している変更と見なせます。

注意が必要なケース:

- `ActionController::Parameters` の戻り値の **内部実装の細部に依存したメタプログラミング** をしている場合（`HashWithIndifferentAccess` の変換タイミングなど）には、挙動が微妙に変わる可能性がありますが、通常のアプリケーションコードでは問題にならない想定です。

## [#59450](https://github.com/rails/rails/pull/59450) Make deep_symbolize_keys and deep_stringify_keys up to 1.48x faster by not allocating a pair per key {#pr-59450}

**マージ日**: 2026/10/31 | **作成者**: [@czj](https://github.com/czj)

1. 概要 (1-2文で)  
`Hash#deep_symbolize_keys` / `deep_stringify_keys` / `deep_transform_keys` と `ActionController::Parameters#deep_transform_keys` の内部実装を変更し、キーごとに不要な `[key, value]` 配列を作らないようにして、最大約 1.5 倍の高速化とオブジェクト生成数削減を行う最適化 PR です。外部から見た振る舞い（結果のクラス・キー順序・衝突時の優先ルール）は一切変わりません。

---

2. 変更内容の詳細

### もともとの問題点

`deep_symbolize_keys` / `deep_stringify_keys` / `deep_transform_keys` は、内部で `_deep_transform_keys_in_object` というヘルパを使っていますが、その中で次のようなイテレーションをしていました。

```ruby
def _deep_transform_keys_in_object(object, &block)
  case object
  when Hash
    object.each_with_object(object.class.new) do |(key, value), result|
      result[yield(key)] = _deep_transform_keys_in_object(value, &block)
    end
  # ...
  end
end
```

`each_with_object` によってブロックには `|(key, value), result|` という形で渡されるため、Rails 側が `(key, value)` という 2 要素配列を毎回展開することになり、「キー1つごとに `[key, value]` の一時配列を1個生成する」というコストがかかっていました。  
深くネストした大きめのハッシュ（JSON:API 形式のペイロードなど）では、この一時配列の生成が多くなり、計測では `deep_symbolize_keys` の 92 個のオブジェクト割り当てのうち 66 個がこの「ペア配列」という状況でした。

### 今回の変更内容

この PR は、そのイテレーションを次のように変更しています。

```ruby
def _deep_transform_keys_in_object(object, &block)
  case object
  when Hash
    result = object.class.new
    object.each do |key, value|
      result[yield(key)] = _deep_transform_keys_in_object(value, &block)
    end
    result
  # ...
  end
end
```

ポイント:

- `each_with_object(self.class.new)` → ローカル変数 `result = object.class.new` に変更
- ブロック引数も `|(key, value), result|` → `|key, value|` に変更  
  → `[key, value]` の 2 要素配列を生成せずに済む
- 戻り値として `result` を明示的に返す

同じ変更が `ActionController::Parameters` 内部の `deep_transform_keys` 用ヘルパにもコピーされ、Strong Parameters 側でも同じ最適化が行われています。ただし、Parameters では各階層で `to_unsafe_h` を挟むため、効果は小さい（≒オーバーヘッドが相対的に大きい）ことが説明されています。

`deep_transform_values` はもともと `transform_values` を使っており、こうしたペア配列は作っていないため今回の対象外です。

### 性能改善の具体的な数字

JSON:API っぽいサンプル（キー 66 個、深さ 5）の計測結果（Ruby 4.x 各種 JIT 含む）では、オブジェクト割り当て数と i/s が次のように変化しています（一部抜粋）:

- `deep_symbolize_keys`
  - オブジェクト数: 92 → 26
  - スループット:
    - Ruby 4.0.9 (no JIT): 95.7k i/s → 133.8k i/s (1.40x)
    - Ruby 4.0.9 (YJIT): 162.8k i/s → 241.2k i/s (1.48x)
    - Ruby 4.1.0-preview1 (ZJIT): 132.5k i/s → 188.6k i/s (1.42x)
- `deep_stringify_keys`
  - オブジェクト数: 92 → 26
  - スループットも同程度の倍率で向上 (1.37〜1.47x 程度)
- `deep_transform_keys { ... }`
  - オブジェクト数: 230 → 164
  - 1.18〜1.31x ほどの改善

`Parameters#deep_transform_keys` も 1.08〜1.11x 程度の改善がありますが、前述の通り、`Parameters` 固有のオーバーヘッドが効いて劇的ではありません。

また、`Hash` / `HashWithIndifferentAccess` / `Parameters` に対して、ランダムにネストした 5,000 個のハッシュ（配列混在・キー衝突も含む）に同じ処理を走らせ、以下を比較して「完全一致」であることを確認済みです。

- 結果オブジェクトのクラス
- キー順序
- 値

---

3. 影響範囲・注意点

**影響範囲**

- `ActiveSupport`:
  - `Hash#deep_symbolize_keys`
  - `Hash#deep_stringify_keys`
  - `Hash#deep_transform_keys` とその内部実装 `_deep_transform_keys_in_object`
  - `HashWithIndifferentAccess` に対しても、同じ実装経由で効果あり
- `ActionPack` / `ActionController`:
  - `ActionController::Parameters#deep_transform_keys`  
    → Strong Parameters でパラメータキーを書き換えるケース（`underscore` したり、camelCase 変換したり）に影響

**動作上の挙動**

- 変更前後で:
  - 返ってくるオブジェクトの型
  - キーの順序
  - 同じキーに変換されたときの「最後の値が勝つ（last-wins）」ルール
- は明示的に変えないことが保証されています（広範な比較検証済み）。

そのため、アプリケーションレベルでは「速度とメモリが良くなっただけ」で、既存のコードを変更する必要はありません。

**注意点**

- 公開 API のシグネチャや例外挙動は変わっていませんが、もしアプリ内で `deep_transform_keys` の挙動に依存した繊細な処理（キー衝突順序や `HashWithIndifferentAccess` のクラスなど）をしているなら、念のため既存テストを一通り流しておくと安心です。
- `ActionController::Parameters` では効果は限定的ですが、大量パラメータを扱う API・大きな JSON ボディを受け取るエンドポイントでは、レスポンスタイムや GC 圧が多少軽くなる可能性があります。

## [#59461](https://github.com/rails/rails/pull/59461) Expose the untouched association name to restrict_with_error messages {#pr-59461}

**マージ日**: 2026/10/31 | **作成者**: [@jasonmaxlee](https://github.com/jasonmaxlee)

1. 概要 (1-2文で)  
`dependent: :restrict_with_error` のエラーメッセージに、従来の `%{record}` に加えてオリジナルの大文字・小文字を保持した `%{association_name}` を渡すようにし、多言語対応（特に名詞を大文字で書く言語）で正しい表記ができるようにした変更です。既存の英語訳などの挙動はそのまま維持されます。

---

2. 変更内容の詳細  

### これまでの問題点

`dependent: :restrict_with_error` を使ったときのエラーメッセージは、I18n で `restrict_dependent_destroy` というキーを使って生成されます。その際、関連名の human 名を `%{record}` として渡していますが、内部で必ず `downcase` されていました。

- 英語圏では  
  - モデル側: `has_many :companies, dependent: :restrict_with_error`  
  - エラーメッセージ: `"Cannot delete client because dependent companies exist"`  
  のような感じで、「companies」を小文字にしたいケースが多く、`downcase` は都合がよかった。
- しかし、ドイツ語など「名詞は先頭大文字」が文法の言語では  
  - 翻訳例: `companies` → `"Firmen"`  
  - `downcase` されると `"firmen"` となり、文法的に誤りになる。
- さらに、`%{record}` にはすでに小文字化された値しか渡されないため、「元の大文字・小文字」を翻訳側で復元することは不可能だった。

一方で、単に `downcase` をやめると、英語アプリで「ラベルとして」大文字書きされた翻訳（例: `"Client companies"`）がそのまま文中に出てしまい、「… because Client companies exist」のような不自然な文章になるアプリが壊れてしまいます。

### 今回の変更点

この PR では、互換性を保ちつつ他言語での制御性を上げるために、次のようにしました。

- `has_many` / `has_one` それぞれの `restrict_with_error` ロジックで:
  - これまでどおり `%{record}` には「小文字化された human 名」を渡す（**既存挙動維持**）
  - 追加で `%{association_name}` に「小文字化していない元の human 名」を渡す（**新しい補助キー**）

これにより:

- 既存の I18n エントリで `%{record}` を使っている英語アプリは、挙動一切変更なし。
- ドイツ語など、大文字を維持したいロケールでは、翻訳側で `%{association_name}` を使うように変更することで正しい表記が可能になる。

#### 具体例

従来 (英語想定のまま):

```yml
# config/locales/en.yml
en:
  errors:
    messages:
      restrict_dependent_destroy:
        has_many: "Cannot delete record because dependent %{record} exist"
        has_one:  "Cannot delete record because a dependent %{record} exists"
```

このままでも挙動は変わりません。`%{record}` には今までどおり downcase 済みの名前が入ります。

ドイツ語などで今回の変更を活かす例:

```yml
# config/locales/de.yml
de:
  errors:
    messages:
      restrict_dependent_destroy:
        has_many: "Datensatz kann nicht gelöscht werden, da abhängige %{association_name} existieren"
        has_one:  "Datensatz kann nicht gelöscht werden, da ein abhängiges %{association_name} existiert"
```

- モデル:

```ruby
class User < ApplicationRecord
  has_many :companies, dependent: :restrict_with_error
end
```

- ドイツ語の翻訳で `companies` → `"Firmen"` としている場合、
  - `%{record}` を使うと `"firmen"`（小文字化）になってしまう
  - `%{association_name}` を使えば `"Firmen"` のまま使える

この PR によって `%{association_name}` が補助的に使えるようになり、ドイツ語側のメッセージを大文字のまま書けるようになります。

### コード上の変更点 (概略)

`has_many_association.rb` / `has_one_association.rb` において、`restrict_with_error` 実行時に I18n へ渡すオプションハッシュに `association_name:` を追加した、というシンプルな変更です。

イメージとしては:

```ruby
# （擬似コード・実際とは多少異なります）
errors.add(:base, :restrict_dependent_destroy,
  record:            association_name.downcase, # 既存
  association_name:  association_name           # 新規
)
```

テスト:

- `has_many_associations_test.rb` / `has_one_associations_test.rb` にそれぞれ 1 テストずつ追加
  - ドイツ語メッセージ内で `%{association_name}` を利用するケースを追加
  - 変更前は:
    - `%{association_name}` が存在しないため `I18n::MissingInterpolationArgument` が発生
    - あるいは `%{record}` 経由だと `"firmen"`, `"konto"` のように小文字化される
  - 変更後は:
    - エラーなく `%{association_name}` が補間され
    - 翻訳側が意図した大文字表記が保たれる  
 既存の `test_restrict_with_error*` 系テストは変更なし・全てパス。

`activerecord/CHANGELOG.md` にも、この新しい補間キー追加についてのエントリが追記されています。

---

3. 影響範囲・注意点  

- 互換性:
  - `%{record}` の意味・値は変わっていないため、**既存アプリのメッセージはそのまま**動作します。
  - 新規に `%{association_name}` が追加されただけの**後方互換な変更**です。
- ロケールファイルの修正方針:
  - 英語ロケール:
    - ほとんどのケースで今までどおり `%{record}` を使い続けて問題ありません。
    - ラベル的に「Client companies」のように大文字混じりで翻訳している場合、`%{record}` に依存しているときは従来通り小文字化された形で出力されます（挙動は変えないため）。
  - ドイツ語など大文字小文字が意味を持つ言語:
    - `restrict_dependent_destroy` のメッセージを `%{record}` から `%{association_name}` に変更することで、正しい大文字表記を維持できます。
- もし自前で `restrict_dependent_destroy` メッセージをオーバーライドしていて、かつ `%{association_name}` というプレースホルダをすでに別用途で使っている場合は、今回から Active Record が同名のキーを渡すようになる点に注意が必要です（通常はそのような使い方はしていないはずですが、名前衝突の可能性としてはあり得ます）。

- 対応 Issue: https://github.com/rails/rails/issues/21064

  - `errors.messages.restrict_dependent_destroy.has_many`

- 実際にこの変更を活かすには、`config/locales/*.yml` 内で `%{association_name}` を使うよう翻訳を更新する必要があります。

## [#59462](https://github.com/rails/rails/pull/59462) Pass associations added to a parent down to existing subclasses {#pr-59462}

**マージ日**: 2026/10/31 | **作成者**: [@jasonmaxlee](https://github.com/jasonmaxlee)

1. 概要 (1-2文で)  
Active Record の関連定義（`has_many` など）を親クラスに「後から」追加した場合でも、その親クラスを継承したサブクラスに正しく伝播するようにしたバグ修正です。エンジン／Concern／再オープンしたクラスで親に関連を追加したとき、既存サブクラスで関連メソッドはあるのに `AssociationNotFoundError` が出る問題を解消します。

---

2. 変更内容の詳細  

### 問題の背景

従来の挙動:

```ruby
class Post < ActiveRecord::Base; end

class FancyPost < Post
  has_many :tags
end

# 後から親に関連を追加
Post.has_many :comments

FancyPost.first.comments
# => ActiveRecord::AssociationNotFoundError
# "FancyPost には 'comments' という関連が見つからない"
```

なぜこうなるか:

- 各モデルは `_reflections` というハッシュで関連情報を保持している
- `add_reflection`（`has_many` などが内部的に使う処理）は、
  - 「関連を定義したクラス」に対して **新しい frozen な `_reflections` ハッシュを書き込む**
- `FancyPost` が `has_many :tags` を定義した時点で、`Post` の `_reflections` をコピーした **自前の `_reflections` ハッシュ** を持つようになる
- その後で `Post.has_many :comments` を呼ぶと:
  - `Post` の `_reflections` は更新される
  - しかし `FancyPost` は自前で持っているコピーを更新しないため、`comments` の Reflection を知らない
- さらに、`normalized_reflections`（Reflection のキャッシュ）もサブクラス側で一度読まれると、親に変更があってもキャッシュが更新されないケースがある

結果として、「親クラスに後から追加した関連」がサブクラスに見えず、例外になるというバグが起きていました。

### PR で行ったこと

`ActiveRecord::Reflection.add_reflection` の挙動を変更して、**親クラスに関連を追加したときに、既存のサブクラスにもその情報を適切に反映する**ようにしました。

具体的には:

1. 親クラスに Reflection（関連）が追加されたあと、
   - そのクラスの `descendants`（すべての子孫クラス）を辿る

2. 各子孫クラスに対して:
   - まず、そのクラスの Reflection キャッシュ（`normalized_reflections` など）をクリアする  
     → 親クラスの変更を正しく反映させるため
   - その子孫クラスが「自分専用の `_reflections` ハッシュ」を持っているかを確認
     - 持っていない（= 親から継承のみしている）場合:
       - キャッシュだけクリアして終了。後で参照するときに、親から正しく継承される
     - 自分専用の `_reflections` を持っている場合:
       - 「同じ名前の関連を自分（または間のクラス）がオーバーライドしていないか」を確認
       - オーバーライドがなければ、**親に追加された Reflection を、その子孫クラスの `_reflections` にも追加**
       - もし同名の関連がすでに子孫側で定義されていれば、**そちらを優先して上書きしない**

これにより、

- 後から親に追加された関連が、
  - 独自の関連を持つサブクラス
  - その孫クラス
  にも正しく見えるようになる
- ただし、サブクラス側で明示的に同名の関連を定義している場合は、これまで通りサブクラスの定義が優先される

### テストで確認していること

`activerecord/test/cases/reflection_test.rb` に追加されたテストで以下を保証:

1. **サブクラスが自前の関連を一つ持っている場合**
   - 親に後から追加した関連もサブクラスで利用できる
   - サブクラスから親の関連を使ったとき、正しくサブクラス用の行（例: `fancy_posts` の `comments`）だけをロードする

2. **孫クラス（子の子）でも同様に動く**

3. **サブクラスが親の Reflection を一度読んでキャッシュしている場合でも**
   - 親に後から追加した関連が見えるようになる（キャッシュが正しくクリアされる）

4. **サブクラスが同じ名前の関連をオーバーライドしている場合**
   - これまで通りサブクラス側の関連定義が保持される（親の新しい関連で上書きしない）

1〜3 は本 PR 前は失敗していたが、変更後はパスするようになったことが示されています。4 は前後で挙動に変化なし。

さらに、この変更を入れた状態で Active Record SQLite のフルテストスイートがパスしていることも記載されています。

3. 影響範囲・注意点  

### 影響範囲

- 対象:
  - Active Record を使った STI/継承モデル全般
  - 特に、**親クラスより先にサブクラスがロード・定義され、その後に親クラスへ関連が追加される**ようなケース
    - Rails Engine が親モデルに関連を追加する
    - Concern を `include` することで親クラスに `has_many` 等が後から乗る
    - クラス再オープン（`class Post < ApplicationRecord; end` を複数ファイルで定義）で関連を追加する

- これまで:
  - 「メソッドは生えているのに、呼ぶと `AssociationNotFoundError`」のような微妙な不整合が起き得た
- これから:
  - 親に後付けした関連が、既に存在するサブクラスにも一貫して伝播する

### パフォーマンス面

- `descendants` の走査は:
  - **サブクラスが既に存在する状態で関連を追加したときに限り**実行される
  - 通常の「親クラス → その後でサブクラスを定義 → 親に関連を追加しない」という多くのケースでは `descendants` は空で、余計な仕事は発生しない
- 関連定義 (`has_many` など) 自体はそこまで頻繁に実行されるものではないため、実運用への影響は限定的と考えられます

### 互換性・注意点

- サブクラスが同名の関連を明示的に定義している場合は、**今まで通りサブクラスの定義が優先される**  
  → 挙動が変わるのは「親にだけ定義された関連」がサブクラスに見える／見えないの差分のみ
- もしアプリ側で `_reflections` や `normalized_reflections` を直接触っているような高度なメタプログラミングをしている場合は、この変更で挙動がより一貫する方向に揃えられますが、念のため挙動確認をした方が安全です
