## [#58917](https://github.com/rails/rails/pull/58917) Remove dead code for Ruby &lt; 3.3.1 {#pr-58917}

**マージ日**: 2026/10/1 | **作成者**: [@hmcguire-shopify](https://github.com/hmcguire-shopify)

1. 概要 (1-2文で)  
Rubyのサポート下限バージョンが 3.3.1 になったことを前提に、`Time` 計算まわりで「Ruby 3.3.1 未満向けのワークアラウンド（死んだコード）」を削除したPRです。テストは 3.3.1 以降の動作確認として有用なため、そのまま維持されています。

---

2. 変更内容の詳細  

対象ファイル:  
- `activesupport/lib/active_support/core_ext/time/calculations.rb`（7行削除、追加なし）

内容としては、以前 Ruby 3.3.0 までの不具合や仕様差を吸収するために入っていた条件分岐・ワークアラウンドが削除されています。

背景となる流れ:
- 過去PR（例: #52347, #57028）で Ruby 3.3 系の挙動差への対応が入っていた。
- 2024年3月のコミット（`a9ed6377...`）で Rails 自体の「サポートする Ruby の最小バージョン」が 3.3.1 に引き上げられた。
- その結果、「Ruby &lt; 3.3.1 でのみ必要な回避コード」は実行されることがなくなり、「死んだコード (dead code)」になっていたため削除。

コードイメージ（あくまで概念的な例）:

```ruby
# 以前（イメージ）
if RUBY_VERSION < "3.3.1"
  # 古い Ruby のバグ／挙動差を補正するコード
  def some_time_calculation(...)
    # workaround
  end
else
  # Ruby 3.3.1+ 向けの本来の実装
  def some_time_calculation(...)
    # normal path
  end
end

# 今回のPR後
def some_time_calculation(...)
  # Ruby 3.3.1+ を前提にした実装のみ
end
```

実際の変更は 7 行削除のみで、API 仕様やメソッド名が変わっているわけではなく、「条件分岐・古いバージョン向けの特別な処理」がなくなっただけです。

また、このワークアラウンド追加時に入れられたテストは、「Ruby 3.3.1 以降で期待する動作が正しく行われているか」を保証する意味があるため、今回も残されています。

---

3. 影響範囲・注意点  

- 対象バージョン:
  - Rails が公式にサポートする Ruby の最小バージョンが 3.3.1 のため、それより古い Ruby を使っているプロジェクトは、そもそもサポート対象外です。
  - したがって「正式サポート範囲内での互換性破壊」はありません。

- 影響範囲:
  - `ActiveSupport` の `Time`/`DateTime` 周辺計算（`time/calculations`）が関係しますが、実質的には「今まで 3.3.1+ で実行されていたコードが、そのまま唯一のコードパスになる」だけです。
  - Ruby 3.3.1 以降で Rails を使っている限り、挙動変更はなく、テストもすでにその前提で書かれています。

- 注意点:
  - 古い Ruby（3.3.0 以前）上で「無理やり」この Rails バージョンを動かしている場合:
    - 以前はワークアラウンドでたまたま動いていた箇所が、今回の削除により `Time` 計算まわりでバグったり、微妙に違う挙動になる可能性があります。
    - ただし Rails コアとしてはそのケースはサポートしない前提です。Ruby を 3.3.1 以上に上げるのが正しい対応になります。

## [#58908](https://github.com/rails/rails/pull/58908) Bump minimum Ruby version to 3.3.5 {#pr-58908}

**マージ日**: 2026/10/1 | **作成者**: [@hmcguire-shopify](https://github.com/hmcguire-shopify)

1. 概要 (1-2文で)  
Rails がサポートする最低 Ruby バージョンを 3.3.5 に引き上げる PR です。  
これにより、Weak{Key,}Map の use-after-free バグを前提にした独自ポリフィルを廃止でき、今後 Active Record のクエリキャッシュ周りをより効率的にリファクタリングできるようにする意図があります。

---

2. 変更内容の詳細  

### 2-1. どんなバグが背景にあるか

- Ruby 3.3.5 未満の WeakMap / WeakKeyMap 実装に use-after-free バグがある  
- このバグは「比較的遭遇しやすい」とされており、安全に WeakKeyMap を使えない
- そのため Rails 側では、WeakKeyMap をそのまま使うのではなく「ポリフィル (代替実装＋ラッパ)」を用意して、利用可能なキー種別を制限していました。

制限の具体例:
- WeakKeyMap のキーにできるのは `Thread` / `Fiber` など、`respond_to?(:alive?)` なオブジェクトだけ  
- つまり、任意オブジェクトを弱参照キーに使うことができず、設計の自由度が落ちていた

### 2-2. 最低 Ruby バージョンを 3.3.5 に上げる目的

PR 作成者のアプリケーションでは、**クエリキャッシュのクリア処理が CPU を食っている**という問題があります。

現在の実装イメージ:

- 各 DB 接続プールが、クエリキャッシュを「現在の実行コンテキスト (Thread/Fiber)」ごとに持っている  
- 「このコンテキストに紐づくキャッシュをクリアしたい」ときに、
  - **全ての connection pool を走査し、その pool 内の「現在の実行コンテキスト用キャッシュ」を消す**
  - → 利用していないプールも含めて毎回全プールを舐めるため、CPU コストが高い

理想の方向性:

- データ構造を「コンテキスト → そのコンテキストで使った connection pool の集合」に**反転**したい
  - いま: `pool -> { context -> cache }`
  - 目標: `context -> { pool -> cache }`
- こうすれば、「現在のコンテキストに紐づくプールだけ」を辿ればよく、**総プール数ではなく、そのコンテキストで実際に使ったプール数だけを走査すればよい**  
  → パフォーマンスが大幅に改善する見込み

この「構造の反転」には、connection pool オブジェクトを WeakKeyMap のキーとして安全に使えることが前提になります。しかし、現状のポリフィルは「Thread / Fiber など `alive?` を持つものしかキーにできない」ため、connection pool をキーにできません。

そこで:

- Ruby 側の WeakKeyMap 実装バグが修正されている 3.3.5 以降を必須にする
- そうすれば、Rails 側の WeakKeyMap ポリフィルを削除し、**任意オブジェクト (例: connection pool)** を WeakKeyMap のキーとして使えるようになる
- その結果として、上記のクエリキャッシュ構造のリファクタリングが可能になる

この PR 自体は「最低バージョンを引き上げるだけ」で、WeakKeyMap ポリフィル削除やクエリキャッシュの実装変更は「後続 PR で行う」と明言されています。

### 2-3. 実際の差分の内容

変更されているのは主に gemspec とガイドのバージョン宣言です。

代表的な変更例 (概念的なイメージ):


コードロジックの変更はなく、あくまで「サポートする Ruby の下限バージョンを宣言上引き上げる」だけの PR です。

---

3. 影響範囲・注意点  

### 3-1. Rails 利用者側への影響

- Rails の次バージョン (この PR が入るバージョン) を使う場合、
  - Ruby 3.3.4 以下では動作対象外になります
  - CI / 本番環境ともに Ruby 3.3.5 以上に上げておく必要があります
- Gem の依存チェック (`required_ruby_version`) によって、古い Ruby では bundle install 自体が失敗するようになります

移行時のチェックリスト:

- `ruby -v` が 3.3.5 以上であることを本番 / 開発 / CI すべてで確認
- `.ruby-version` や `Gemfile` の `ruby "x.y.z"` 指定を 3.3.5 以上に変更
- 使用している他の gem が Ruby 3.3.5 に対応しているかどうかを確認
  - 特に C 拡張を含む gem (例: nokogiri, grpc, mysql2, pg など) は Ruby のマイナーバージョンアップでビルドし直しが必要な場合があります

### 3-2. 内部実装・今後の変更に関する影響

この PR の目的は「将来的なリファクタリングの前提条件づくり」です。  
今後想定される変更:

- WeakKeyMap ポリフィルが削除される
  - これにより、WeakKeyMap のキーとして使えるオブジェクトの種類が制限されなくなる
- Active Record のクエリキャッシュ実装が変更される
  - 「全 connection pool を走査して現在コンテキストのキャッシュを消す」方式から、
  - 「現在コンテキストに紐づいている pool のみを辿る」方式へと変更される見込み
- 結果として、
  - マルチ DB / マルチテナントなどで connection pool が多い環境ほど、
  - クエリキャッシュクリア時の CPU 使用量が下がる可能性が高い

ライブラリ作者視点の注意点:

- Rails 内部の WeakKeyMap 仕様に依存していた「ポリフィル前提の挙動」が、将来的に変わる可能性がある
- ただし通常のアプリケーションコードから WeakKeyMap を直接触ることは稀なので、影響を受けるのは主に Rails の拡張・プラグインを書いているような層に限られると考えられます

## [#58898](https://github.com/rails/rails/pull/58898) Avoid reprocessing ActiveRecord::Result column names {#pr-58898}

**マージ日**: 2026/10/1 | **作成者**: [@dersam](https://github.com/dersam)

1. 概要 (1-2文で)  
ActiveRecord::Result が内部で「カラム名の再処理（主に String の intern / freeze）」を行うのをやめ、DBアダプタ側での処理に一元化したパフォーマンス改善のPRです。  
これにより、不要な文字列オブジェクトの割り当てを避けつつ、カラム名配列は引き続き freeze される形になります。

---

2. 変更内容の詳細  

### 何をしているか

- `ActiveRecord::Result` 内で、カラム名 (`@columns`) に対して行っていた「都度 each で回して変換・加工する処理」を削除
- 代わりに、アダプタ（MySQL, SQLite, PostgreSQL など）の段階で文字列の intern などを済ませる前提に変更
- `ActiveRecord::Result` 側では、カラム名の配列を受け取ったあとに
  - 追加の処理は行わず
  - 配列自体を `freeze` するだけに簡略化

PR本文中のポイント:
- 「String interning is now handled in the database adapters」  
  → 文字列のインターン（同一内容の文字列を共有してメモリ節約・比較高速化する仕組み）がアダプタ側で完結する設計に統一
- 「Doing it in the adapters allows us to skip allocations that happen with the `each` version」  
  → `Result` 生成時に Ruby 側で `each` を回しながら `intern` / `freeze` などをしていた分のオブジェクト割り当てを削減
- 「We can now remove this and only freeze the array」  
  → ActiveRecord 本体では、配列の不変性だけを保証し、要素（カラム名文字列）の処理は行わない方針

### コード上のイメージ

実際の差分は1行追加・3行削除程度ですが、イメージとしては:

```ruby
# 変更前（イメージ）
def initialize(columns, rows)
  @columns = columns.map { |c| c.to_s.freeze } # / intern など
  @columns.freeze
  @rows = rows
end

# 変更後（イメージ）
def initialize(columns, rows)
  @columns = columns.freeze # 中身の文字列はアダプタ側ですでに処理済み前提
  @rows = rows
end
```

※実際のコードとは多少異なる可能性がありますが、意図としてはこのような「Result 側で列名をあれこれ加工しない」方向への簡略化です。

---

3. 影響範囲・注意点  

- **対象:**  
  - ActiveRecord を通じて DB クエリを発行し、その結果を `ActiveRecord::Result` として扱う全機能（低レベル API を含む）
- **実質的な振る舞いの変更:**  
  - 結果としてのカラム名が frozen である点は維持される想定
  - 文字列の intern など、メモリ・パフォーマンスに関わる処理がアダプタ側に完全移譲される
- **開発者が意識すべき点:**
  - 通常の AR モデル利用 (`User.select(...)` など) では、API 的な挙動は変わらないはずで、明示的な対応は不要
  - 自前でアダプタを拡張・実装している場合:
    - カラム名の文字列処理（`intern`, `freeze` など）をアダプタ側で責任を持って行う必要がある  
    - それをしていないと、Result のカラム名が想定より多くメモリを消費したり、GC 負荷が上がる可能性がある
  - 低レベルで `ActiveRecord::Result` を直接生成しているコードがあり、その中で「Result 側でカラム名を加工してくれる前提」に依存していた場合は挙動が変わる（ただし、そのような利用はかなりニッチ）

- **後方互換性のリスク:**
  - 公式にサポートされる通常の利用パターンでは、仕様変更というよりは実装の最適化に近く、互換性リスクは低い
  - ただし、カラム名オブジェクトの「同一性（`object_id`）」までテストしているようなコードがあると、intern のタイミング変更によってテストが不安定になる可能性は理論上ある

---

4. 参考情報 (あれば)  

- 関連 PR: [#58803](https://github.com/rails/rails/pull/58803)  
  - こちらで「文字列の intern をアダプタ側で行う」方針の議論・実装が進められており、今回の PR はその仕上げとして ActiveRecord::Result 側の重複処理を削除した位置づけです。
- ActiveRecord::Result の役割:
  - AR が SELECT などを発行した結果を、行列ベースの汎用的なコンテナとして表現するクラス
  - カラム名 (`columns`) と行データ (`rows`) を管理し、モデルにマッピングされる前段階の構造を担っているため、ここでのオブジェクト削減はクエリ全般のパフォーマンスに効きやすい箇所です。

## [#58892](https://github.com/rails/rails/pull/58892) Fix input `id` not matching label `for` when collection value is an empty string {#pr-58892}

**マージ日**: 2026/10/1 | **作成者**: [@55728](https://github.com/55728)

1. 概要 (1-2文で)  
`collection_radio_buttons` / `collection_check_boxes` などで、値が空文字列 `""` のときに生成される `<input>` の `id` と `<label>` の `for` が一致しなくなるバグを修正した PRです。`nil` の場合の修正 (#57209) を拡張し、「サニタイズ結果が空文字列になる値」全般に対して一貫した ID 付与になるようにしています。

---

2. 変更内容の詳細  

### 何が問題だったか

次のようなコードを考えます:

```ruby
collection_radio_buttons :user, :active,
  [["Yes", true], ["Undefined", ""]],
  :last, :first
```

期待されるのは、`value: ""` の要素に対して、`input` と `label` が同じ ID を参照することです。

しかし従来は次のような HTML が生成されていました:

```html
<input type="radio" value="" name="user[active]" id="user_active_" />
<label for="user_active">Undefined</label>
```

- `input` 側の ID: `user_active_`
- `label` 側の for: `user_active`

つまり末尾のアンダースコア `_` の有無が揃っておらず、`label` と `input` が正しく紐付かない状態でした。

背景:

- `label` 側は `sanitize_attribute_name` の結果が空文字列のときは、末尾の `_値` を付けない実装になっていた
- `input` 側（`add_default_name_and_field_for_value`）は、`nil` のときだけ `_値` を付けない挙動になっていた
- そのため「`nil` は OK だが、空文字列 `""` のときに不整合」が起きていた

### どう直したか

`actionview/lib/action_view/helpers/tags/base.rb` の `add_default_name_and_field_for_value` のロジックを変更し、

- 「元の値が `nil` かどうか」ではなく
- 「`sanitize_attribute_name(value)` した結果が空かどうか」

で、`_sanitized_value` を ID/名前に付けるかどうかを判定するようにしました。

これにより:

- `sanitize_attribute_name(value)` が空文字列になる値（`nil` や `""` など）の場合  
  → `user_active`（サフィックスなし）
- それ以外の値の場合  
  → `user_active_true` / `user_active_yes` のようにサフィックス付き

という挙動になります。`label` 側も同じロジックを使うため、常に一致するようになります。

### API レベルで影響を受ける箇所

`add_default_name_and_field_for_value` は次のヘルパから共有利用されています:

- `radio_button`
- `check_box`（`multiple: true` の場合）
- `label`（`value:` を指定した場合）

そのため、コレクション系だけでなく、単体呼び出しでも挙動が変わります。

例:

```ruby
radio_button :user, :active, ""
label :user, :active, value: ""
```

従来:

```html
<input type="radio" value="" name="user[active]" id="user_active_" />
<label for="user_active">...</label> <!-- あるいは for="user_active_" など不一致の可能性 -->
```

修正後:

```html
<input type="radio" value="" name="user[active]" id="user_active" />
<label for="user_active">...</label>
```

### テスト

- `actionview/test/template/form_collections_helper_test.rb` にテストを追加
- `collection_radio_buttons` と `collection_check_boxes` の両方について、値が `""` の場合に `id` / `for` が一致することを確認

---

3. 影響範囲・注意点  

#### 影響範囲

1. `collection_radio_buttons` / `collection_check_boxes` において、コレクションの値が空文字列 `""` の要素  
   → `id` / `for` の末尾から不要な `_` が消え、`user_active_` → `user_active` のように変わります。

2. 次のような単体ヘルパ呼び出しでも同様に ID が変わります:
   - `radio_button :user, :active, ""`
   - `check_box :user, :roles, { multiple: true }, ""`
   - `label :user, :active, value: ""`

3. これにより:
   - スクリーンリーダーやクリックターゲットの挙動が改善（`label` と `input` の紐付きが正しくなる）
   - CSS / JS が `#user_active_` のような古い ID を前提にしている場合は壊れる可能性がある

#### 注意点

- 破壊的変更の範囲は「ID 名が変わる可能性がある」に限定されますが、DOM を直接フックしているコード（テストを含む）があると影響を受けます。
- 既に #57209 を適用済みの Rails 8.1 系で、空文字列値を使っているフォームを持つアプリは、この PR で ID が「より一貫した形」に揃えられます。  
  → そのぶん不具合修正としての価値は高い一方、DOM 名の変更としては認識しておく必要があります。
- heartcombo/simple_form などフォームビルダーを利用している場合、今回の修正はその上で動くヘルパにも波及します（根本の ID 生成ロジックが変わるため）。

## [#58882](https://github.com/rails/rails/pull/58882) Fix the :validate default in the Association Basics guide [ci skip] {#pr-58882}

**マージ日**: 2026/10/1 | **作成者**: [@ramen2020](https://github.com/ramen2020)

1. 概要 (1-2文で)  
Association Basics ガイドの`:validate`オプションのデフォルト値説明が実装と食い違っていたため、関連の種類ごとに正しいデフォルト挙動が分かるように修正したドキュメント更新PRです。あわせて、`has_and_belongs_to_many` は `:validate` をサポートしないという誤った記述も削除されています。

---

2. 変更内容の詳細(あればサンプルコードも含めて)

### 何が問題だったか

元の Association Basics ガイドでは:

- `:validate` のデフォルトは常に `false`
- `has_and_belongs_to_many` は `:validate` オプションをサポートしない

と読める記述になっていました。

しかし実際の実装 (`ActiveRecord::Reflection#validate?`) は以下のようになっています。

```ruby
def validate?
  if options.key?(:validate)
    options[:validate]
  else
    options[:autosave] == true || collection?
  end
end
```

これを踏まえると:

- `:validate` が明示されていない場合  
  - `collection? == true` であれば `true`  
    → `has_many`, `has_and_belongs_to_many` はデフォルト `true`
  - `collection? == false` かつ `autosave: true` であれば `true`  
    → `has_one autosave: true`, `belongs_to autosave: true` は `true`
  - それ以外は `false`  
    → 通常の `has_one`, `belongs_to` は `false`

また、`has_and_belongs_to_many` は内部的に `has_many` を組み立てる際に `:validate` オプションをそのまま渡しており、`validate: false` なども有効です。

### ガイドへの具体的な修正内容

`:validate` セクションの説明が、次のような趣旨の内容に変更されたと考えられます（意訳）:

- デフォルト値は関連の種類によって異なる:
  - `has_many`, `has_and_belongs_to_many`  
    - デフォルト: `validate: true`
  - `has_one`, `belongs_to`  
    - デフォルト: `validate: false`
    - ただし `autosave: true` を指定した場合は `validate: true` 相当になる
- `has_and_belongs_to_many` では `:validate` が使えない、という記述を削除

PR の説明で示されていた動作確認結果は以下のとおりです（新規に1件の無効な子レコードを親に関連付けて `save` した場合）:

| Association                            | 親の `save` 結果 |
| -------------------------------------- | ---------------- |
| `has_many` (デフォルト)               | `false`  (保存失敗) |
| `has_many validate: false`            | `true`   (保存成功) |
| `has_and_belongs_to_many` (デフォルト)| `false`  (保存失敗) |
| `has_and_belongs_to_many validate: false` | `true` (保存成功) |
| `has_one` (デフォルト)                | `true`   (保存成功) |
| `has_one autosave: true`              | `false`  (保存失敗) |
| `belongs_to` (デフォルト)             | `true`   (保存成功) |
| `belongs_to autosave: true`           | `false`  (保存失敗) |

この挙動に合うようにガイドの文章が4行追加、5行削除で調整されています。

### サンプルコードイメージ

例えば:

```ruby
class Author < ApplicationRecord
  has_many :books              # デフォルトで validate: true
  has_one :profile             # デフォルトで validate: false
  has_one :account, autosave: true  # 実質 validate: true
end

class Book < ApplicationRecord
  belongs_to :author           # デフォルトで validate: false
end
```

- `author.books.build(invalid_attributes)` して `author.save`  
  → `has_many` は `validate: true` なので、`false` (保存失敗)
- `author.build_profile(invalid_attributes)` して `author.save`  
  → `has_one` は `validate: false` なので、`true` (親は保存される)
- `author.build_account(invalid_attributes)` して `author.save`  
  → `autosave: true` なので、`false` (保存失敗)

今回はこのような実際の挙動と整合するようにドキュメントだけが修正されています。

---

3. 影響範囲・注意点

- 影響範囲は **ドキュメントのみ** であり、Rails 本体の挙動・API には一切変更はありません。
- ただし、これまでガイドだけを信じて「`has_many` などでは関連先の検証はデフォルトで走らない」「`has_and_belongs_to_many` では `validate:` は効かない」と思い込んでいた場合、その理解が誤りであったことに注意が必要です。
- 実運用では、次の点を意識すると安全です:
  - 「親保存時に子のバリデーションも必ず走らせたい」  
    → `has_one`, `belongs_to` であれば `autosave: true` か `validate: true` を明示する。
  - 「親は保存したいが、無効な子がいてもかまわない」  
    → `has_many`, `has_and_belongs_to_many` なら `validate: false` を明示する。
- 他のドキュメントやブログ記事に、古い（誤った）説明が残っている可能性があるため、挙動を確認したいときは API ドキュメントかソース（`Reflection#validate?`）を参照するほうが確実です。

---

4. 参考情報 (あれば)

- 該当実装:  
  `ActiveRecord::Reflection#validate?`  
  https://github.com/rails/rails/blob/7d52e0123842/activerecord/lib/active_record/reflection.rb#L741-L742
- API ドキュメント（`:validate` のデフォルトについて正しい説明がある）  
  - `has_many`: デフォルト `validate: true`  
  - `has_and_belongs_to_many`: デフォルト `validate: true`  
  - `has_one`, `belongs_to`: デフォルト `validate: false`（ただし `autosave: true` で実質有効化）

`FormTagHelper` の API ドキュメント中で、`range_field_tag` / `time_field_tag` / `datetime_field_tag` のサンプルコードが実際の出力と食い違っていた問題を修正した PR です。実装の挙動は変えず、「ドキュメント上の例が正しく動く／正しく説明している状態」に揃えています。

---

2. 変更内容の詳細  

### 2-1. `range_field_tag` の例の修正

`range_field_tag` のシグネチャは以下の通りです。

```ruby
def range_field_tag(name, value = nil, options = {})
```

元のドキュメント例では:

```ruby
range_field_tag 'quantity', in: 1...10
```

のように書かれており、この呼び出しは Ruby 的には

```ruby
name   = 'quantity'
value  = { in: 1...10 }  # 第2引数にオプションハッシュが入ってしまう
options = {}
```

となります。そのため、実際の出力は:

```html
<input type="range" name="quantity" id="quantity" value-in="&quot;1...10&quot;" />
```

のように、`in:` オプションが `value-in` という謎属性として出力されていました（本来期待している `min="1" max="9"` にはならない）。

これを修正するため、PR では例を次のように変更しています。

```ruby
range_field_tag("quantity", nil, in: 1...10)
# => <input type="range" name="quantity" id="quantity" min="1" max="9" />

range_field_tag("quantity", nil, min: 1, max: 10, step: 2)
# => <input type="range" name="quantity" id="quantity" min="1" max="10" step="2" />
```

ポイント:

- 第2引数に `nil` を明示的に渡すことで、`in:` / `min:` / `max:` / `step:` が正しく `options` として解釈される。
- 出力 HTML の自己終了タグ `/>` がドキュメントの例から抜けていた箇所も合わせて修正。

これにより、`number_field_tag` のドキュメント例と同じスタイル（`value` を指定しないときは第2引数に `nil`）に統一されています。

### 2-2. `time_field_tag` / `datetime_field_tag` の `:include_seconds` 例を削除

API ドキュメントには、以下のような説明と例がありました（イメージ）:

```ruby
time_field_tag("time", "01:01", include_seconds: true)
# => <input type="time" name="time" id="time" value="01:01:00.000" />
```

しかし実装を見ると、`time_field_tag` / `datetime_field_tag` は単に `text_field_tag` をラップしているだけで、`include_seconds:` オプションを特別扱いしていません。そのため、実際の動作は:

```ruby
time_field_tag("time", "01:01", include_seconds: true)
# => <input type="time" name="time" id="time" value="01:01" include_seconds="true" />
```

のように、`include_seconds` がカスタム属性としてそのまま出力されるだけで、秒付きフォーマット（`01:01:00.000` 等）にはなりません。

PR では、この食い違いを解消するために:

- `time_field_tag` / `datetime_field_tag` のドキュメントから `:include_seconds` オプションに関する記述と例を削除

しています。

あえて実装側に `include_seconds` 対応を追加せず「ドキュメントを実装に合わせる」方向にしたのは、「挙動の変更ではなくドキュメントの修正に留める」という方針によるものです。

## [#58864](https://github.com/rails/rails/pull/58864) Generator tests avoid collisions by using a temporary directory. {#pr-58864}

**マージ日**: 2026/10/1 | **作成者**: [@ChaelCodes](https://github.com/ChaelCodes)

1. 概要 (1-2文で)
Rails のジェネレータ用テストが、テストごとに一時ディレクトリを使うようになり、`tmp/generators` 共有による並列実行時のファイル競合・テストのフレークが解消されました。これに伴い、テスト用の出力ディレクトリの削除タイミングが `setup` から `teardown` に変更されています。

---

2. 変更内容の詳細

### 背景にある問題

従来のジェネレータテストは:

- すべて `tmp/generators` を `destination_root` として使用
- `prepare_destination` が「各テストの `setup` で `destination_root` を削除 → 再作成」

という動きをしていました。

この設計だと:

1. **並列テスト実行時の競合**
   - テストAとテストBが同じ `tmp/generators` を使う
   - テストAの `setup` で `tmp/generators` を削除
   - その直後にテストBが同じディレクトリを前提に動こうとして失敗
   - → テストがフレークする（ときどき落ちる）

2. **同じパスに同名ファイルを生成するテスト同士の競合**
   - 異なるテストケースでも同じ `app/models/post.rb` のようなパスを利用すると、状態が混ざる可能性がある

という問題が起きていました。

### この PR が行ったこと

#### 1. テストごとに一時ディレクトリを使うように変更

- 各テストケース（もしくは各テストメソッド）ごとに、**ユニークな一時ディレクトリ**を `destination_root` として使うように変更しています。
- 実質的には、`Dir.mktmpdir` のような仕組みで都度ランダムなディレクトリを作り、そこでジェネレータを走らせるイメージです。

これにより:

- テスト間で `destination_root` が共有されなくなり、並列実行でも互いの出力を壊さない
- 同じパス・同名ファイルを生成するテストが複数あっても、安全に共存できる

というメリットがあります。

#### 2. `destination_root` の削除タイミングを `teardown` に移動

以前は:

- `setup` 内で `prepare_destination` を呼び、`destination_root`（= `tmp/generators`）を消して作り直していた

今回:

- `destination_root` が一時ディレクトリになり、テスト開始後にランダムに決まる
- テスト完了後にそのディレクトリをクリーンアップ（削除）する必要がある
- しかし「どのディレクトリ名か」はテスト実行中にしか分からないため、**削除処理を `teardown` 側に移動**しています

つまり:

- `setup`: 一時ディレクトリを作成し、それを `destination_root` にセット
- テスト本体: そのディレクトリ配下にジェネレータがファイルを生成
- `teardown`: 使い終わった一時ディレクトリを削除

というライフサイクルに変わりました。

#### 3. ジェネレータ用テストテンプレートの更新

変更ファイルに `generator_test.rb.tt` が含まれていることから:

- `rails g generator Foo` などで作られる **ジェネレータ用テストのテンプレート**も、この新方式に追従するよう修正されています。
- これにより、新しく作成されるジェネレータテストも、はじめから「テストごとに一時ディレクトリを使う」形になります。

#### 4. `testing/behavior.rb` の調整

`Rails::Generators::Testing::Behavior` モジュール内の `prepare_destination` 周りが:

- グローバルな `tmp/generators` を初期化する挙動から
- 一時ディレクトリベースの `destination_root` と協調する挙動へ

と変更されています。行数的には +4/-2 と小さな差分ですが、責務の位置づけ（いつ・どこで消すか）が変わっています。

---

## [#58893](https://github.com/rails/rails/pull/58893) Remove support for dynamic controller/action in routes {#pr-58893}

**マージ日**: 2026/9/30 | **作成者**: [@tenderlove](https://github.com/tenderlove)

1. 概要 (1–2文で)  
このPRでは、Railsのルーティングから「URLパラメータから `:controller` や `:action` を動的に読み取る」仕組みが完全に削除されました。Rails 5.0 から非推奨だった `get ":controller(/:action(/:id))"` 形式などが今後はエラーとなり、コントローラとアクションを明示的に指定する書き方へ移行する必要があります。

---

2. 変更内容の詳細

### 2-1. 動的 `:controller` / `:action` ルーティングの完全削除

以下のような「URLの一部をそのままコントローラ名・アクション名として解決する」ルート定義は、**もはや利用できず `ArgumentError` を投げる**ようになりました。

```ruby
# これまでは動いていたが、今後は ArgumentError
get ":controller(/:action(/:id))"
get ":controller/:action"
```

これらは Rails 5.0 から非推奨 (deprecation) になっていて、「今まで警告は出ていたが動いていたもの」が、今回のPRで**実際に削除**されています。

#### 推奨される書き換え

従来:

```ruby
get ":controller(/:action(/:id))"
# /photos -> PhotosController#index
# /photos/1 -> PhotosController#show (慣習で)
```

今後:

```ruby
get "photos",     to: "photos#index"
get "photos/:id", to: "photos#show"
```

- どの URL がどのコントローラ#アクションに対応するかを**ルート定義側で明示**するのが前提になります。
- 暗黙的にアクション名を推測したり、URLの文字列をそのままクラスやメソッドにマッピングする仕組みは消えます。

### 2-2. コントローラクラスを直接渡す書き方の変更

従来は、`to:` にコントローラクラスだけを渡すと、「動的アクション解決」と同じ仕組みに依存してアクションが補完される動作がありました。

```ruby
# 以前: 暗黙に #show などを解決していたケースがある
get "show", to: PhotosController
```

この挙動は、内部的には「動的な controller/action 解決」と同じパスに乗っていたため、今回の削除に巻き込まれています。

今後は**アクションを明示的に指定**する必要があります:

```ruby
get "show", to: PhotosController, action: "show"
# または
get "show", to: "photos#show"
```

### 2-3. `:controller` / `:action` に対する `Regexp` の扱い変更

`:controller` や `:action` に `Regexp` 制約を付けていたようなルートは、もはや **マッチし得ないルートとして即座にエラーを投げる**ようになりました。

例:

```ruby
# これまでは「どうせマッチしないルート」が定義できてしまっていたケース
get ":controller/:action", controller: /admin_.+/
```

このような「ダイナミック controller/action 前提の正規表現制約」は、そもそも今回の削除で意味をなさなくなったため、**ルート定義時点でエラーとして弾く**ように変更されています。

### 2-4. 内部実装レベルでの主な変更ポイント

高レベルにまとめると:

- `ActionDispatch::Routing::Mapper`  
  - `:controller` / `:action` を動的に解決するパス (デフォルトルーティング、レガシーな auto-routing) が削除。
  - ルート定義時に `dynamic controller/action` を検出して `ArgumentError` を上げる処理が追加。
- `ActionDispatch::Routing::RouteSet` および `Journey` 関連 (`formatter.rb`, `visitors.rb`)  
  - URL生成・パス解析の際にコントローラ/アクションを URL から補完するロジックが整理・削除。
- `ActionDispatch::Http::Request`  
  - リクエストオブジェクトが params から controller/action を「後付けで決める」ようなコードが削除され、ルートが決めた値を前提とする形に単純化。
- 各種テスト (`actionpack/test/controller/...` など)  
  - 旧来の `get ":controller(/:action(/:id))"` に依存したテストが軒並み削除/書き換え。
  - 代わりに、明示的な `to: "photos#show"` スタイルのルータに合わせてテストが修正。

コード全体としては、古い「マジックなルーティングパス」を削ぎ落とし、ルーティング → params → コントローラの流れをより単純・明示的にする変更になっています。

---

3. 影響範囲・注意点

### 3-1. 既存アプリのルーティングエラー

以下に当てはまるアプリは、Rails をこのバージョンに上げた瞬間から **起動時または最初のリクエスト時に `ArgumentError`** となる可能性が高いです。

- `config/routes.rb` に次のようなエントリが残っている:

```ruby
get ":controller(/:action(/:id))"
get ":controller/:action/:id"
match ":controller(/:action(/:id))", via: :all
```

- `resources` を使わず、上記のような「catch-all」なルーティングに頼っている古いアプリ。

対応方針:

1. 該当パターンを**全削除またはコメントアウト**。
2. 実際に必要なエンドポイントごとに、明示的なルートを定義し直す:

   ```ruby
   # NG (削除対象)
   get ":controller(/:action(/:id))"

   # OK (明示的に書く)
   resources :photos  # index/show/create/... が生成される
   get "dashboard", to: "admin/dashboard#index"
   ```

3. 既存の URL が多く、後方互換を保ちたい場合は、
   - `resources` + `member/collection` ルート
   - `scope` / `namespace` を活用してパターンをまとめる
   などで段階的に整理していくのが現実的です。

### 3-2. コントローラクラスを `to:` に渡しているルート

以下のようなコードがある場合:

```ruby
get "show", to: PhotosController
```

今後は**必ず `action:` を付与**してください:

```ruby
get "show", to: PhotosController, action: "show"
# もしくは
get "show", to: "photos#show"
```

`to: SomeController` を使うパターンはそれ自体あまり一般的ではありませんが、エンジンや internal DSL で使っている場合は注意が必要です。

### 3-3. メタプログラミング的なルーティング生成

以下のような「ループで `:controller` を動的に入れ替えつつルートを量産する」ようなメタプログラミングをしていた場合も、根本的な見直しが必要です。

```ruby
# 例: 動的 controller 名をパラメータで受けていたようなケース
%w[photos posts].each do |name|
  get "#{name}/:action", controller: name
end
```

- URL の一部をそのままクラス名等にマッピングする発想自体が危険・非推奨とみなされており、今回のPRで明確に締め出されています。
- 必要なら `resources :photos`, `resources :posts` などに展開し、アクションを列挙する形が推奨されます。

---

4. 参考情報

- この機能は **Rails 5.0 で depreciation notice が出ていた**もので、Rails 6, 7 系を経てついに削除に至った、という位置づけです。
- 公式ガイドのルーティングのベストプラクティス:
  - Rails Guides: Routing from the Outside In  
    https://guides.rubyonrails.org/routing.html  
    → `resources`, `namespace`, `scope`, `match` などを使った「明示的ルーティング」の考え方が整理されています。
- 変更内容は `actionpack/CHANGELOG.md` にも記載されており、「動的コントローラ/アクションルートの削除」が明示的な breaking change として扱われています。

このPRの本質は、「暗黙的で危険な自動マッピング」をやめて、**コントローラ/アクションはルートで明示する**という Rails の現在の設計方針をより徹底するものと理解すると良いです。

## [#58905](https://github.com/rails/rails/pull/58905) Lazy call_arg inspection for attribute methods {#pr-58905}

**マージ日**: 2026/9/30 | **作成者**: [@hmcguire-shopify](https://github.com/hmcguire-shopify)

1. 概要 (1-2文で)  
`ActiveModel::AttributeMethods` 内で、属性メソッド生成時の `call_args` の `inspect` 呼び出しを「必要になった時だけ実行する」ように変更し、無駄な String オブジェクトの生成を減らすパフォーマンス改善です。モデル × カラム × 属性メソッドごとに発生していた余計な文字列割り当てが、ほとんどのケースで発生しなくなります。

---

2. 変更内容の詳細  

### これまでの動作
`ActiveModel::AttributeMethods` は、未定義メソッド呼び出し時などに、`call_args` を元にエラーメッセージやデバッグ情報を組み立てることがあります。その過程で、次のような形で引数を一括で `inspect` 化していました:

```ruby
call_args.map!(&:inspect)
```

この処理は、

- すべての `call_args` について
- まだ使われるかどうか分からない段階で
- 文字列(`#inspect` の結果)を生成し、配列を書き換える

という性質があります。

PR の説明にある通り、その後のフローでは「カラム × 属性メソッド」の組み合わせのうち、**最初の 1 回しか `call_args` の文字列表現を実際には使っていなかった**にもかかわらず、モデル × カラム × 属性メソッドごとに常に `inspect` 付きの文字列を生成していました。

### この PR での変更
`call_args.map!(&:inspect)` を「呼び出しの早い段階で一括実行」するのではなく、**実際に `inspect` された引数が必要になる箇所まで処理を遅延（lazy）させた**、というのがこの PR の本質です。

イメージとしては、従来:

```ruby
# 以前: 早い段階で必ず全引数を inspect していた
call_args.map!(&:inspect)
# 以降、エラーメッセージなどで call_args を使用
```

となっていたところを、変更後は:

```ruby
# 必要になるまで inspect しない
# ...
if need_inspected_args
  inspected_call_args = call_args.map!(&:inspect)
  # inspected_call_args を使う処理
end
```

といった形に近づけた、という変更です（実際のコードは多少異なる可能性がありますが、意図としてはこのような「使う直前で初めて inspect する」形にリファクタリングされています）。

これにより、

- 多くのケースでは `inspect` 自体が呼ばれない  
- したがって、**不要な String オブジェクトの割り当てが行われない**

という挙動になります。

---

3. 影響範囲・注意点  

### 影響範囲
- 対象: `ActiveModel::AttributeMethods` を利用している全てのモデル（`ActiveRecord::Base` を継承した通常の Rails モデルを含む）  
- 実際の影響: 主に内部のパフォーマンス改善であり、アプリ側のコード変更は不要

### 挙動の変化の可能性
通常の利用において、外部に見える挙動（API）は変わらないようになっています。注意すべき点は次のような場合です:

- `call_args` を `inspect` する前提で、`AttributeMethods` 内部の非公開 API に依存している（メタプログラミングや Monkey Patch など）  
  - そのようなコードは本来非推奨ですが、この PR により、**「常に `call_args` が文字列（`inspect` 済み）である」という前提は崩れます**。
- `call_args` の内容や型を内部フックで覗き見している場合  
  - 一部のタイミングで、以前は String だったものが、元のオブジェクト（Symbol, Numeric, など）のままになっている可能性があります。

標準的な Rails アプリケーションで、公式にサポートされている API だけを使用している限りは、動作上の違いを感じることはなく、パフォーマンスがわずかに向上するだけと考えてよいです。

---

4. 参考情報 (あれば)  

- 該当 PR: https://github.com/rails/rails/pull/58905  
- 関連コンポーネント:  
  - `ActiveModel::AttributeMethods`（Active Record モデルの動的な属性メソッド生成ロジック）  
- 類似の最適化として、Rails 本体では「例外メッセージの構築を遅延させる」「バックトレース生成を必要時のみ行う」など、`inspect` や文字列生成を遅らせるパターンが多数採用されており、本 PR もその一環の位置づけといえます。

## [#58746](https://github.com/rails/rails/pull/58746) Escape JSON with String#tr!  {#pr-58746}

**マージ日**: 2026/9/30 | **作成者**: [@federico-carrocera](https://github.com/federico-carrocera)

1. 概要 (1-2文で)  
Rails の JSON エンコード処理において、特殊文字のエスケープを `String#gsub!` ベースから `String#tr!`（ハッシュ対応版）を用いた実装へ最適化し、大きめの JSON ドキュメントで大きなパフォーマンス向上を図った PR です。エンコードが不正な場合は従来どおり `gsub!` にフォールバックするため、互換性を保ちつつ高速化しています。

---

2. 変更内容の詳細  

### 2-1. 何をしている PR か  
Ruby 本体側の新機能として、`String#tr!(hash)` が導入されました（1パスで UTF-8 文字列を書き換え可能、正規表現不要）。  
この PR では、Rails の JSON エンコーダ（特に `JSONGemCoderEncoder`）が JSON エスケープ処理にこの `tr!` を使うように変更されています。

従来の実装は:

- 文字列をバイナリエンコーディングに変更 (`ASCII-8BIT`)
- エスケープすべきバイト列を `Regexp.union` と `gsub!(regex, hash)` で置換
- UTF-8 に戻す

という流れでしたが、新しい実装では、UTF-8 のまま `tr!(hash)` によって一発変換します。

### 2-2. エスケープ対象文字とロジック  

Rails の JSON エンコードで問題になるのは主に:

- U+2028 (LINE SEPARATOR)
- U+2029 (PARAGRAPH SEPARATOR)
- `<`, `>`, `&`

これらは HTML 埋め込み時の XSS やスクリプトコンテキストでの問題を避けるためにユニコードエスケープへ変換されます。  
PR の説明中にあるマッピングは概ね次のようなものです:

```ruby
ESCAPES = {
  "\u2028" => '\u2028',
  "\u2029" => '\u2029',
  ">"      => '\u003e',
  "<"      => '\u003c',
  "&"      => '\u0026',
}
```

Rails 側でも同様のマッピングを JSON エンコード時に使用し、それを `tr!` に渡します。

### 2-3. 有効なエンコーディングのみ `tr!` を使う  

`String#tr!` は「不正なエンコーディングの文字列」に対しては例外を上げる仕様です。そのため、Rails 側では:

```ruby
def escape_with_tr(json)
  return escape_with_gsub(json) unless json.valid_encoding?
  json.tr!(ESCAPES)
  json
end
```

のように、

1. `valid_encoding?` が `true` なら `tr!` を使用（高速パス）
2. `false` なら従来どおり `gsub!` による処理（フォールバック）

という二段構成になっています。  
これにより、既存のアプリで不正なエンコーディングを含む文字列が紛れ込んでいたケースでも、今までと同じ挙動（`gsub!` ベース）で動作し、例外で落ちることを避けています。

### 2-4. パフォーマンス特性  

PR で提示されているベンチマーク結果（Ruby 4.1 dev, arm64, Darwin）は次の通りです。

- 小さい JSON（48 bytes, エスケープ対象なし）の場合
  - `gsub!`: 約 6.18M i/s
  - `tr!`: 約 4.51M i/s  
  -> 小さい & 置換不要な文字列では、事前コンパイル済み Regexp を使う `gsub!` の方が速い（`tr!` は毎回翻訳テーブルを作るため）。

- 大きな JSON（約 51KB, HTML を 900 回繰り返し）の場合
  - `gsub!`: 約 1.95k i/s （~512 µs / call）
  - `tr!`: 約 20.45k i/s（~49 µs / call）  
  -> 約 10.5 倍速い。

Rails 実運用では JSON が数 KB〜数十 KB になるケースが多いため、この変更によって全体としては十分な性能改善が見込める、と判断されています。

### 2-5. どのエンコーダが対象か  

- Rails には複数の JSON エンコーダがありますが、`JSON::Coder` が利用可能な環境ではデフォルトで `JSONGemCoderEncoder` が使われます。
- この PR では「両方のエンコーダ」が更新されていますが、現実的には `JSONGemCoderEncoder` の影響が最も大きくなります。
- `activesupport/lib/active_support/json/encoding.rb` にあるエスケープ処理が `tr!` 対応版に更新されています。

---

3. 影響範囲・注意点  

### 3-1. 影響範囲  

- 影響を受けるのは「Rails で JSON を生成する全てのコード」です。  
  例:
  - `render json: object`
  - `object.to_json`（Rails の ActiveSupport 拡張経由）
  - `ActiveSupport::JSON.encode(object)`

- 特に HTML に埋め込む JSON（`<script>` タグ内の初期データなど）でのエスケープ処理はこの変更の直接的な恩恵を受けます。

### 3-2. 互換性と振る舞いの変化  

基本的には**出力される JSON の内容は変わらない**（バイト列レベルで一致するよう、テスト & ベンチで確認済み）ことが前提で実装されています。PR 中でも以下のように検査しています:

```ruby
raise "paths disagree" unless escape_gsub(src.dup).b == escape_tr(src.dup).b
```

このため、アプリケーションコード側で想定している JSON フォーマットやエスケープ結果は従来どおりです。

ただし、次のようなケースには注意してください:

- **エンコーディングが不正な文字列を JSON に流し込んでいる場合**
  - その文字列は `valid_encoding? == false` になり、`tr!` ではなく旧来の `gsub!` パスへ回ります。
  - これ自体は挙動の変化ではありませんが、「`tr!` による高速化の恩恵を受けない」ため、そうした文字列を事前に正規化しておくと性能改善につながります。

- **Ruby バージョンとの対応**
  - `String#tr!(hash)` は Ruby 本体側の新機能に依存します。  
  - Rails 側では Ruby の該当バージョン以降をターゲットとしているため問題ありませんが、もし独自に `String#tr!` をモンキーパッチしていた場合には、挙動が変わる可能性があります。

### 3-3. パフォーマンス面の実務的な影響  

- 大量の JSON を返す API、もしくは `render json:` を大量に叩く SPA バックエンドなどでは、CPU 使用率の低減やスループット向上が期待できます。
- 逆に、非常に小さな JSON を「頻繁に」「ほぼエスケープ不要な形で」生成するマイクロサービスの場合、理論上は旧来の `gsub!` の方が速いケースもありますが、Rails 側のベンチでは「全体としては `tr!` の方が有利」と判断されています。
  - 必要であればアプリケーションレベルで独自エンコーダを実装し直すことで、局所的にチューニングする余地はあります。
