## [#58929](https://github.com/rails/rails/pull/58929) Clarify scope of record reloading {#pr-58929}

**マージ日**: 2026/10/3 | **作成者**: [@fxn](https://github.com/fxn)

1. 概要 (1-2文で)  
`ActiveRecord::Persistence#reload` が「何を」「どこまで」リロードするのかを明確にするため、ドキュメント文言の改善と、それに対応するテストが追加された PR です。  
主に「属性値と AR が管理する内部状態はリセットされるが、開発者が独自に持たせたカスタム状態はそのまま残る」ことが明示されました。

---

2. 変更内容の詳細  

### 2-1. `reload` の挙動の明確化

これまで `reload` の説明は「レコードをDBから再読込する」といった粒度で、次の点が曖昧でした。

- 「再読込される」のが具体的に何なのか  
- Active Record が管理する内部状態と、アプリ側が持たせたカスタムな状態の扱いの違い

PR での意図は以下です。

- **リロードされるもの**
  - データベースに保存されている **属性値 (attributes)**  
  - それに整合するように、Active Record が内部で保持している **AR 管理下の状態**（変更トラッキング等）

- **リロードされないもの**
  - モデルインスタンスにぶら下げた **カスタムなインスタンス変数・キャッシュ・外部サービス由来の状態** など  
    （例: `@expensive_api_result` のようなもの）

PR の説明文から要点を抽出すると:

- `reload` は **属性値をDBから読み直して上書きする** メソッドである
- それに応じて **AR が内部的に管理している状態もリセットされる**
- ただし、**開発者が独自に追加した状態（インスタンス変数など）はそのまま残る**
- これにより、たとえばテストで「DBだけリセットされたが、外部サービス結果のキャッシュが残っていた」というケースが起こり得るので、その挙動を明示した

### 2-2. ドキュメントの文言修正 (`persistence.rb`)

`activerecord/lib/active_record/persistence.rb` で、`reload` のコメント（APIドキュメント）が次のような方針で調整されています。

- 「レコードをリロードする」という抽象的な表現から、  
  → 「属性値をDBの状態に合わせて読み直す」という具体的な表現へ
- 「Active Record が制御するものは合わせてリセットされるが、それ以外（カスタム状態）は対象外」という境界を明示
- 内部実装の詳細（どの ivar・どのフラグがどう変わるか）はあえてぼかし、「AR が内部的に整合性を取る」という程度の説明に留める

※PR本文にもある通り、「何が AR 管理の状態で、何がカスタム状態なのか」をコードレベルで厳密に区別して自動的に処理するのは困難かつ後方互換性を壊す可能性があるため、**挙動を変えるのではなく、あくまで「仕様として説明する」方向**です。

### 2-3. テストの追加 (`persistence_test.rb`)

`activerecord/test/cases/persistence_test.rb` にテストが追加され、ドキュメントで説明された挙動が実際の仕様として固定されます。

概念的には、次のようなテストが入っていると考えられます（擬似コード）:

```ruby
def test_reload_resets_attributes_but_keeps_custom_state
  user = User.create!(name: "Alice")
  user.custom_cache = :cached_value   # カスタムなインスタンス変数
  user.name = "Changed locally"

  user.reload

  assert_equal "Alice", user.name             # 属性値はDBの値に戻る
  assert_equal :cached_value, user.custom_cache  # カスタム状態は残る
end
```

ここでポイントになるのは:

- DB に保存されている `name` は `reload` によって「正しい状態」に戻る
- しかし `custom_cache` のような **AR によって知られていないインスタンス変数はそのまま残る**  

という仕様をテストで保証しているという点です。

---

3. 影響範囲・注意点  

- **実行時の挙動は変更されていない**  
  既存アプリケーションの `reload` の挙動は従来通りで、コード上の互換性を壊す変更はありません。  
  変わったのは「説明とテスト」であり、現状の挙動を公式に仕様として固定した形です。

- **テストやキャッシュ実装での落とし穴**  
  このPRが明示している通り、次のようなケースでは注意が必要です。

  - モデルインスタンスに **外部サービスのレスポンスをキャッシュ** している
  - **memoization**（`@foo ||= heavy_calculation`）で重い処理結果をインスタンス変数に保持している
  - テストで `reload` すれば「全部きれいになる」と思い込んでいる

  これらは `reload` ではリセットされないため、**DBの状態とカスタムキャッシュの状態が食い違う** 可能性があります。  
  もし「リロード時にカスタム状態も消したい」場合は、`after_find` / `after_initialize` / 独自メソッドを使って明示的にリセットする必要があります。

- **設計上の指針としての明文化**  
  今回のドキュメント更新により、「ARが責任を持つ範囲」と「アプリケーションが責任を持つ範囲」がよりはっきりしました。  
  AR の `reload` はあくまで「DB由来の属性と、それに付随するAR内部状態」を対象とし、  
  それ以外のインスタンス変数やオブジェクト状態のライフサイクル管理は、**アプリケーション側の責任** であることが明確化されています。

## [#58913](https://github.com/rails/rails/pull/58913)  Freeze events emitted by ActiveSupport::EventReporter {#pr-58913}

**マージ日**: 2026/10/2 | **作成者**: [@keshavbiswa](https://github.com/keshavbiswa)

1. 概要 (1-2文で)  
ActiveSupport::EventReporter がサブスクライバに渡すイベントデータ（ハッシュ）を `freeze` することで、サブスクライバ間での副作用や順序依存を防ぐ変更です。  
これにより、イベントの内容を書き換えようとするサブスクライバは `FrozenError` となり、通知されるイベントの整合性が保証されます。

---

2. 変更内容の詳細

### 背景問題

`ActiveSupport::EventReporter#notify` は、1つのイベントハッシュをそのまま全サブスクライバに共有していました。  
その結果:

- あるサブスクライバが `event[:payload][:foo] = :bar` のようにイベントを書き換えると、その後に実行されるサブスクライバは書き換え後のデータを受け取ってしまう
- パラメータフィルタリング等で削除された値を、後続のサブスクライバが「元に戻す」ことも理論上可能
- 結果として、「どのデータが見えるか」が購読順序に依存してしまう

という問題がありました。

### 具体的な変更点

このPRでは、`notify` 内で作られるイベントのトップレベル構造をすべて `freeze` するように変更しています。

対象:

- イベントハッシュ自体
- `:payload` ハッシュ
- `:source` (source location を表すオブジェクト)
- （元々）`tags` と `context` はすでに `freeze` 済み

方針:

- Reporter 内で「自分で構築したコピー」に対してのみ `freeze` を行う
- 呼び出し元が渡した `payload` ハッシュや、`notify` に直接渡されたイベントオブジェクトは **freeze しない**
  - つまり、呼び出し元のデータ構造の所有権を奪わない

イメージコード（擬似的）:

```ruby
def notify(name, payload: {}, **options)
  # 呼び出し元の payload はそのまま（freezeしない）
  event_payload = payload.dup.freeze
  event_source  = build_source_location(...).freeze

  event = {
    name: name,
    payload: event_payload,
    source: event_source,
    tags: tags.freeze,       # もともと freeze されている
    context: context.freeze, # もともと freeze されている
  }.freeze

  subscribers.each do |subscriber|
    subscriber.call(event) # ここから event は読み取り専用
  end
end
```

### エラー挙動

- サブスクライバ側で、例えば:

  ```ruby
  ActiveSupport::EventReporter.subscribe("request") do |event|
    event[:payload][:user_id] = 123   # または event[:payload][:foo].upcase!
  end
  ```

  のように「イベントオブジェクトをインプレース変更」しようとすると `FrozenError` が発生します。

- `ActiveSupport::EventReporter` は既存のエラーハンドリングポリシーに従い:
  - デフォルトでは、そのエラーを内部で報告（ログ等）しつつ処理継続
  - `raise_on_error` オプションが有効な場合は、そのまま例外を再送出

Rails 本体に含まれる標準のサブスクライバはイベントを書き換えない設計なので、この変更によって Rails 内部で `FrozenError` が出ることは想定されていません。

### テスト・ドキュメント

- `activesupport/test/event_reporter_test.rb`
  - イベントが freeze されること
  - 変更しようとすると `FrozenError` になること
  - deep freeze されていない（ネストしたオブジェクトはそのまま）こと  
  などを確認するテストが追加。
- `activesupport/CHANGELOG.md`
  - 振る舞いの変更として、イベントが freeze されることが明記されています。

---

3. 影響範囲・注意点

### 影響範囲

- ActiveSupport::EventReporter を使ってイベント購読を行っているすべてのコード
  - 特に、ブロック/サブスクライバ内でイベントハッシュや payload を直接書き換えている場合

### 注意点

1. **イベントオブジェクトは読み取り専用とみなす必要がある**

   ```ruby
   reporter.subscribe("foo") do |event|
     # NG: 直接書き換え
     event[:payload][:foo] = "bar"   # FrozenError

     # OK: 読み取るだけ
     process(event[:payload][:foo])
   end
   ```

2. **freeze は浅い**

   - `payload` 自体のハッシュは freeze されますが、payload 内の値（オブジェクト）は freeze されません。
   - 例えば:

     ```ruby
     reporter.notify("foo", payload: { data: [] })

     reporter.subscribe("foo") do |event|
       event[:payload][:data] << 1  # これは可能（配列自体は freeze されていない）
     end
     ```

   - 「サブスクライバに渡す前に、完全に不変にしたい」場合は、呼び出し元の側で深いコピーや deep freeze を行う必要があります。

3. **既存コードの互換性**

   - これまで「たまたま動いていた」イベントの書き換えコードは破壊的変更になります。
   - カスタムインストルメンテーションやモニタリングライブラリで:
     - イベントを加工して後続サブスクライバに渡す
     - イベントをそのまま保持して後で書き換える
   - といったパターンを使っている場合は、設計の見直しが必要です。
     - 例: イベントを複製してから加工する:

       ```ruby
       reporter.subscribe("foo") do |event|
         event_copy = event.deep_dup
         event_copy[:payload][:foo] = "bar"
         # 以降は event_copy を使う
       end
       ```

4. **パフォーマンス**

   - 各サブスクライバごとにコピーを作らず、1イベントにつき1つのコピー＋shallow freeze のみ。
   - EventReporter は比較的ホットパスになり得るため、deep freeze や subscriber ごとのコピーは避けていることが明示されています。

---

4. 参考情報 (あれば)

- 対応Issue: #58912  
  「サブスクライバ間でイベントハッシュが共有されることによる副作用」の報告・議論に対する修正。
- 変更対象:
  - `activesupport/lib/active_support/event_reporter.rb`
  - `activesupport/test/event_reporter_test.rb`
  - `activesupport/CHANGELOG.md`  
- 設計方針:
  - イベントの「観測結果」を安定させる（購読順序に依存させない）
  - 呼び出し元のデータ所有権は尊重する（元の payload などは凍結しない）
  - Hot path であることを考慮し、deep freeze・subscriber ごとのコピーは行わない

## [#58680](https://github.com/rails/rails/pull/58680) Cache ActiveSupport::ParameterFilter instances across requests {#pr-58680}

**マージ日**: 2026/10/2 | **作成者**: [@eregon](https://github.com/eregon)

1. 概要 (1-2文で)  
各リクエストごとに生成されていた `ActiveSupport::ParameterFilter`（内部で複数の `Regexp` を生成）が、同じフィルタ一覧であればグローバルに再利用されるようになり、ログ用パラメータフィルタの構築コストが削減されました。これにより特にフィルタ数が多いアプリケーションや `config.precompile_filter_parameters` を無効にしている環境で、リクエストあたりのオーバーヘッドが有意に減少します。

---

2. 変更内容の詳細

### 何をしているか

- `ActionDispatch::Request` が使う `ActiveSupport::ParameterFilter` インスタンスを、
  - 「リクエスト単位のメモ化」から
  - 「プロセス全体で共有されるキャッシュ」  
  に変更しています。

- キャッシュは `Concurrent::Map` で実装されており、**フィルタの配列（Array）の内容をキー**にして `ParameterFilter` インスタンスを記憶します。
  - 同じ配列オブジェクトでなくても、`Array#==` が `true` になる（中身が同じ）配列であれば同じキーとして扱われます。
  - `env_filter` のように毎回新しい配列を組み立てるコードでも、内容が同じならキャッシュヒットします。

- `ParameterFilter` は生成後に不変（イミュータブル）とみなせるため、**複数リクエスト・複数スレッドでの共有が安全**と判断されています。

### キャッシュの上限と挙動

- キャッシュは**最大 100 エントリ**に制限されています。
  - 101 個目以降が追加されそうになったら、キャッシュ全体をクリアします（単純な全クリア戦略）。
  - 理由: フィルタリストを動的に大量生成するアプリケーションで、無制限にキャッシュが増え続けるのを防ぐため。

- 典型的なアプリケーションでは、フィルタ定義は数パターンに収まることが多いため、キャッシュミスはあまり発生しない想定です。

### パフォーマンス背景

- 従来:
  - 各リクエストで `ActiveSupport::ParameterFilter.new(filters)` が呼ばれ、
  - その中で `compile_filters!` → `Regexp.new`, `Regexp.escape`, `Regexp#to_s` などが実行されていました。
  - 正規表現の生成はパース・バイトコード生成などがあり、比較的重い処理です。

- この PR 後:
  - 同じ `filters` 配列であれば、**最初の1回だけコンパイル**され、その後はキャッシュ済みの `ParameterFilter` を再利用します。
  - Ruby 4.0.6 / actionpack 8.1.1 の計測例では、1 回の `ParameterFilter` 構築が
    - キャッシュなし: ~5–6μs
    - キャッシュヒット: ~0.9μs  
    に短縮されています。

- ベンチマーク（railsbench, 2000 req/iteration, 中央値ベース）:
  - `config.precompile_filter_parameters = true`（7.1 以降のデフォルト）:
    - no JIT: 約 0.5% 高速化
    - YJIT: 約 0.65% 高速化
  - `config.precompile_filter_parameters = false`（生のフィルタリストを毎回コンパイル）:
    - YJIT: 約 7.9% 高速化  
      → キャッシュにより「非 precompile 設定でも、precompile ありと同等の速度」になると説明されています。

---

3. 影響範囲・注意点

### 影響範囲

- 影響する処理:
  - ログ出力時のパラメータフィルタリング（`filter_parameters`, `config.filter_parameters` を通じて設定されるもの）
  - `ActionDispatch::Request#filtered_parameters` や関連メソッド内で利用される `ActiveSupport::ParameterFilter`

- 期待される効果:
  - ほとんどのアプリケーションでリクエストごとのオーバーヘッドが減少。
  - とくに:
    - フィルタ数が多い（正規表現を多用している）アプリケーション
    - `config.precompile_filter_parameters = false` な環境  
    で効果が出やすい。

### 互換性と安全性

- `ParameterFilter` を共有するようになったが、**インスタンスは不変前提で設計されている**ため、スレッドセーフ。
- キャッシュキーは「フィルタ配列の内容」なので、**同じフィルタ定義なら挙動は完全に従来どおり**です。
  - 例: `[:password, :token, /credit_card/]` のような配列を再利用していれば、そのままキャッシュできます。
- フィルタを都度動的に変える（例: リクエストごとにランダムなフィルタを足すなど）とキャッシュミスが多くなり、さらに 100 エントリ超でキャッシュがクリアされますが、
  - 「キャッシュがなかった以前の状態」に戻るだけなので、**機能的な後退やバグにはつながらない**（最悪でも性能上の恩恵が減るだけ）。

### 開発者視点の注意点

- フィルタ定義をできるだけ**同じ配列内容で再利用**することで、キャッシュの恩恵を最大化できます。
  - 例:
    - 良い: `MY_FILTERS = [:password, :token]; ParameterFilter.new(MY_FILTERS)`
    - 微妙: 毎回 `[:password, :token] + extra_filters` を新規に作る（内容が変われば当然キャッシュミスが増える）
- フィルタを「リクエストスコープで変更・拡張する」ような高度な使い方をしている場合:
  - 引き続き動作はしますが、キャッシュ頻度が下がり、性能向上は限定的かもしれません。

## [#58289](https://github.com/rails/rails/pull/58289) Roll back when a before_commit callback raises a rollback error {#pr-58289}

**マージ日**: 2026/10/2 | **作成者**: [@adam-h](https://github.com/adam-h)

1. 概要 (1–2文で)  
`before_commit` コールバック内で `TransactionRollbackError` が発生した場合でも、トランザクションを正しくロールバックするように `within_new_transaction` の挙動が修正されました。これにより、トランザクションが開いたまま接続プールに戻ってしまう不具合が解消されます。

---

2. 変更内容の詳細  

### 問題の背景

`ActiveRecord::ConnectionAdapters::TransactionManager#within_new_transaction` は、おおまかに次のような流れで処理をしています:

1. トランザクションを開始
2. ブロックを実行（モデルの保存やコールバック実行など）
3. `before_commit` コールバック群 (`before_commit_records`) を実行
4. DB に対して `COMMIT` を投げる (`transaction.commit`)
5. 例外が起きた場合は `ROLLBACK` する … というのが本来の期待挙動

ところが既存コードでは、

- `within_new_transaction` の中で `TransactionRollbackError` を rescue して「ROLLBACK せずに終了する」特別扱いが入っていた
- この rescue 範囲に `before_commit_records`（`COMMIT` 実行前）が含まれていた

ために、

- `before_commit` コールバック内で `TransactionRollbackError` が発生すると
  - 「`COMMIT` 失敗時を想定した特別な rescue」と同じ扱いになってしまう
  - まだ `COMMIT` 自体は発行されていないにもかかわらず、`ROLLBACK` をスキップ
  - 結果として「トランザクションが開いたまま」そのコネクションがプールに戻る

という不整合な状態が起きていました。

### 本PRでの修正方針

修正のポイントは次の2つです。

1. 「`COMMIT` 後の `TransactionRollbackError` だけ特別扱いする」ように rescue の位置を移動
2. `within_new_transaction` レベルの `TransactionRollbackError` 専用 rescue を廃止し、`before_commit` 中の例外は通常のロールバック処理に通す

具体的には、`activerecord/lib/active_record/connection_adapters/abstract/transaction.rb` のトランザクション管理ロジックが変更されています。

元の構造（概略）:

```ruby
def within_new_transaction
  transaction = begin_transaction(...)
  yield
  add_to_commit_records
  before_commit_records
  begin
    transaction.commit
  rescue TransactionRollbackError
    # COMMIT 失敗時は ROLLBACK をスキップする特別扱い
  end
rescue Exception => e
  transaction.rollback
  raise
ensure
  # cleanup ...
end
```

新しい構造のイメージ:

```ruby
def within_new_transaction
  transaction = begin_transaction(...)
  yield
  add_to_commit_records
  before_commit_records

  # ★ invalidation（= COMMIT 後に ROLLBACK をスキップする処理）を
  #    transaction.commit のすぐ隣に移動
  transaction.commit
rescue TransactionRollbackError => e
  # ここは「COMMIT から上がってきたもの」だけを扱うようになる
  # → COMMIT が失敗した場合は、トランザクションは DB 側ですでに終了しており、
  #    余計な ROLLBACK を投げない
  # （#56717 と同じ振る舞いを維持）
rescue Exception => e
  # before_commit を含む「COMMIT 前」に発生した例外はここに落ちる
  # → これまで通り ROLLBACK を実行する
  transaction.rollback
  raise
ensure
  # cleanup ...
end
```

ポイント:

- `COMMIT` が「実際に送られた後」の `TransactionRollbackError` だけを特別扱いするようにした  
  → これは、たとえば PostgreSQL でシリアライゼーションエラーなどにより `COMMIT` が失敗したケース（#56717）を想定した挙動で、DB 側ではすでにトランザクションが終わっているため、`ROLLBACK` を投げないのが正しい。
- それより前（`before_commit` 含む）の例外は「通常のエラー」として扱われ、`rescue Exception` 側で `ROLLBACK` されるように戻した  
  → `before_commit` 内で `TransactionRollbackError` を投げても、きちんとロールバックされる。

### テスト追加内容

`activerecord/test/cases/adapters/postgresql/transaction_test.rb` にテストが追加されています（+22行）。

テストではおそらく次のようなシナリオが検証されています（概略）:

- PostgreSQL アダプタ使用時
- モデルに `before_commit` コールバックを定義し、その中で `raise ActiveRecord::TransactionRollbackError` を発生させる
- そのモデルを `transaction` ブロック内で保存し、`before_commit` で例外を投げる
- 期待結果
  - トランザクションはロールバックされていること
  - コネクションがトランザクション中のままプールに戻らないこと（後続クエリが通常通り動く）

これにより、今回のバグが再現していたケースが再度発生しないことを保証しています。

---

3. 影響範囲・注意点  

### 影響範囲

- 対象:
  - `before_commit` / `after_commit` などのコミット直前・直後のコールバックを利用しているコード
  - `TransactionRollbackError` をアプリケーションレベルで明示的に投げているロジック
  - PostgreSQL など、`COMMIT` 時にシリアライゼーションエラーなどで `TransactionRollbackError` が発生し得るDB

### 実質的な動作変更

- 変わる点
  - `before_commit` 内で `TransactionRollbackError` が発生した場合に、**明示的に ROLLBACK が実行されるようになる**（以前はスキップされていたバグを修正）
  - これにより、トランザクションが開いたままプールに戻ることがなくなり、後続処理で「なぜか常にトランザクション内扱いになる」などの不可解な不具合が減る

- 変わらない点
  - 実際に `COMMIT` が投げられた後に DB から返る `TransactionRollbackError`（例: シリアライゼーションエラー）は、**これまで通り ROLLBACK を投げない**  
    → #56717 で導入された挙動は維持される

### 注意点

- もし既存コードが「`before_commit` で `TransactionRollbackError` を投げてもトランザクションが継続している」という誤った前提に依存していた場合、その前提は崩れます。
  - とはいえ、この前提に依存するのはほぼバグに近い使い方なので、修正の影響は本来望ましい方向です。
- DB セッション状態を直接いじるような高度な実装（例えば生 SQL でトランザクション境界を操作しているなど）をしている場合は、今回の変更で「予期せぬ ROLLBACK が追加された」と誤解しないように、`before_commit` と `COMMIT` の境界を意識して挙動を確認してください。

---

4. 参考情報 (あれば)

- 該当PR:  
  - Roll back when a before_commit callback raises a rollback error (#58289)
- 関連Issue:  
  - #58288 — `before_commit` コールバック内での `TransactionRollbackError` により、トランザクションがロールバックされずに接続プールに戻ってしまう問題
- 関連する過去のPR:  
  - #56717 — `COMMIT` 自体がシリアライゼーションエラーなどで失敗した場合に、不要な ROLLBACK を回避する挙動を導入したPR（今回もこの挙動は維持されている）

アプリケーション側で `before_commit` コールバックや `TransactionRollbackError` を積極的に使っている場合は、テスト環境でトランザクションの挙動（特にネストしたトランザクションやエラー発生時の状態遷移）を一度確認しておくと安全です。

## [#58813](https://github.com/rails/rails/pull/58813) Include extra node state in Arel equality {#pr-58813}

**マージ日**: 2026/10/2 | **作成者**: [@e-akashsaini](https://github.com/e-akashsaini)

1. 概要 (1–2文で)  
Arel の一部ノード (`Matches`, `DoesNotMatch`, `Regexp`, `NotRegexp`, `InfixOperation`, `UnaryOperation`) について、SQL 出力に影響する追加状態（escape 文字や大文字小文字区別フラグ、演算子）を `eql?` / `hash` 判定に含めるようにし、異なる条件が `where` のマージや `or` 結合時に誤って同一視されて消えてしまう問題を修正する PR です。  
これにより、`Relation#or` / `merge` / `WhereClause` の重複排除が、より直感的かつ安全な挙動になります（Active Record が自前で生成する通常のクエリは影響なし）。

---

2. 変更内容の詳細

### 問題の背景

Arel の多くのノードクラスは `Arel::Nodes::Binary` / `Unary` を継承しており、デフォルトの `eql?` / `hash` は「クラス＋オペランド」だけを比較対象にします。

しかし、以下のクラスは「クラス＋オペランド以外の状態」が SQL に影響するにもかかわらず、その状態が `eql?` / `hash` に含まれていませんでした:

| ノード | 無視されていた状態 | 影響する SQL |
|-------|--------------------|-------------|
| `Matches`, `DoesNotMatch` | `escape`, `case_sensitive` | `ESCAPE` 句、`LIKE` vs `ILIKE` (PostgreSQL) |
| `Regexp`, `NotRegexp`     | `case_sensitive`            | `~` vs `~*` (PostgreSQL) |
| `InfixOperation`          | `operator`                  | `>`, `<`, `->>`, `@>` など任意の中置演算子 |
| `UnaryOperation`          | `operator`                  | 任意の prefix 演算子 |

その結果、**異なる SQL を生成する 2 つのノードが `eql?` / `hash` 上は同一**と見なされ、以下のような現象が起きます。

- `ActiveRecord::Relation::WhereClause` は内部的に `Array#-` や `Array#|` を使って述語を重複排除しているため、一方の条件が捨てられる
- `Relation#or` は `self - other` が空だと「同じ条件」とみなして idempotent ショートカットを使い、`Or` ノードを作らずに左辺の Relation をそのまま返す

具体例:

```ruby
title = Post.arel_table[:title]
a = Post.where(title.matches("100%", "!"))
b = Post.where(title.matches("100%"))

a.or(b).to_sql
# 修正前:
# SELECT "posts".* FROM "posts" WHERE "posts"."title" LIKE '100%' ESCAPE '!'

# 修正後:
# SELECT "posts".* FROM "posts" WHERE
# ("posts"."title" LIKE '100%' ESCAPE '!' OR "posts"."title" LIKE '100%')


a.merge(b).to_sql
# 修正前:
# ... WHERE "posts"."title" LIKE '100%' ESCAPE '!'

# 修正後:
# ... WHERE "posts"."title" LIKE '100%' ESCAPE '!' AND "posts"."title" LIKE '100%'
```

修正前は、`escape` の違いを持つ `Matches` が同一視されており、`or` も `merge` も新しい条件が追加されませんでした。

同じ問題は:

- `InfixOperation.new(:">", ...)` と `InfixOperation.new(:"<", ...)`
- PostgreSQL における `LIKE` (case_sensitive) と `ILIKE` (case_insensitive)
- 正規表現 `~` / `~*` (`Regexp` / `NotRegexp` の `case_sensitive` の違い)

などでも発生し得ます。どれも文法としては正しいが、「ユーザーが意図したよりも絞り込まれたクエリ」になるというバグです。

Rails が内部で生成するクエリでは、これらのノードに「異なる追加状態」を持たせるケースはなく、影響は基本的に **Arel の API (`matches`, `matches_regexp`, `InfixOperation` など) を直接使っているコード**に限られます。

---

### 具体的なコード変更

対象クラスごとに、追加状態を考慮した `hash` / `eql?` / `==` を定義しています。パターンは既存の `Extract`, `NamedFunction`, `NamedWindow` と同じです。

#### Matches / DoesNotMatch

```ruby
def hash
  super ^ [@escape, @case_sensitive].hash
end

def eql?(other)
  super &&
    self.escape == other.escape &&
    self.case_sensitive == other.case_sensitive
end
alias :== :eql?
```

- `super` は `Binary` / `Unary` の `hash` / `eql?` を呼ぶ
  - つまり「クラス＋左オペランド＋右オペランド」の比較は今まで通り維持
- その上で `escape` と `case_sensitive` も比較対象に追加
- `alias :== :eql?` を各クラスでやり直しているのは、親クラス側の `alias` が親の実装にバインドされてしまうため

#### Regexp / NotRegexp

```ruby
def hash
  super ^ [@case_sensitive].hash
end

def eql?(other)
  super &&
    self.case_sensitive == other.case_sensitive
end
alias :== :eql?
```

- PostgreSQL の `~` / `~*` を切り替える `case_sensitive` を考慮

#### InfixOperation

```ruby
def hash
  super ^ [@operator].hash
end

def eql?(other)
  super &&
    self.operator == other.operator
end
alias :== :eql?
```

- `>` と `<`、`->>` と `@>` など「演算子の違い」を equality に含める

#### UnaryOperation

```ruby
def hash
  super ^ [@operator].hash
end

def eql?(other)
  super &&
    self.operator == other.operator
end
alias :== :eql?
```

- prefix 演算子についても同様

#### 既存クラスの微修正

`Extract`, `NamedFunction`, `Window` の `hash` 実装で `super` を使うような微調整も入っていますが、機能的にはこれまでと同じ意図を保ったまま実装スタイルを揃える程度です（+1/-1）。

---

### テスト

新規・拡張テストで変更をカバー:

- `activerecord/test/cases/arel/nodes/matches_test.rb`（新規）
  - `Matches` / `Regexp` それぞれについて:
    - `escape` が異なると `eql?` / `hash` が異なる
    - `case_sensitive` が異なると異なる
    - すべてのインスタンス変数が同じなら同一とみなされる（コントロール）
- `infix_operation_test.rb` / `unary_operation_test.rb`
  - 既存の「オペランド差による不等」テストに加え、「`operator` が異なる場合も不等」となるケースを追加
- `relation/or_test.rb`
  - 実際に `Relation#or` で `Matches` の escape 違いが OR 条件として残ることを確認する回帰テスト

これら 6 テストは、この PR のライブラリ変更がないと失敗します。

---

3. 影響範囲・注意点

- 影響するのは **Arel ノードの equality (`eql?` / `==` / `hash`) を利用しているコード** です
  - `WhereClause` 内部の重複排除
  - `Relation#or` のショートカット
  - `ActiveSupport::Cache` などで「Arel ノードを Hash のキーや Set の要素にしている」場合
- 特に影響が出るケース:
  - `Arel::Predications#matches`, `matches_regexp`
    - `escape` や `case_sensitive` を変えた 2 つの predicate が、**もはや「同一」扱いされません**
  - `Arel::Nodes::InfixOperation`, `UnaryOperation` を直接使っている場合
    - `operator` が異なると必ず不等になります

これは「バグ修正」であり、**正しい表現としては「今まで誤って同一と扱われていたものが、きちんと区別されるようになる」**なので、多くの場合は望ましい挙動のはずです。

注意点:

- もし既存アプリケーションが「`InfixOperation` / `Matches` などを、`operator` / `escape` / `case_sensitive` 無視で同一視している」ことに依存していた場合、その前提は崩れます
  - たとえば「`>` と `<` を同一視して SET で一意化する」ような実装があった場合、今後は 2 要素として扱われる
- equality は `where` / `merge` のホットパスなので、`Binary` / `Unary` で一括して「`instance_variables` 反映による汎用 eq 実装」を導入する案は却下され、ピンポイント修正に留めています
  - パフォーマンスや意味的な変更リスク（例: `Arel::Table#hash` は alias をあえて無視している）を避けるため

**Active Record が自前で組み立てる通常のクエリは、そもそもこれらの「追加状態の差」を持つノードを同じカラムに対して同時に使っていないため、この PR によって既存の Rails 生成 SQL が変わることはありません。**

---

4. 参考情報 (あれば)

- バグは Arel が Active Record に統合された初期 (`17ca17072d`) から存在し、Rails 6.0.0 以降のすべてのリリースに潜在していました。
- 修正対象は「ノードの equality 判定」のみであり、アダプタ（SQLite / MySQL / PostgreSQL）依存のロジックには触れていません。
- ローカルでは `ARCONN=sqlite3` で Arel 関連テストおよび Relation 関連テスト一式、`rake test:sqlite3` がすべて成功したことが記載されています。MySQL / PostgreSQL は CI 前提ですが、変更内容的にアダプタ非依存です。

## [#58918](https://github.com/rails/rails/pull/58918) Remove dead code for Ruby &lt; 3.3.5 {#pr-58918}

**マージ日**: 2026/10/2 | **作成者**: [@hmcguire-shopify](https://github.com/hmcguire-shopify)

1. 概要 (1-2文で)  
Ruby 3.3.5 未満向けのポリフィル（互換コード）を Active Record のコネクションプール／クエリキャッシュ周りから削除し、Ruby 3.3.5 以降を前提にした実装へ整理した PR です。これにより、Thread/Fiber 以外のキーを内部マップに使えるようになり、クエリキャッシュのクリア処理などで今後のパフォーマンス改善がしやすくなります。

---

2. 変更内容の詳細  

### 全体像
- 対象:
  - `activerecord/lib/active_record/connection_adapters/abstract/connection_pool.rb`
  - `activerecord/lib/active_record/connection_adapters/abstract/query_cache.rb`
- 目的:
  - Ruby 3.3.5 より前のバージョンを考慮したポリフィル（古い Ruby 向けの互換実装）を削除
  - Ruby 本体が提供する新しい挙動を前提として内部実装を単純化
  - Map（内部的なハッシュやストレージ）で Thread/Fiber 以外のオブジェクトをキーに使えるようにする足場を整備

### connection_pool.rb の変更点
- 主な変更は「スレッド／ファイバーごとに接続情報を管理するための内部マップ」の扱いから、古い Ruby 向けの迂回実装を削除したことです。
- これまで:
  - Ruby &lt; 3.3.5 の制約や不具合を回避するために、
    - Thread や Fiber をキーにした WeakMap/Map 相当のポリフィル
    - あるいは GC されにくい／キーのライフサイクルに制約がある実装
    を使っていた可能性があります。
- これから:
  - Ruby 3.3.5 で導入された／安定した Map 系機能（例えば WeakMap 相当の機能や、内部 C 実装のマップ）を前提に、ポリフィル側のコードを削除。
  - その結果、マップのキーとして Thread/Fiber に限定されず、任意のオブジェクト（例えば ConnectionHandler など）を使えるようになります。

ざっくりとしたイメージ（実際のコードは異なりますが、構造の変化イメージ）:

**Before（旧 Ruby サポートのためのポリフィルあり）**

```ruby
# Ruby < 3.3.5 でも動くようなポリフィル
class LegacyMap
  def initialize
    @hash = {}
  end

  def [](key)
    @hash[key.object_id]
  end

  def []=(key, value)
    @hash[key.object_id] = value
  end
end

# どこかで Ruby バージョンを見て Map 実装を切り替え
MAP_CLASS = if RUBY_VERSION < "3.3.5"
  LegacyMap
else
  RubyNativeMap # 例: Ruby が提供する新しい実装
end

@connections = MAP_CLASS.new
```

**After（Ruby 3.3.5 前提、ポリフィル削除）**

```ruby
# 常に Ruby 本体の新しい Map 実装を使用
@connections = RubyNativeMap.new
```

これにより、`@connections` のキーとして Thread/Fiber 以外も安全に使える前提が整います。

### query_cache.rb の変更点
- こちらは差分 1 行程度の単純な修正で、上記の Map 利用方法の変更に追随したものと思われます。
  - 例えば、クエリキャッシュをスレッドローカルや Fiber ローカルに紐づけていた箇所を、より汎用的なキー（たとえばコネクションプールインスタンスや別の ID）で管理できるようにするための準備的変更です。
- 結果として、クエリキャッシュの「どのキーで」「どの単位で」キャッシュを持つか、という戦略を柔軟に変更できるようになります。

---

3. 影響範囲・注意点  

### 影響範囲
- 対象コンポーネント:
  - Active Record のコネクションプール (`ConnectionPool`)
  - クエリキャッシュ (`QueryCache`)
- 実運用上の主な影響:
  - この PR 自体は主に「内部実装の整理」と「将来の最適化のための前準備」です。
  - 現時点では API の挙動変更よりも、内部でどのようなキーでマップを管理しているか、というレベルの変更に留まります。
- ただし、内部のマップ実装が変わることで:
  - クエリキャッシュのクリア処理（`clear_query_cache`, `clear_active_connections!` など）の実装がシンプルかつ高パフォーマンスに書き直しやすくなります。
  - Thread/Fiber 境界に強く依存していたキャッシュ管理から、「任意のコンテキスト単位」でキャッシュを持つ戦略にシフトしやすくなります。

### 注意点 / マイグレーション観点
- この PR は Ruby 3.3.5 以降を前提にポリフィルを削除しているため、
  - Rails のこのバージョン以降を使う場合、Ruby も 3.3.5 以上が事実上の前提になる可能性が高いです。
  - Ruby 3.3.4 以下で Rails を動かす構成は、将来的にサポート外・非推奨になる／もしくは既になっていると考えた方が安全です。
- Active Record の内部クラス（`ConnectionPool`, `QueryCache`）をモンキーパッチしている場合:
  - 内部の Map 実装に依存したコード（たとえば「Thread を直接キーにする前提で動くパッチ」など）は動かなくなる可能性があります。
  - `Thread.current` ベースのキャッシュ管理に深く依存した独自実装がある場合は、該当箇所を再確認した方がよいです。

## [#58919](https://github.com/rails/rails/pull/58919) Don't duplicate integration tests' fixture paths {#pr-58919}

**マージ日**: 2026/10/2 | **作成者**: [@earlofurl](https://github.com/earlofurl)

1. 概要 (1-2文で)  
`ActionDispatch::IntegrationTest` の `fixture_paths` が二重に登録されてしまう問題を修正し、同じフィクスチャを何度もロードし直してしまう非効率さを解消する PR です。これにより、特にフィクスチャ数が多いアプリケーションで、テスト全体の実行時間が大きく短縮されます。

---

2. 変更内容の詳細  

### 問題の背景

`rails/test_help` を require した Rails アプリで、以下のような状態になっていました。

```ruby
ActiveSupport::TestCase.fixture_paths
# => ["/app/test/fixtures/"]

ActionDispatch::IntegrationTest.fixture_paths
# 本来は上記と同じ配列を継承していれば十分だが…
# => ["/app/test/fixtures/", "/app/test/fixtures/"]  # 同じパスが2回入る
```

原因は以下の2点です。

1. `ActionDispatch::IntegrationTest` は `ActiveSupport::TestCase` を継承しており、`fixture_paths` も継承される
2. さらに `action_dispatch_integration_test` の load hook で、親クラスの `fixture_paths` をもう一度 `IntegrationTest.fixture_paths` に追加していた

この結果、`fixture_paths` に同じパスが2回入った状態になっていました。

さらに、Rails のフィクスチャは「`fixture_paths` を含んだキー」でキャッシュされます。そのため:

- 通常のテスト (`ActiveSupport::TestCase` 派生) が使うキー
- 統合テスト (`ActionDispatch::IntegrationTest`) が使うキー

が異なる (後者は `fixture_paths` が重複した配列になる) ため、同じフィクスチャであってもキャッシュを共有できず、テストタイプをまたぐたびにフィクスチャを再ロードしていました。

加えて、コミット `17cb852d72` により、「キャッシュキーが見つからない場合はフィクスチャキャッシュをリセットして再挿入する」という挙動になったため、テストファイルを順番に走らせると、

- 通常テスト → 統合テスト → 通常テスト → … と切り替わるたびに、
- すべてのフィクスチャが毎回入れ直される

という性能上のペナルティが顕在化していました（8.1 では未適用だったため影響なし）。

### 今回の修正

`railties/lib/rails/test_help.rb` の、`ActionDispatch::IntegrationTest` に対する load hook 内で、`fixture_paths` をそのまま連結するのではなく「重複しないように追加する」ように変更しています。

イメージとしては以下のような修正です（擬似コード）:

```ruby
# 変更前（イメージ）
ActionDispatch::IntegrationTest.fixture_paths += ActiveSupport::TestCase.fixture_paths

# 変更後（イメージ）
ActionDispatch::IntegrationTest.fixture_paths |= ActiveSupport::TestCase.fixture_paths
# または .uniq を通す等、重複を排除
```

※実際には #58454 (`08d4e20ce3`) で `ActiveSupport::TestCase` 向けに行われたのと同じ `uniq` ベースのアプローチと揃えています。

あわせて、`railties/test/application/integration_test_case_test.rb` にテストを追加し、

- `IntegrationTest.fixture_paths` が親クラスと同じパスを二重に持たないこと

を検証しています。この新しいテストは、この修正を入れないと失敗するようになっています。

---

3. 影響範囲・注意点  

### 影響範囲

- `rails/test_help` を読み込んでいるアプリケーションの
  - `ActionDispatch::IntegrationTest` を使った統合テスト
  - それ以外の `ActiveSupport::TestCase` ベースのテスト
- 特に、フィクスチャファイル数が多く、かつ「統合テストと通常テストが混在している」プロジェクトで、フィクスチャロードにかかる時間が大幅に削減されます。

PR 内での測定結果:

- 対象: フィクスチャファイル 111 個、テストファイル 20 個（うち 10 個が統合テスト）、テストケース 738
- 8.1.3 ベースに `17cb852d72` の挙動をパッチして再現
- Before:
  - フィクスチャロード回数: 77 回
  - フィクスチャロード時間: 28.0 秒
  - 総テスト時間: 127 秒
- After:
  - フィクスチャロード回数: 1 回
  - フィクスチャロード時間: 0.8 秒
  - 総テスト時間: 108 秒

小規模なアプリ（main 固定）でも、フィクスチャロード回数が 5 回 → 1 回になったと報告されています。

### 互換性・注意点

- `fixture_paths` 自体の意味や仕様は変わっていません。「同じパスが二重に入らなくなった」だけなので、通常のユースケースでの挙動変化はほぼありません。
- もしアプリやライブラリ側で「`fixture_paths` の重複を前提にした特殊な処理」をしている場合は影響しうるものの、そのようなコードはまず存在しないと考えられます。
- PR 中でも言及されていますが、実は「IntegrationTest 用フックをやめて継承に完全に任せる」という選択肢もありえました。ただし、`ActiveSupport::TestCase` と同様の `uniq` で整える形にして、挙動を揃えています。

---

4. 参考情報 (あれば)

- 該当 PR: https://github.com/rails/rails/pull/58919  
- 関連コミット:
  - `17cb852d72` — フィクスチャキャッシュのミス時にキャッシュをリセットする変更
  - `08d4e20ce3` / PR #58454 — `ActiveSupport::TestCase` の `fixture_paths` 重複を解消した変更
- 修正ファイル:
  - `railties/lib/rails/test_help.rb`  
  - `railties/test/application/integration_test_case_test.rb`  

実運用上は、Rails をこの PR を含むバージョンに上げるだけで、統合テストと通常テスト間でフィクスチャキャッシュが共有されるようになり、大規模なフィクスチャを使うプロジェクトではテスト時間短縮が期待できます。

## [#58908](https://github.com/rails/rails/pull/58908) Bump minimum Ruby version to 3.3.5 {#pr-58908}

**マージ日**: 2026/10/1 | **作成者**: [@hmcguire-shopify](https://github.com/hmcguire-shopify)

1. 概要 (1-2文で)  
Rails がサポートする最低 Ruby バージョンを 3.3.5 に引き上げる PR です。  
これにより、Weak{Key,}Map の use-after-free バグを前提にした独自ポリフィルを廃止でき、今後 Active Record のクエリキャッシュ周りをより効率的にリファクタリングできるようにする意図があります。

---

2. 変更内容の詳細  

### 2-1. どんなバグが背景にあるか

- Ruby 3.3.5 未満の WeakMap / WeakKeyMap 実装に use-after-free バグがある  
- このバグは「比較的遭遇しやすい」とされており、安全に WeakKeyMap を使えない
- そのため Rails 側では、WeakKeyMap をそのまま使うのではなく「ポリフィル (代替実装＋ラッパ)」を用意して、利用可能なキー種別を制限していました。

制限の具体例:
- WeakKeyMap のキーにできるのは `Thread` / `Fiber` など、`respond_to?(:alive?)` なオブジェクトだけ  
- つまり、任意オブジェクトを弱参照キーに使うことができず、設計の自由度が落ちていた

### 2-2. 最低 Ruby バージョンを 3.3.5 に上げる目的

PR 作成者のアプリケーションでは、**クエリキャッシュのクリア処理が CPU を食っている**という問題があります。

現在の実装イメージ:

- 各 DB 接続プールが、クエリキャッシュを「現在の実行コンテキスト (Thread/Fiber)」ごとに持っている  
- 「このコンテキストに紐づくキャッシュをクリアしたい」ときに、
  - **全ての connection pool を走査し、その pool 内の「現在の実行コンテキスト用キャッシュ」を消す**
  - → 利用していないプールも含めて毎回全プールを舐めるため、CPU コストが高い

理想の方向性:

- データ構造を「コンテキスト → そのコンテキストで使った connection pool の集合」に**反転**したい
  - いま: `pool -> { context -> cache }`
  - 目標: `context -> { pool -> cache }`
- こうすれば、「現在のコンテキストに紐づくプールだけ」を辿ればよく、**総プール数ではなく、そのコンテキストで実際に使ったプール数だけを走査すればよい**  
  → パフォーマンスが大幅に改善する見込み

この「構造の反転」には、connection pool オブジェクトを WeakKeyMap のキーとして安全に使えることが前提になります。しかし、現状のポリフィルは「Thread / Fiber など `alive?` を持つものしかキーにできない」ため、connection pool をキーにできません。

そこで:

- Ruby 側の WeakKeyMap 実装バグが修正されている 3.3.5 以降を必須にする
- そうすれば、Rails 側の WeakKeyMap ポリフィルを削除し、**任意オブジェクト (例: connection pool)** を WeakKeyMap のキーとして使えるようになる
- その結果として、上記のクエリキャッシュ構造のリファクタリングが可能になる

この PR 自体は「最低バージョンを引き上げるだけ」で、WeakKeyMap ポリフィル削除やクエリキャッシュの実装変更は「後続 PR で行う」と明言されています。

### 2-3. 実際の差分の内容

変更されているのは主に gemspec とガイドのバージョン宣言です。

代表的な変更例 (概念的なイメージ):

```ruby

s.required_ruby_version = ">= 3.3.5"
```

以下の各コンポーネントの `.gemspec` で、`required_ruby_version` が「3.3.5 以上」に変更されています。

- actioncable
- actionmailbox
- actionmailer
- actionpack
- actiontext
- actionview
- activejob
- activemodel
- activerecord
- activestorage
- activesupport
- rails (トップレベル)
- railties
- tools/rail_inspector
- tools/releaser

加えて、`guides/source/upgrading_ruby_on_rails.md` の Ruby バージョン要件の記載も 3.3.5 に更新されています。

コードロジックの変更はなく、あくまで「サポートする Ruby の下限バージョンを宣言上引き上げる」だけの PR です。

---

3. 影響範囲・注意点  

### 3-1. Rails 利用者側への影響

- Rails の次バージョン (この PR が入るバージョン) を使う場合、
  - Ruby 3.3.4 以下では動作対象外になります
  - CI / 本番環境ともに Ruby 3.3.5 以上に上げておく必要があります
- Gem の依存チェック (`required_ruby_version`) によって、古い Ruby では bundle install 自体が失敗するようになります

移行時のチェックリスト:

- `ruby -v` が 3.3.5 以上であることを本番 / 開発 / CI すべてで確認
- `.ruby-version` や `Gemfile` の `ruby "x.y.z"` 指定を 3.3.5 以上に変更
- 使用している他の gem が Ruby 3.3.5 に対応しているかどうかを確認
  - 特に C 拡張を含む gem (例: nokogiri, grpc, mysql2, pg など) は Ruby のマイナーバージョンアップでビルドし直しが必要な場合があります

### 3-2. 内部実装・今後の変更に関する影響

この PR の目的は「将来的なリファクタリングの前提条件づくり」です。  
今後想定される変更:

- WeakKeyMap ポリフィルが削除される
  - これにより、WeakKeyMap のキーとして使えるオブジェクトの種類が制限されなくなる
- Active Record のクエリキャッシュ実装が変更される
  - 「全 connection pool を走査して現在コンテキストのキャッシュを消す」方式から、
  - 「現在コンテキストに紐づいている pool のみを辿る」方式へと変更される見込み
- 結果として、
  - マルチ DB / マルチテナントなどで connection pool が多い環境ほど、
  - クエリキャッシュクリア時の CPU 使用量が下がる可能性が高い

ライブラリ作者視点の注意点:

- Rails 内部の WeakKeyMap 仕様に依存していた「ポリフィル前提の挙動」が、将来的に変わる可能性がある
- ただし通常のアプリケーションコードから WeakKeyMap を直接触ることは稀なので、影響を受けるのは主に Rails の拡張・プラグインを書いているような層に限られると考えられます

## [#58898](https://github.com/rails/rails/pull/58898) Avoid reprocessing ActiveRecord::Result column names {#pr-58898}

**マージ日**: 2026/10/1 | **作成者**: [@dersam](https://github.com/dersam)

1. 概要 (1-2文で)  
ActiveRecord::Result が内部で「カラム名の再処理（主に String の intern / freeze）」を行うのをやめ、DBアダプタ側での処理に一元化したパフォーマンス改善のPRです。  
これにより、不要な文字列オブジェクトの割り当てを避けつつ、カラム名配列は引き続き freeze される形になります。

---

2. 変更内容の詳細  

### 何をしているか

- `ActiveRecord::Result` 内で、カラム名 (`@columns`) に対して行っていた「都度 each で回して変換・加工する処理」を削除
- 代わりに、アダプタ（MySQL, SQLite, PostgreSQL など）の段階で文字列の intern などを済ませる前提に変更
- `ActiveRecord::Result` 側では、カラム名の配列を受け取ったあとに
  - 追加の処理は行わず
  - 配列自体を `freeze` するだけに簡略化

PR本文中のポイント:
- 「String interning is now handled in the database adapters」  
  → 文字列のインターン（同一内容の文字列を共有してメモリ節約・比較高速化する仕組み）がアダプタ側で完結する設計に統一
- 「Doing it in the adapters allows us to skip allocations that happen with the `each` version」  
  → `Result` 生成時に Ruby 側で `each` を回しながら `intern` / `freeze` などをしていた分のオブジェクト割り当てを削減
- 「We can now remove this and only freeze the array」  
  → ActiveRecord 本体では、配列の不変性だけを保証し、要素（カラム名文字列）の処理は行わない方針

### コード上のイメージ

実際の差分は1行追加・3行削除程度ですが、イメージとしては:

```ruby
# 変更前（イメージ）
def initialize(columns, rows)
  @columns = columns.map { |c| c.to_s.freeze } # / intern など
  @columns.freeze
  @rows = rows
end

# 変更後（イメージ）
def initialize(columns, rows)
  @columns = columns.freeze # 中身の文字列はアダプタ側ですでに処理済み前提
  @rows = rows
end
```

※実際のコードとは多少異なる可能性がありますが、意図としてはこのような「Result 側で列名をあれこれ加工しない」方向への簡略化です。

---

3. 影響範囲・注意点  

- **対象:**  
  - ActiveRecord を通じて DB クエリを発行し、その結果を `ActiveRecord::Result` として扱う全機能（低レベル API を含む）
- **実質的な振る舞いの変更:**  
  - 結果としてのカラム名が frozen である点は維持される想定
  - 文字列の intern など、メモリ・パフォーマンスに関わる処理がアダプタ側に完全移譲される
- **開発者が意識すべき点:**
  - 通常の AR モデル利用 (`User.select(...)` など) では、API 的な挙動は変わらないはずで、明示的な対応は不要
  - 自前でアダプタを拡張・実装している場合:
    - カラム名の文字列処理（`intern`, `freeze` など）をアダプタ側で責任を持って行う必要がある  
    - それをしていないと、Result のカラム名が想定より多くメモリを消費したり、GC 負荷が上がる可能性がある
  - 低レベルで `ActiveRecord::Result` を直接生成しているコードがあり、その中で「Result 側でカラム名を加工してくれる前提」に依存していた場合は挙動が変わる（ただし、そのような利用はかなりニッチ）

- **後方互換性のリスク:**
  - 公式にサポートされる通常の利用パターンでは、仕様変更というよりは実装の最適化に近く、互換性リスクは低い
  - ただし、カラム名オブジェクトの「同一性（`object_id`）」までテストしているようなコードがあると、intern のタイミング変更によってテストが不安定になる可能性は理論上ある

---

4. 参考情報 (あれば)  

- 関連 PR: [#58803](https://github.com/rails/rails/pull/58803)  
  - こちらで「文字列の intern をアダプタ側で行う」方針の議論・実装が進められており、今回の PR はその仕上げとして ActiveRecord::Result 側の重複処理を削除した位置づけです。
- ActiveRecord::Result の役割:
  - AR が SELECT などを発行した結果を、行列ベースの汎用的なコンテナとして表現するクラス
  - カラム名 (`columns`) と行データ (`rows`) を管理し、モデルにマッピングされる前段階の構造を担っているため、ここでのオブジェクト削減はクエリ全般のパフォーマンスに効きやすい箇所です。

## [#58892](https://github.com/rails/rails/pull/58892) Fix input `id` not matching label `for` when collection value is an empty string {#pr-58892}

**マージ日**: 2026/10/1 | **作成者**: [@55728](https://github.com/55728)

1. 概要 (1-2文で)  
`collection_radio_buttons` / `collection_check_boxes` などで、値が空文字列 `""` のときに生成される `<input>` の `id` と `<label>` の `for` が一致しなくなるバグを修正した PRです。`nil` の場合の修正 (#57209) を拡張し、「サニタイズ結果が空文字列になる値」全般に対して一貫した ID 付与になるようにしています。

---

2. 変更内容の詳細  

### 何が問題だったか

次のようなコードを考えます:

```ruby
collection_radio_buttons :user, :active,
  [["Yes", true], ["Undefined", ""]],
  :last, :first
```

期待されるのは、`value: ""` の要素に対して、`input` と `label` が同じ ID を参照することです。

しかし従来は次のような HTML が生成されていました:

```html
<input type="radio" value="" name="user[active]" id="user_active_" />
<label for="user_active">Undefined</label>
```

- `input` 側の ID: `user_active_`
- `label` 側の for: `user_active`

つまり末尾のアンダースコア `_` の有無が揃っておらず、`label` と `input` が正しく紐付かない状態でした。

背景:

- `label` 側は `sanitize_attribute_name` の結果が空文字列のときは、末尾の `_値` を付けない実装になっていた
- `input` 側（`add_default_name_and_field_for_value`）は、`nil` のときだけ `_値` を付けない挙動になっていた
- そのため「`nil` は OK だが、空文字列 `""` のときに不整合」が起きていた

### どう直したか

`actionview/lib/action_view/helpers/tags/base.rb` の `add_default_name_and_field_for_value` のロジックを変更し、

- 「元の値が `nil` かどうか」ではなく
- 「`sanitize_attribute_name(value)` した結果が空かどうか」

で、`_sanitized_value` を ID/名前に付けるかどうかを判定するようにしました。

これにより:

- `sanitize_attribute_name(value)` が空文字列になる値（`nil` や `""` など）の場合  
  → `user_active`（サフィックスなし）
- それ以外の値の場合  
  → `user_active_true` / `user_active_yes` のようにサフィックス付き

という挙動になります。`label` 側も同じロジックを使うため、常に一致するようになります。

### API レベルで影響を受ける箇所

`add_default_name_and_field_for_value` は次のヘルパから共有利用されています:

- `radio_button`
- `check_box`（`multiple: true` の場合）
- `label`（`value:` を指定した場合）

そのため、コレクション系だけでなく、単体呼び出しでも挙動が変わります。

例:

```ruby
radio_button :user, :active, ""
label :user, :active, value: ""
```

従来:

```html
<input type="radio" value="" name="user[active]" id="user_active_" />
<label for="user_active">...</label> <!-- あるいは for="user_active_" など不一致の可能性 -->
```

修正後:

```html
<input type="radio" value="" name="user[active]" id="user_active" />
<label for="user_active">...</label>
```

### テスト

- `actionview/test/template/form_collections_helper_test.rb` にテストを追加
- `collection_radio_buttons` と `collection_check_boxes` の両方について、値が `""` の場合に `id` / `for` が一致することを確認

---

3. 影響範囲・注意点  

#### 影響範囲

1. `collection_radio_buttons` / `collection_check_boxes` において、コレクションの値が空文字列 `""` の要素  
   → `id` / `for` の末尾から不要な `_` が消え、`user_active_` → `user_active` のように変わります。

2. 次のような単体ヘルパ呼び出しでも同様に ID が変わります:
   - `radio_button :user, :active, ""`
   - `check_box :user, :roles, { multiple: true }, ""`
   - `label :user, :active, value: ""`

3. これにより:
   - スクリーンリーダーやクリックターゲットの挙動が改善（`label` と `input` の紐付きが正しくなる）
   - CSS / JS が `#user_active_` のような古い ID を前提にしている場合は壊れる可能性がある

#### 注意点

- 破壊的変更の範囲は「ID 名が変わる可能性がある」に限定されますが、DOM を直接フックしているコード（テストを含む）があると影響を受けます。
- 既に #57209 を適用済みの Rails 8.1 系で、空文字列値を使っているフォームを持つアプリは、この PR で ID が「より一貫した形」に揃えられます。  
  → そのぶん不具合修正としての価値は高い一方、DOM 名の変更としては認識しておく必要があります。
- heartcombo/simple_form などフォームビルダーを利用している場合、今回の修正はその上で動くヘルパにも波及します（根本の ID 生成ロジックが変わるため）。

- 元 issue: heartcombo/simple_form#1840  
  https://github.com/heartcombo/simple_form/issues/1840#issuecomment-5872299154
- 関連 PR: #57209（`nil` の場合の不一致修正）

## [#58882](https://github.com/rails/rails/pull/58882) Fix the :validate default in the Association Basics guide [ci skip] {#pr-58882}

**マージ日**: 2026/10/1 | **作成者**: [@ramen2020](https://github.com/ramen2020)

1. 概要 (1-2文で)  
Association Basics ガイドの`:validate`オプションのデフォルト値説明が実装と食い違っていたため、関連の種類ごとに正しいデフォルト挙動が分かるように修正したドキュメント更新PRです。あわせて、`has_and_belongs_to_many` は `:validate` をサポートしないという誤った記述も削除されています。

---

2. 変更内容の詳細(あればサンプルコードも含めて)

### 何が問題だったか

元の Association Basics ガイドでは:

- `:validate` のデフォルトは常に `false`
- `has_and_belongs_to_many` は `:validate` オプションをサポートしない

と読める記述になっていました。

しかし実際の実装 (`ActiveRecord::Reflection#validate?`) は以下のようになっています。

```ruby
def validate?
  if options.key?(:validate)
    options[:validate]
  else
    options[:autosave] == true || collection?
  end
end
```

これを踏まえると:

- `:validate` が明示されていない場合  
  - `collection? == true` であれば `true`  
    → `has_many`, `has_and_belongs_to_many` はデフォルト `true`
  - `collection? == false` かつ `autosave: true` であれば `true`  
    → `has_one autosave: true`, `belongs_to autosave: true` は `true`
  - それ以外は `false`  
    → 通常の `has_one`, `belongs_to` は `false`

また、`has_and_belongs_to_many` は内部的に `has_many` を組み立てる際に `:validate` オプションをそのまま渡しており、`validate: false` なども有効です。

### ガイドへの具体的な修正内容

`:validate` セクションの説明が、次のような趣旨の内容に変更されたと考えられます（意訳）:

- デフォルト値は関連の種類によって異なる:
  - `has_many`, `has_and_belongs_to_many`  
    - デフォルト: `validate: true`
  - `has_one`, `belongs_to`  
    - デフォルト: `validate: false`
    - ただし `autosave: true` を指定した場合は `validate: true` 相当になる
- `has_and_belongs_to_many` では `:validate` が使えない、という記述を削除

PR の説明で示されていた動作確認結果は以下のとおりです（新規に1件の無効な子レコードを親に関連付けて `save` した場合）:

| Association                            | 親の `save` 結果 |
| -------------------------------------- | ---------------- |
| `has_many` (デフォルト)               | `false`  (保存失敗) |
| `has_many validate: false`            | `true`   (保存成功) |
| `has_and_belongs_to_many` (デフォルト)| `false`  (保存失敗) |
| `has_and_belongs_to_many validate: false` | `true` (保存成功) |
| `has_one` (デフォルト)                | `true`   (保存成功) |
| `has_one autosave: true`              | `false`  (保存失敗) |
| `belongs_to` (デフォルト)             | `true`   (保存成功) |
| `belongs_to autosave: true`           | `false`  (保存失敗) |

この挙動に合うようにガイドの文章が4行追加、5行削除で調整されています。

### サンプルコードイメージ

例えば:

```ruby
class Author < ApplicationRecord
  has_many :books              # デフォルトで validate: true
  has_one :profile             # デフォルトで validate: false
  has_one :account, autosave: true  # 実質 validate: true
end

class Book < ApplicationRecord
  belongs_to :author           # デフォルトで validate: false
end
```

- `author.books.build(invalid_attributes)` して `author.save`  
  → `has_many` は `validate: true` なので、`false` (保存失敗)
- `author.build_profile(invalid_attributes)` して `author.save`  
  → `has_one` は `validate: false` なので、`true` (親は保存される)
- `author.build_account(invalid_attributes)` して `author.save`  
  → `autosave: true` なので、`false` (保存失敗)

今回はこのような実際の挙動と整合するようにドキュメントだけが修正されています。

---

3. 影響範囲・注意点

- 影響範囲は **ドキュメントのみ** であり、Rails 本体の挙動・API には一切変更はありません。
- ただし、これまでガイドだけを信じて「`has_many` などでは関連先の検証はデフォルトで走らない」「`has_and_belongs_to_many` では `validate:` は効かない」と思い込んでいた場合、その理解が誤りであったことに注意が必要です。
- 実運用では、次の点を意識すると安全です:
  - 「親保存時に子のバリデーションも必ず走らせたい」  
    → `has_one`, `belongs_to` であれば `autosave: true` か `validate: true` を明示する。
  - 「親は保存したいが、無効な子がいてもかまわない」  
    → `has_many`, `has_and_belongs_to_many` なら `validate: false` を明示する。
- 他のドキュメントやブログ記事に、古い（誤った）説明が残っている可能性があるため、挙動を確認したいときは API ドキュメントかソース（`Reflection#validate?`）を参照するほうが確実です。

2. 変更内容の詳細  

### 2-1. `range_field_tag` の例の修正

`range_field_tag` のシグネチャは以下の通りです。

```ruby
def range_field_tag(name, value = nil, options = {})
```

元のドキュメント例では:

```ruby
range_field_tag 'quantity', in: 1...10
```

のように書かれており、この呼び出しは Ruby 的には

```ruby
name   = 'quantity'
value  = { in: 1...10 }  # 第2引数にオプションハッシュが入ってしまう
options = {}
```

となります。そのため、実際の出力は:

```html
<input type="range" name="quantity" id="quantity" value-in="&quot;1...10&quot;" />
```

のように、`in:` オプションが `value-in` という謎属性として出力されていました（本来期待している `min="1" max="9"` にはならない）。

これを修正するため、PR では例を次のように変更しています。

```ruby
range_field_tag("quantity", nil, in: 1...10)
# => <input type="range" name="quantity" id="quantity" min="1" max="9" />

range_field_tag("quantity", nil, min: 1, max: 10, step: 2)
# => <input type="range" name="quantity" id="quantity" min="1" max="10" step="2" />
```

ポイント:

- 第2引数に `nil` を明示的に渡すことで、`in:` / `min:` / `max:` / `step:` が正しく `options` として解釈される。
- 出力 HTML の自己終了タグ `/>` がドキュメントの例から抜けていた箇所も合わせて修正。

これにより、`number_field_tag` のドキュメント例と同じスタイル（`value` を指定しないときは第2引数に `nil`）に統一されています。

---

### 2-2. `time_field_tag` / `datetime_field_tag` の `:include_seconds` 例を削除

API ドキュメントには、以下のような説明と例がありました（イメージ）:

```ruby
time_field_tag("time", "01:01", include_seconds: true)
# => <input type="time" name="time" id="time" value="01:01:00.000" />
```

しかし実装を見ると、`time_field_tag` / `datetime_field_tag` は単に `text_field_tag` をラップしているだけで、`include_seconds:` オプションを特別扱いしていません。そのため、実際の動作は:

```ruby
time_field_tag("time", "01:01", include_seconds: true)
# => <input type="time" name="time" id="time" value="01:01" include_seconds="true" />
```

のように、`include_seconds` がカスタム属性としてそのまま出力されるだけで、秒付きフォーマット（`01:01:00.000` 等）にはなりません。

秒の有無を解釈してくれるのは以下の「フォームビルダー版」のヘルパーのみです。

- `time_field` / `datetime_field` (`ActionView::Helpers::FormHelper`)
- 具体的には `Tags::TimeField` / `Tags::DatetimeField` による処理

`*_tag` 系はあくまで「単純に `<input type="...">` を出すだけ」のヘルパーなので、`include_seconds` を知らないのが正しい挙動です。

PR では、この食い違いを解消するために:

- `time_field_tag` / `datetime_field_tag` のドキュメントから `:include_seconds` オプションに関する記述と例を削除

しています。

あえて実装側に `include_seconds` 対応を追加せず「ドキュメントを実装に合わせる」方向にしたのは、「挙動の変更ではなくドキュメントの修正に留める」という方針によるものです。

---

  - 変更ファイル: `actionview/lib/action_view/helpers/form_tag_helper.rb`
  - 追加 3 行 / 削除 8 行（実装コードではなくコメント行）

開発者視点での注意点:

1. `range_field_tag` の使い方
   - オプション (`in:`, `min:`, `max:`, `step:` など) を渡す場合、**第2引数の value を省略すると Hash が value と解釈される** ことに注意してください。

   - これは `number_field_tag` など他の `*_field_tag` にも共通するパターンです。

     - これまでも秒を扱うような特別な挙動はしておらず
     - この PR による挙動変更もない
     ため、動作が変わることはありません。ただし「ドキュメントで見た挙動」を期待していた場合は、フォームビルダーヘルパーへの移行を検討すべきです。

## [#58864](https://github.com/rails/rails/pull/58864) Generator tests avoid collisions by using a temporary directory. {#pr-58864}

**マージ日**: 2026/10/1 | **作成者**: [@ChaelCodes](https://github.com/ChaelCodes)

1. 概要 (1-2文で)
Rails のジェネレータ用テストが、テストごとに一時ディレクトリを使うようになり、`tmp/generators` 共有による並列実行時のファイル競合・テストのフレークが解消されました。これに伴い、テスト用の出力ディレクトリの削除タイミングが `setup` から `teardown` に変更されています。

---

2. 変更内容の詳細

### 背景にある問題

従来のジェネレータテストは:

- すべて `tmp/generators` を `destination_root` として使用
- `prepare_destination` が「各テストの `setup` で `destination_root` を削除 → 再作成」

という動きをしていました。

この設計だと:

1. **並列テスト実行時の競合**
   - テストAとテストBが同じ `tmp/generators` を使う
   - テストAの `setup` で `tmp/generators` を削除
   - その直後にテストBが同じディレクトリを前提に動こうとして失敗
   - → テストがフレークする（ときどき落ちる）

2. **同じパスに同名ファイルを生成するテスト同士の競合**
   - 異なるテストケースでも同じ `app/models/post.rb` のようなパスを利用すると、状態が混ざる可能性がある

という問題が起きていました。

### この PR が行ったこと

#### 1. テストごとに一時ディレクトリを使うように変更

- 各テストケース（もしくは各テストメソッド）ごとに、**ユニークな一時ディレクトリ**を `destination_root` として使うように変更しています。
- 実質的には、`Dir.mktmpdir` のような仕組みで都度ランダムなディレクトリを作り、そこでジェネレータを走らせるイメージです。

これにより:

- テスト間で `destination_root` が共有されなくなり、並列実行でも互いの出力を壊さない
- 同じパス・同名ファイルを生成するテストが複数あっても、安全に共存できる

というメリットがあります。

#### 2. `destination_root` の削除タイミングを `teardown` に移動

以前は:

- `setup` 内で `prepare_destination` を呼び、`destination_root`（= `tmp/generators`）を消して作り直していた

今回:

- `destination_root` が一時ディレクトリになり、テスト開始後にランダムに決まる
- テスト完了後にそのディレクトリをクリーンアップ（削除）する必要がある
- しかし「どのディレクトリ名か」はテスト実行中にしか分からないため、**削除処理を `teardown` 側に移動**しています

つまり:

- `setup`: 一時ディレクトリを作成し、それを `destination_root` にセット
- テスト本体: そのディレクトリ配下にジェネレータがファイルを生成
- `teardown`: 使い終わった一時ディレクトリを削除

というライフサイクルに変わりました。

#### 3. ジェネレータ用テストテンプレートの更新

変更ファイルに `generator_test.rb.tt` が含まれていることから:

- `rails g generator Foo` などで作られる **ジェネレータ用テストのテンプレート**も、この新方式に追従するよう修正されています。
- これにより、新しく作成されるジェネレータテストも、はじめから「テストごとに一時ディレクトリを使う」形になります。

#### 4. `testing/behavior.rb` の調整

`Rails::Generators::Testing::Behavior` モジュール内の `prepare_destination` 周りが:

- グローバルな `tmp/generators` を初期化する挙動から
- 一時ディレクトリベースの `destination_root` と協調する挙動へ

と変更されています。行数的には +4/-2 と小さな差分ですが、責務の位置づけ（いつ・どこで消すか）が変わっています。

---

3. 影響範囲・注意点

- **影響範囲**
  - Rails 本体の **ジェネレータテスト基盤**（`Rails::Generators::TestCase`, `Rails::Generators::Testing::Behavior`）を使っているテストに影響します。
  - `rails g generator` で生成される **新規のジェネレータ用テスト**は、この新しい一時ディレクトリ方式を前提としたコードになります。

- **メリット**
  - 並列実行時のジェネレータテストが安定する（フレークの低減）
  - テスト同士が同じファイルパスを使っても安全
  - テスト実行後に中間ファイルがきれいにクリーンアップされやすい（各テスト専用ディレクトリの削除）

- **注意点 / 互換性**
  - もし独自に `destination_root` を **固定パスに上書きしているテスト**がある場合、そのテストが新しいライフサイクル（`setup` / `teardown`）とどう干渉するかを確認する必要があります。
  - テスト中に `destination_root` を前提としたパスをハードコードしている場合（例: `Rails.root.join("tmp/generators/...")` を前提にしているなど）、一時ディレクトリ方式に合うよう見直した方がよい可能性があります。

---

- 該当 PR: https://github.com/rails/rails/pull/58864
- 問題の発端となった外部プロジェクトの PR（RubyEvents のジェネレータテスト改善）:
  - https://github.com/rubyevents/rubyevents/pull/1934
- 関連コード:
  - `Rails::Generators::Testing::Behavior#prepare_destination`  
    https://github.com/rails/rails/blob/f3866028dd6a802599a0c8a243b2f7a2cccc0932/railties/lib/rails/generators/testing/behavior.rb#L100-L103

## [#58893](https://github.com/rails/rails/pull/58893) Remove support for dynamic controller/action in routes {#pr-58893}

**マージ日**: 2026/9/30 | **作成者**: [@tenderlove](https://github.com/tenderlove)

1. 概要 (1–2文で)  
このPRでは、Railsのルーティングから「URLパラメータから `:controller` や `:action` を動的に読み取る」仕組みが完全に削除されました。Rails 5.0 から非推奨だった `get ":controller(/:action(/:id))"` 形式などが今後はエラーとなり、コントローラとアクションを明示的に指定する書き方へ移行する必要があります。

---

2. 変更内容の詳細

### 2-1. 動的 `:controller` / `:action` ルーティングの完全削除

以下のような「URLの一部をそのままコントローラ名・アクション名として解決する」ルート定義は、**もはや利用できず `ArgumentError` を投げる**ようになりました。

```ruby
# これまでは動いていたが、今後は ArgumentError
get ":controller(/:action(/:id))"
get ":controller/:action"
```

これらは Rails 5.0 から非推奨 (deprecation) になっていて、「今まで警告は出ていたが動いていたもの」が、今回のPRで**実際に削除**されています。

#### 推奨される書き換え

従来:

```ruby
get ":controller(/:action(/:id))"
# /photos -> PhotosController#index
# /photos/1 -> PhotosController#show (慣習で)
```

今後:

```ruby
get "photos",     to: "photos#index"
get "photos/:id", to: "photos#show"
```

- どの URL がどのコントローラ#アクションに対応するかを**ルート定義側で明示**するのが前提になります。
- 暗黙的にアクション名を推測したり、URLの文字列をそのままクラスやメソッドにマッピングする仕組みは消えます。

### 2-2. コントローラクラスを直接渡す書き方の変更

従来は、`to:` にコントローラクラスだけを渡すと、「動的アクション解決」と同じ仕組みに依存してアクションが補完される動作がありました。

```ruby
# 以前: 暗黙に #show などを解決していたケースがある
get "show", to: PhotosController
```

この挙動は、内部的には「動的な controller/action 解決」と同じパスに乗っていたため、今回の削除に巻き込まれています。

今後は**アクションを明示的に指定**する必要があります:

```ruby
get "show", to: PhotosController, action: "show"
# または
get "show", to: "photos#show"
```

### 2-3. `:controller` / `:action` に対する `Regexp` の扱い変更

`:controller` や `:action` に `Regexp` 制約を付けていたようなルートは、もはや **マッチし得ないルートとして即座にエラーを投げる**ようになりました。

例:

```ruby
# これまでは「どうせマッチしないルート」が定義できてしまっていたケース
get ":controller/:action", controller: /admin_.+/
```

このような「ダイナミック controller/action 前提の正規表現制約」は、そもそも今回の削除で意味をなさなくなったため、**ルート定義時点でエラーとして弾く**ように変更されています。

### 2-4. 内部実装レベルでの主な変更ポイント

高レベルにまとめると:

- `ActionDispatch::Routing::Mapper`  
  - `:controller` / `:action` を動的に解決するパス (デフォルトルーティング、レガシーな auto-routing) が削除。
  - ルート定義時に `dynamic controller/action` を検出して `ArgumentError` を上げる処理が追加。
- `ActionDispatch::Routing::RouteSet` および `Journey` 関連 (`formatter.rb`, `visitors.rb`)  
  - URL生成・パス解析の際にコントローラ/アクションを URL から補完するロジックが整理・削除。
- `ActionDispatch::Http::Request`  
  - リクエストオブジェクトが params から controller/action を「後付けで決める」ようなコードが削除され、ルートが決めた値を前提とする形に単純化。
- 各種テスト (`actionpack/test/controller/...` など)  
  - 旧来の `get ":controller(/:action(/:id))"` に依存したテストが軒並み削除/書き換え。
  - 代わりに、明示的な `to: "photos#show"` スタイルのルータに合わせてテストが修正。

コード全体としては、古い「マジックなルーティングパス」を削ぎ落とし、ルーティング → params → コントローラの流れをより単純・明示的にする変更になっています。

---

3. 影響範囲・注意点

### 3-1. 既存アプリのルーティングエラー

以下に当てはまるアプリは、Rails をこのバージョンに上げた瞬間から **起動時または最初のリクエスト時に `ArgumentError`** となる可能性が高いです。

- `config/routes.rb` に次のようなエントリが残っている:

```ruby
get ":controller(/:action(/:id))"
get ":controller/:action/:id"
match ":controller(/:action(/:id))", via: :all
```

- `resources` を使わず、上記のような「catch-all」なルーティングに頼っている古いアプリ。

対応方針:

1. 該当パターンを**全削除またはコメントアウト**。
2. 実際に必要なエンドポイントごとに、明示的なルートを定義し直す:

   ```ruby
   # NG (削除対象)
   get ":controller(/:action(/:id))"

   # OK (明示的に書く)
   resources :photos  # index/show/create/... が生成される
   get "dashboard", to: "admin/dashboard#index"
   ```

3. 既存の URL が多く、後方互換を保ちたい場合は、
   - `resources` + `member/collection` ルート
   - `scope` / `namespace` を活用してパターンをまとめる
   などで段階的に整理していくのが現実的です。

### 3-2. コントローラクラスを `to:` に渡しているルート

以下のようなコードがある場合:

```ruby
get "show", to: PhotosController
```

今後は**必ず `action:` を付与**してください:

```ruby
get "show", to: PhotosController, action: "show"
# もしくは
get "show", to: "photos#show"
```

`to: SomeController` を使うパターンはそれ自体あまり一般的ではありませんが、エンジンや internal DSL で使っている場合は注意が必要です。

### 3-3. メタプログラミング的なルーティング生成

以下のような「ループで `:controller` を動的に入れ替えつつルートを量産する」ようなメタプログラミングをしていた場合も、根本的な見直しが必要です。

```ruby
# 例: 動的 controller 名をパラメータで受けていたようなケース
%w[photos posts].each do |name|
  get "#{name}/:action", controller: name
end
```

- URL の一部をそのままクラス名等にマッピングする発想自体が危険・非推奨とみなされており、今回のPRで明確に締め出されています。
- 必要なら `resources :photos`, `resources :posts` などに展開し、アクションを列挙する形が推奨されます。

---

4. 参考情報

- この機能は **Rails 5.0 で depreciation notice が出ていた**もので、Rails 6, 7 系を経てついに削除に至った、という位置づけです。
- 公式ガイドのルーティングのベストプラクティス:
  - Rails Guides: Routing from the Outside In  
    https://guides.rubyonrails.org/routing.html  
    → `resources`, `namespace`, `scope`, `match` などを使った「明示的ルーティング」の考え方が整理されています。
- 変更内容は `actionpack/CHANGELOG.md` にも記載されており、「動的コントローラ/アクションルートの削除」が明示的な breaking change として扱われています。

このPRの本質は、「暗黙的で危険な自動マッピング」をやめて、**コントローラ/アクションはルートで明示する**という Rails の現在の設計方針をより徹底するものと理解すると良いです。

  - CI の Ruby バージョンマトリックスや `.ruby-version`, `Gemfile` の `ruby` 宣言などを、ドキュメントの要件に合わせて更新すべきかどうか判断しやすくなる。
- 「まだ Rails 8.2 の最低 Ruby バージョンを誤って低く想定していた」プロジェクトでは、実際のアップグレード作業前に Ruby 自体のアップグレード計画が必要になる点に注意してください。

4. 参考情報 (あれば)  

- 実際の最低 Ruby バージョンは、以下のいずれかを確認するのが確実です:
  - 該当 PR (#58907) の diff（`upgrading_ruby_on_rails.md` 内の記述）
  - Rails ガイド: Upgrading Ruby on Rails  
    https://guides.rubyonrails.org/upgrading_ruby_on_rails.html
  - Rails の gemspec (`rails.gemspec`) や各コンポーネントの gemspec に書かれている `required_ruby_version`  

これらを確認して、`Gemfile` 等に:

```ruby
ruby "X.Y.Z"
```

のように明示することで、チーム全体で Rails 8.2 対応の Ruby バージョンを統一できます。

## [#58905](https://github.com/rails/rails/pull/58905) Lazy call_arg inspection for attribute methods {#pr-58905}

**マージ日**: 2026/9/30 | **作成者**: [@hmcguire-shopify](https://github.com/hmcguire-shopify)

1. 概要 (1-2文で)  
`ActiveModel::AttributeMethods` 内で、属性メソッド生成時の `call_args` の `inspect` 呼び出しを「必要になった時だけ実行する」ように変更し、無駄な String オブジェクトの生成を減らすパフォーマンス改善です。モデル × カラム × 属性メソッドごとに発生していた余計な文字列割り当てが、ほとんどのケースで発生しなくなります。

---

2. 変更内容の詳細  

### これまでの動作
`ActiveModel::AttributeMethods` は、未定義メソッド呼び出し時などに、`call_args` を元にエラーメッセージやデバッグ情報を組み立てることがあります。その過程で、次のような形で引数を一括で `inspect` 化していました:

```ruby
call_args.map!(&:inspect)
```

この処理は、

- すべての `call_args` について
- まだ使われるかどうか分からない段階で
- 文字列(`#inspect` の結果)を生成し、配列を書き換える

という性質があります。

PR の説明にある通り、その後のフローでは「カラム × 属性メソッド」の組み合わせのうち、**最初の 1 回しか `call_args` の文字列表現を実際には使っていなかった**にもかかわらず、モデル × カラム × 属性メソッドごとに常に `inspect` 付きの文字列を生成していました。

### この PR での変更
`call_args.map!(&:inspect)` を「呼び出しの早い段階で一括実行」するのではなく、**実際に `inspect` された引数が必要になる箇所まで処理を遅延（lazy）させた**、というのがこの PR の本質です。

イメージとしては、従来:

```ruby
# 以前: 早い段階で必ず全引数を inspect していた
call_args.map!(&:inspect)
# 以降、エラーメッセージなどで call_args を使用
```

となっていたところを、変更後は:

```ruby
# 必要になるまで inspect しない
# ...
if need_inspected_args
  inspected_call_args = call_args.map!(&:inspect)
  # inspected_call_args を使う処理
end
```

といった形に近づけた、という変更です（実際のコードは多少異なる可能性がありますが、意図としてはこのような「使う直前で初めて inspect する」形にリファクタリングされています）。

これにより、

- 多くのケースでは `inspect` 自体が呼ばれない  
- したがって、**不要な String オブジェクトの割り当てが行われない**

という挙動になります。

---

3. 影響範囲・注意点  

### 影響範囲
- 対象: `ActiveModel::AttributeMethods` を利用している全てのモデル（`ActiveRecord::Base` を継承した通常の Rails モデルを含む）  
- 実際の影響: 主に内部のパフォーマンス改善であり、アプリ側のコード変更は不要

### 挙動の変化の可能性
通常の利用において、外部に見える挙動（API）は変わらないようになっています。注意すべき点は次のような場合です:

- `call_args` を `inspect` する前提で、`AttributeMethods` 内部の非公開 API に依存している（メタプログラミングや Monkey Patch など）  
  - そのようなコードは本来非推奨ですが、この PR により、**「常に `call_args` が文字列（`inspect` 済み）である」という前提は崩れます**。
- `call_args` の内容や型を内部フックで覗き見している場合  
  - 一部のタイミングで、以前は String だったものが、元のオブジェクト（Symbol, Numeric, など）のままになっている可能性があります。

標準的な Rails アプリケーションで、公式にサポートされている API だけを使用している限りは、動作上の違いを感じることはなく、パフォーマンスがわずかに向上するだけと考えてよいです。

---

4. 参考情報 (あれば)  

- 該当 PR: https://github.com/rails/rails/pull/58905  
- 関連コンポーネント:  
  - `ActiveModel::AttributeMethods`（Active Record モデルの動的な属性メソッド生成ロジック）  
- 類似の最適化として、Rails 本体では「例外メッセージの構築を遅延させる」「バックトレース生成を必要時のみ行う」など、`inspect` や文字列生成を遅らせるパターンが多数採用されており、本 PR もその一環の位置づけといえます。

## [#58746](https://github.com/rails/rails/pull/58746) Escape JSON with String#tr!  {#pr-58746}

**マージ日**: 2026/9/30 | **作成者**: [@federico-carrocera](https://github.com/federico-carrocera)

1. 概要 (1-2文で)  
Rails の JSON エンコード処理において、特殊文字のエスケープを `String#gsub!` ベースから `String#tr!`（ハッシュ対応版）を用いた実装へ最適化し、大きめの JSON ドキュメントで大きなパフォーマンス向上を図った PR です。エンコードが不正な場合は従来どおり `gsub!` にフォールバックするため、互換性を保ちつつ高速化しています。

---

2. 変更内容の詳細  

### 2-1. 何をしている PR か  
Ruby 本体側の新機能として、`String#tr!(hash)` が導入されました（1パスで UTF-8 文字列を書き換え可能、正規表現不要）。  
この PR では、Rails の JSON エンコーダ（特に `JSONGemCoderEncoder`）が JSON エスケープ処理にこの `tr!` を使うように変更されています。

従来の実装は:

- 文字列をバイナリエンコーディングに変更 (`ASCII-8BIT`)
- エスケープすべきバイト列を `Regexp.union` と `gsub!(regex, hash)` で置換
- UTF-8 に戻す

という流れでしたが、新しい実装では、UTF-8 のまま `tr!(hash)` によって一発変換します。

### 2-2. エスケープ対象文字とロジック  

Rails の JSON エンコードで問題になるのは主に:

- U+2028 (LINE SEPARATOR)
- U+2029 (PARAGRAPH SEPARATOR)
- `<`, `>`, `&`

これらは HTML 埋め込み時の XSS やスクリプトコンテキストでの問題を避けるためにユニコードエスケープへ変換されます。  
PR の説明中にあるマッピングは概ね次のようなものです:

```ruby
ESCAPES = {
  "\u2028" => '\u2028',
  "\u2029" => '\u2029',
  ">"      => '\u003e',
  "<"      => '\u003c',
  "&"      => '\u0026',
}
```

Rails 側でも同様のマッピングを JSON エンコード時に使用し、それを `tr!` に渡します。

### 2-3. 有効なエンコーディングのみ `tr!` を使う  

`String#tr!` は「不正なエンコーディングの文字列」に対しては例外を上げる仕様です。そのため、Rails 側では:

```ruby
def escape_with_tr(json)
  return escape_with_gsub(json) unless json.valid_encoding?
  json.tr!(ESCAPES)
  json
end
```

のように、

1. `valid_encoding?` が `true` なら `tr!` を使用（高速パス）
2. `false` なら従来どおり `gsub!` による処理（フォールバック）

という二段構成になっています。  
これにより、既存のアプリで不正なエンコーディングを含む文字列が紛れ込んでいたケースでも、今までと同じ挙動（`gsub!` ベース）で動作し、例外で落ちることを避けています。

### 2-4. パフォーマンス特性  

PR で提示されているベンチマーク結果（Ruby 4.1 dev, arm64, Darwin）は次の通りです。

- 小さい JSON（48 bytes, エスケープ対象なし）の場合
  - `gsub!`: 約 6.18M i/s
  - `tr!`: 約 4.51M i/s  
  -> 小さい & 置換不要な文字列では、事前コンパイル済み Regexp を使う `gsub!` の方が速い（`tr!` は毎回翻訳テーブルを作るため）。

- 大きな JSON（約 51KB, HTML を 900 回繰り返し）の場合
  - `gsub!`: 約 1.95k i/s （~512 µs / call）
  - `tr!`: 約 20.45k i/s（~49 µs / call）  
  -> 約 10.5 倍速い。

Rails 実運用では JSON が数 KB〜数十 KB になるケースが多いため、この変更によって全体としては十分な性能改善が見込める、と判断されています。

### 2-5. どのエンコーダが対象か  

- Rails には複数の JSON エンコーダがありますが、`JSON::Coder` が利用可能な環境ではデフォルトで `JSONGemCoderEncoder` が使われます。
- この PR では「両方のエンコーダ」が更新されていますが、現実的には `JSONGemCoderEncoder` の影響が最も大きくなります。
- `activesupport/lib/active_support/json/encoding.rb` にあるエスケープ処理が `tr!` 対応版に更新されています。

---

3. 影響範囲・注意点  

### 3-1. 影響範囲  

- 影響を受けるのは「Rails で JSON を生成する全てのコード」です。  
  例:
  - `render json: object`
  - `object.to_json`（Rails の ActiveSupport 拡張経由）
  - `ActiveSupport::JSON.encode(object)`

- 特に HTML に埋め込む JSON（`<script>` タグ内の初期データなど）でのエスケープ処理はこの変更の直接的な恩恵を受けます。

### 3-2. 互換性と振る舞いの変化  

基本的には**出力される JSON の内容は変わらない**（バイト列レベルで一致するよう、テスト & ベンチで確認済み）ことが前提で実装されています。PR 中でも以下のように検査しています:

```ruby
raise "paths disagree" unless escape_gsub(src.dup).b == escape_tr(src.dup).b
```

このため、アプリケーションコード側で想定している JSON フォーマットやエスケープ結果は従来どおりです。

ただし、次のようなケースには注意してください:

- **エンコーディングが不正な文字列を JSON に流し込んでいる場合**
  - その文字列は `valid_encoding? == false` になり、`tr!` ではなく旧来の `gsub!` パスへ回ります。
  - これ自体は挙動の変化ではありませんが、「`tr!` による高速化の恩恵を受けない」ため、そうした文字列を事前に正規化しておくと性能改善につながります。

- **Ruby バージョンとの対応**
  - `String#tr!(hash)` は Ruby 本体側の新機能に依存します。  
  - Rails 側では Ruby の該当バージョン以降をターゲットとしているため問題ありませんが、もし独自に `String#tr!` をモンキーパッチしていた場合には、挙動が変わる可能性があります。

### 3-3. パフォーマンス面の実務的な影響  

- 大量の JSON を返す API、もしくは `render json:` を大量に叩く SPA バックエンドなどでは、CPU 使用率の低減やスループット向上が期待できます。
- 逆に、非常に小さな JSON を「頻繁に」「ほぼエスケープ不要な形で」生成するマイクロサービスの場合、理論上は旧来の `gsub!` の方が速いケースもありますが、Rails 側のベンチでは「全体としては `tr!` の方が有利」と判断されています。
  - 必要であればアプリケーションレベルで独自エンコーダを実装し直すことで、局所的にチューニングする余地はあります。

---
